# 계좌 샤딩 조정 모드를 실행 구성으로 켜서 4개 프로세스로 띄운 작업

## ADR 네타

### 칸 계산은 목적지 표에서 분리하고, 칸 개수는 조정 토픽의 파티션 개수에서 읽는다

- **context(무슨 상황)**: 계좌 샤딩(계좌를 칸 256개로 나눠 워커들이 Kafka 컨슈머 그룹으로 나눠 갖는 구조)은 U1~U6까지 구현·병합돼 있었고 통합 테스트도 통과한 상태였다. 그런데 그 기능을 켜는 설정 키 `account-shard.coordination.enabled`가 레포의 어느 실행 구성에도 없었다. 기본값이 꺼짐이라, 앱을 띄우면 언제나 정적 폴백(워커 한 대)으로 돌았다. 즉 **앱으로 한 번도 뜬 적이 없는 기능**이었다.
- **왜(문제·동기)**: 실행 구성을 만들어 api 1대·매칭 워커 1대·계좌 워커 2대로 실제로 띄우자 네 군데가 막혔다. 셋은 기동을 멈추게 했고, 하나는 떠도 샤딩을 무력화했다.
  1. 계좌 워커: 담당 칸 판정(`IntPredicate`) 후보가 둘(`KafkaShardAssignment` 자신 + 그것을 감싼 `kafkaOwnedSlots`)이라 Spring이 고르지 못했다. 파라미터 이름 `ownedSlots`가 두 빈 이름과 달라 이름 해소도 안 됐다.
  2. api·매칭 워커: 같은 모양이 `AssignmentDestinationResolver` + `dynamicAccountDestinationResolver`로 있었다.
  3. 칸 계산 무력화: `ShardRoutingTable`이 "칸 계산"과 "칸→목적지 조회"를 같이 갖고 있었는데, 조정 모드는 목적지(`shard-routing.shards`)를 설정에 안 적는 것이 전제라 표가 칸 1개짜리로 폴백했다. `slotFor`가 표 길이로 나눈 나머지라 **모든 계좌가 0번 칸**이 됐고, 그 칸을 가진 워커 한 대로만 주문이 갔다. 배정은 128/128로 정상이었는데 한 대는 아무것도 못 받았다.
  4. 배정 값에 주소가 하나뿐: 계좌 워커는 주문(20040)과 체결(20060)을 다른 주소에서 받는데 `account-shard-map`에는 주문 주소만 실렸다. 매칭 워커가 그 주소로 체결을 보내 체결이 아무도 안 듣는 포트로 갔다.
- **어떻게(대안·결정·트레이드오프)**:
  - 중복 빈: `@Primary`로 우선순위 주기 / 빈 이름을 파라미터 이름과 맞추기 / 감싸기만 하는 빈 제거. **제거를 택했다** — U4 커밋 메시지가 "정확히 하나만 `IntPredicate` 빈으로 등록한다(모드 혼합 금지)"라고 의도를 적어 뒀는데, 구현 클래스 자체가 그 인터페이스라 한 겹이 더해져 의도가 깨져 있었다. 제거하면 그 의도가 성립한다. 한계는 후보가 하나라는 사실에 기대는 것이라, 같은 타입 빈이 또 생기면 다시 깨진다(이름·한정자로 지정하는 쪽이 구조적으로 안전).
  - 칸 계산: Kafka 자신이 키→파티션 계산(`Partitioner`)과 파티션→브로커 조회(메타데이터)를 나눠 갖는다. 같은 방식으로 `SlotHasher`(칸 개수만 아는 순수 계산)를 분리했다.
  - 칸 개수: 앱마다 yml에 같은 숫자를 사람이 적어 맞추는 방식은 한 곳만 틀려도 조용히 어긋난다(주문은 도착하는데 받은 워커가 NOT_OWNED로 거부). Kafka 프로듀서가 파티션 개수를 브로커 메타데이터에서 읽듯, 조정 토픽 `account-shard-assignment`의 파티션 개수를 읽어 쓰기로 했다(`ShardSlotCountSource`). 대가는 api·매칭이 기동할 때 Admin 요청을 한 번 더 보내는 것과, 파티션을 늘리면 나누는 수가 바뀌어 계좌 소유가 통째로 뒤집힌다는 제약이 생기는 것이다. 토픽은 계좌 워커가 만들므로 api·매칭은 생길 때까지 최대 60초 기다린다.
  - 체결 주소: 설정에서 두 주소를 같게 적기(A안, Aeron은 같은 채널에 스트림 ID로 구분해 태울 수 있다) / 배정 값에 두 주소를 싣기(B안). **둘 다 했다** — A안으로 먼저 돌려 나머지를 확인하고, 그다음 B안으로 코드를 고쳐 주소를 다시 갈라 놓고 재확인했다. 값 형식은 `order=<채널>\nfill=<채널>` 두 줄이다. Aeron 채널 문자열이 등호와 세로줄을 포함해(`aeron:udp?endpoint=host:1|term-length=64k`) 그 문자들을 구분자로 쓸 수 없고, 줄바꿈은 채널에 들어갈 수 없다. 주소가 하나만 적힌 옛 값은 둘 다 그 주소로 읽는다(compacted 토픽이라 남아 있을 수 있다).
- **무엇을(실제 변경·파일·커밋)**: `ecb9905` — core에 `SlotHasher`·`ShardSlotCountSource`·`WorkerEndpoints` 추가, `AccountDestinationResolver`를 `orderEndpointFor`/`fillEndpointFor`로 분리, `AssignmentDestinationResolver`가 칸별로 주소 묶음을 들도록 변경, 감싸기 빈 3곳 제거, `AccountEngine`·`AccountEventHandler`가 `SlotHasher`를 쓰도록 변경, `KafkaShardAssignment`가 두 주소를 발행. `77b637b` — 로컬 4프로세스 실행 프로파일(`application-shard-a/b.yml`, api·매칭 `application-shard.yml`, `shard-demo-seed.sql`).
- **결과·수치**: 4개 프로세스를 실제로 띄워 확인했다. 워커 둘이 칸 128개씩 배정(A=0~127, B=128~255), api·매칭이 칸 개수 256을 브로커에서 읽음, 계좌 90001(칸 109)과 90005(칸 150)의 주문이 서로 다른 워커로 감, 체결 한 건(`tradeId=7506546664061026304`)이 양쪽 워커에 반영(`applied=true` 2건). 주문 포트와 체결 포트를 다르게 둔 상태에서도 같은 결과. 테스트는 core 84건 강제 재실행 통과(건너뜀 0, 신규 `SlotHasherTest` 5건·`WorkerEndpointsTest` 4건·배정 값 두 주소 통합 테스트 1건), 다섯 모듈 테스트 통과. **워커 재기동 후 같은 칸 복귀와 재시작 시간은 미측정** — `session.timeout.ms`는 여전히 근거 없는 잠정값이다(로컬 프로파일은 30초, 코드 기본값 2분).

## 블로그 네타

### "통합 테스트는 다 통과했는데, 그 기능은 앱으로 한 번도 뜬 적이 없었다"

- **훅·핵심 주장**: 테스트가 통과한다는 것과 그 기능이 동작한다는 것은 다르다. 계좌 샤딩은 단위·통합 테스트를 다 통과하고 main에 병합돼 있었지만, 그 기능을 켜는 설정이 실행 구성에 없어서 아무도 앱으로 띄운 적이 없었다. 켜 보니 기동을 막는 결함 셋과 샤딩을 통째로 무력화하는 결함 하나가 나왔다.
- **context**: v2는 계좌 잔고를 DB 락 없이 메모리에서 처리한다. 그게 성립하려면 계좌 하나를 워커 하나만 만져야 하고, 그래서 "누가 어느 계좌를 맡나"가 구조의 전제다. 그 배정을 사람이 설정에 적지 않고 워커들이 Kafka 컨슈머 그룹으로 나눠 갖게 만들었다.
- **어떻게(서사·근거)**:
  1. "적용돼 있나"를 클래스 존재와 호출부로 판정했다가 틀렸다. 런타임 구성으로 판정해야 했다 — 기능을 켜는 키가 어느 yml에도 없었다.
  2. 실행 구성을 만들어 띄우자 기동이 멈췄다. Spring이 같은 타입 빈 둘 중 하나를 고르지 못한 것인데, 원인은 구현 클래스가 이미 그 인터페이스를 구현하고 있는데 감싸기만 하는 빈을 한 겹 더 둔 것이었다. 커밋 메시지에는 "정확히 하나만 등록한다"고 적혀 있었다 — 의도와 구현이 어긋나 있었고, 앱을 안 띄우면 드러나지 않는 종류였다.
  3. 기동이 되자 더 큰 것이 나왔다. 배정은 128/128로 멀쩡한데 주문이 전부 한 워커로 갔다. 칸 계산과 목적지 조회가 한 객체에 있었고, 조정 모드에서는 목적지를 설정에 안 적으니 그 객체가 칸 1개짜리로 폴백했다. 나누는 수가 1이면 모든 계좌가 0번 칸이다.
  4. 고치는 방향을 Kafka 자신의 구조와 대조했다. 키→파티션 계산과 파티션→브로커 조회는 Kafka에서도 다른 부품이고, 파티션 개수는 설정에 적지 않고 브로커에서 읽는다. 둘 다 그대로 따랐다.
  5. 마지막으로 체결이 도착하지 않는 문제가 남았다. 계좌 워커는 주문과 체결을 다른 포트에서 받는데 배정 값에는 주문 주소만 실렸다. 설정으로 두 포트를 같게 두면 당장 돌지만 제약이 설정에만 남는다. 값에 두 주소를 싣도록 고쳐 제약을 코드로 옮겼다.
