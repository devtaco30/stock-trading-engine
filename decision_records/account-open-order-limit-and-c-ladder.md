# 정리 호출 수정, 계좌당 미체결 상한, 그리고 상한 숫자를 정하려고 속도를 측정하는 방법

## ADR 네타

### 체결 번호 구간 정리는 스냅샷 경계에서 한 번만 한다 (ADR-039)
- **context(무슨 상황)**: 계좌 워커가 맡은 계좌 수가 늘수록 주문 접수가 느려졌다. 같은 총 60만 건을 계좌 300개에 나누면 초당 약 6만 건, 3,000개에 나누면 약 3.3만 건이었다.
- **왜(문제·동기)**: 계좌 3,000개·총 60만 건·로그 끔 조건에서 업무 thread를 `jstack`으로 0.3초 간격으로 떴더니 덤프의 90%에서 일했고 그 시간의 58%가 `AccountEventHandler.pruneIfDurable()`(이벤트마다 모든 계좌를 돌며 오래된 세대를 지우는 호출), 32%가 스냅샷 만들기였다. 저널 thread는 4~5%뿐이라 저널 기록은 원인이 아니었다. 한계: safepoint 편향 가능, 덤프 40~82개.
- **어떻게(대안·결정·트레이드오프)**: 대안은 이벤트마다 유지, `durableSeq` 변경 때만 호출(ADR-034가 이미 기각: 쓰기 thread가 느리면 지울 세대가 다음 갱신까지 남음), 이벤트를 받은 계좌만 지움(이벤트 없는 계좌는 세대가 계속 쌓임), 스냅샷 경계에서 모든 계좌를 한 번 지움. 마지막을 택했다(Jack 결정). 대가: durable이 양수가 된 뒤 옛 코드는 다음 이벤트에서 세대를 2개로 줄였고 새 코드는 다음 경계까지(최대 10,000 이벤트) 쌓여 있던 세대를 전부 둔다. 복구 직후에는 실제 쓰기 객체의 `durableSeq`가 0에서 시작(`AccountSnapshotWriter.java:51`)해 첫 경계에서는 정리가 안 되고 두 번째 경계에서 처음 일어나, 복원 세대 3개가 최대 약 2 x 10,000 이벤트 남는다.
- **무엇을(실제 변경·파일·커밋)**: `AccountEventHandler`에서 이벤트마다 부르던 `pruneIfDurable()`을 없애고 `takeSnapshotAndStartNewGeneration()` 끝(새 세대를 열고 직렬화해 offer한 뒤)에서 한 번만. 시험을 먼저 썼고 옛 코드에서 2건이 실패(durableSeq 조회 스냅샷 2회에 20,001회). 처음 쓴 시험은 `durableSeq`를 올리는 시점과 정리 사이 경합으로 3회 중 2회 실패해, 엔진을 종료한 뒤 세대를 직접 읽는 방식으로 고쳤다. 커밋 c39023b, 문체 정리 3ee8e28.
- **결과·수치**: 총 60만 건 N=3000 접수 속도 중앙값 33,210 → 65,869건/초(1.98배, 3회, 범위 비겹침). 곡선 재측정(고정 m, 로그 켬, 옛/새 빌드 번갈아 3회): N=3000 옛 32,427 / 새 78,934(2.43배, 범위 비겹침), N=300 옛 59,396 / 새 73,158(1.23배, 범위 겹침), N=10·30은 차이 없음. 측정 구간이 0.05~0.6초로 짧아 개별 값 변동이 큼. 한 대 맥.

### 계좌당 미체결 상한을 두고 복구는 엔진 설정값으로 판정한다 (ADR-040)
- **context(무슨 상황)**: 계좌 하나의 미체결 주문 수에 제한이 없었다. 계좌 이벤트에 취소가 없어(`AccountEventType`: BUY, SELL, BUY_FILL, SELL_FILL, SETTLEMENT) 접수된 주문은 체결로만 줄어든다. 주문 한 건이 그 계좌의 모든 예약을 훑어서(`AccountState.reservedSellQuantity`, `totalReserved`) 비용이 계좌당 미체결 수에 비례한다.
- **왜(문제·동기)**: Jack이 업계 방식으로 정했다: 매수와 매도 예약을 합친 계좌의 미체결 수가 상한에 이르면 새 주문을 거부하고 기존 주문은 그대로 둔다.
- **어떻게(대안·결정·트레이드오프)**: 복구가 상한 값을 어디서 받느냐가 핵심이었다. A안 엔진 설정값(채택, Jack이 「재시작 때 상한을 바꿀 이유가 없다」고 답함), B안 접수 시점 상한을 저널 엔트리에 기록(코덱 flags 0b1_0000 + int, 옛 엔트리는 무제한으로 읽혀 옛 저널 재현), C안 거부 판정을 수신 thread가 저널에 기록(기각: 미체결 개수는 처리 thread가 고치는 상태이고 저널 핸들러가 기록한 뒤 비즈니스 핸들러가 읽는 순서라 판정이 저널 시점에 없음). A안의 대가: 상한을 바꿔 이어서 시작하면 재적용 판정이 달라져 돈이 어긋난다(낮추면 접수·전달한 주문의 체결이 예약 없는 체결로 폐기, 올리면 거부·통보한 주문이 접수되어 매칭에 없는 예약이 남음). 감지 장치가 없고 운영 규칙으로만 막는다. 상한은 필수 설정(코드에 기본값 없음), 부하 하네스는 `MAX_OPEN_ORDERS` 환경변수를 요구한다(비교용은 1000000을 명시).
- **무엇을(실제 변경·파일·커밋)**: `AccountState.openOrderCount()`, `RejectReason.OPEN_ORDER_LIMIT_EXCEEDED`, 핸들러의 holdingFull 거부 뒤 검사, `AccountEngine.setOpenOrderLimit`, `AccountWorkerProperties.maxOpenOrdersPerAccount`(필수·1 이상), 복구 경로가 엔진 설정값을 이벤트에 찍음. 복구 시험이 BUY만 다뤄 SELL 분기에서 설정을 지워도 통과해, 매도 복구 시험 2건을 더하고 줄을 지우면 실패하는 것을 확인했다. 커밋 552cd7c, 030edb7, a988269.
- **결과·수치**: account-disruptor 151건, account-worker 173건 통과(변경 트리 3회 연속). 알려진 대가를 ADR에 적음: 거부된 requestId도 장부에 남아 같은 번호 재시도는 중복 처리, 취소가 없어 상한에 닿으면 체결로 줄 때까지 풀 방법 없음, 담당 없는 종목 slot의 주문은 재전송 대기 중에도 미체결로 셈, 회신 없이 주문이 사라지는 경로가 있으면 예약이 상한을 영구히 소모(`MatchingEventHandler.java:213-216`, `:221-225`, `RejectReplyPublisher.java:105-124` 확인, 계좌 재시작 때 미전달 주문 재구성 코드는 못 찾았으나 전수 확인 아님). 상한 숫자는 미정.

### 상한 숫자를 정하려고 계좌당 미체결 C별 접수 속도를 측정하는 방법: 성장 곡선에서 C 고정 사다리로
- **context(무슨 상황)**: 상한 C를 정하려면 「계좌 N개가 각각 미체결 C건을 든 고정 상태」의 접수 속도가 필요하다.
- **왜(문제·동기)**: 처음 잰 값들은 목적에 맞지 않았다. 고정 m 방식은 측정 창이 0.05~0.12초라 흔들렸고, 성장 곡선은 C가 0에서 자라는 동안의 구간 평균이라 C가 고정된 상태가 아니었으며, 계좌 수 N과 전체 합 N x C가 같이 변해 둘을 가를 수 없었다. 「창 10초 이상」과 「쌓은 양의 몇 % 이내만 보내 C를 거의 고정」은 N=300 C=6000 한 칸 말고는 같이 만족되지 않는다(계산: 10초 창에 필요한 양이 쌓인 양의 13~510%).
- **어떻게(대안·결정·트레이드오프)**: 방식 R: 보유를 최종 C 이상으로 시드하고 단계마다 수량 1 매도로 C까지 쌓은 뒤, 가용 보유(보유 - 예약)보다 1 큰 수량의 매도를 보낸다. 이 매도는 계좌의 모든 매도 예약을 훑은 뒤 `INSUFFICIENT_HOLDING`으로 거부되므로(`AccountState.java:304-305`, `:391-396`) 순회 비용은 같고 예약이 늘지 않아 C가 고정되고 창을 마음대로 늘릴 수 있다. 쌓는 구간은 보고기의 접수 합계가 오르는 구간이라 거부 구간과 분리된다. 대리값 검증으로 같은 상태에서 접수를 드리프트 5% 이내로 소량 보내 접수/거부 비를 측정한다. 대가: 체결이 없는 상태라 운영 균형 상태(체결·정산 처리, 매칭 호가창 가동)를 재현하지 못하고, 거부마다 WARN 로그가 나므로 그 로거를 ERROR로 올려 껐다(운영에서는 거부마다 WARN이 남아 비용이 더해진다).
- **무엇을(실제 변경·파일·커밋)**: 측정 브랜치에 `step_rates.py`(m 구간·전체 합 구간 분석), `ladder_plan.py`(단계별 쌓기량·거부 수량·접수 검증량·시드 보유), `ladder.sh`(사다리 실행기, DRY_RUN 시험), `probe_rates.py`(거부·접수 구간 분석), U10Tool `--quantity`·`U10_SENDER_WAIT_MS`, run.sh `ACCEPT_WAIT_SECS`. 모든 단위를 시험 먼저로 구현했다. 커밋 5254152, 3c38134, b9297ff, c49047f, 4860359, d486807, 621c74c, 2eefade.
- **결과·수치**(상한 검사 끈 MAX_OPEN_ORDERS=1000000 비교용, 새 빌드, 거부 속도 건/초, 3회 중앙값, 모든 창 10초 이상, 건수 일치): N=30: C=201 224,562 / 999 107,438 / 2001 40,265 / 6000 15,628. N=100: 133,286 / 75,667 / 34,368 / 9,676. N=300: 45,069 / 24,791 / 12,804 / 4,300. 속도 x C가 N=30 약 0.8~1.1억, N=100 약 0.6~0.8억, N=300 약 0.25억으로 C=999 이상에서 거의 일정(예약 하나당 순회 약 9~12 / 13~17 / 39ns). 같은 C에서 N=300은 N=30의 0.20~0.32배. 접수/거부 비: N=300 C=6000 0.74~0.83(접수 창 16~18초), N=300 C=2001 0.78~0.91(창 1~2초), N=100 C=6000 0.55~0.78(창 3~4초), N=30 C=6000 0.28~0.31(창 2초). 같은 전체 합 [18만,60만)에서 N을 바꾼 기존 성장 곡선 비교: N=30 4.8k, N=100 12.2k, N=300 27k(계좌당 m이 클수록 느림). 같은 m [2000,6000)에서는 N이 클수록 느림(13.3k, 11.9k, 6.0k). 말하지 못하는 것: N 영향의 원인(주문을 모든 계좌에 돌려 보내 캐시가 밀리는 효과라는 가설만, 미검증), 사다리 끝 접수 속도가 기존 성장 곡선 값과 다른 이유(N=30 C=6000 9.7k 대 4.5k, 미확인), 한 대 맥.

## 블로그 네타

### "주문 한 건이 계좌의 예약을 전부 훑는다: 계좌당 미체결 상한을 정하려고 속도를 측정하다"
- **훅·핵심 주장**: 접수 속도가 계좌 수에 따라 달라지는 줄 알았는데 원인은 이벤트마다 모든 계좌를 도는 정리 호출이었고(jstack 58%), 그것을 고치고 나니 이번에는 계좌 하나가 든 미체결 수 C가 접수 속도를 거의 1/C로 깎았다. 상한은 그 곡선을 보고 정한다.
- **context**: 단일 writer 계좌 엔진(링버퍼 한 thread)이 주문마다 그 계좌의 예약 맵 전체를 순회한다. 취소가 없다.
- **어떻게(서사·근거)**: (1) 같은 총량인데 계좌 수만 달라 느려지는 현상 -> jstack으로 정리 호출 확인 -> 호출을 스냅샷 경계로 옮김 -> 2.43배. (2) 상한 도입과 복구 판정을 설정에서만 읽는 결정(저널에 상한을 안 싣는 대가: 운영 규칙으로만 막음). (3) 속도 측정 설계가 목적에 맞지 않아 세 번 바뀐 과정: 고정 m은 창이 너무 짧고, 성장 곡선은 C가 고정이 아니며, 최종적으로 거부되는 매도로 C를 고정하는 사다리. 거부 경로가 같은 순회를 하므로 C를 그대로 둔 채 길게 잴 수 있다는 점이 핵심. 대리값이 접수와 얼마나 다른지(접수/거부 0.28~0.91)를 같은 상태에서 잰 것까지.
- **재료(커밋·도식·수치)**: 위 ADR 네타 세 건의 수치와 커밋. 도식 후보: 단계별 사다리(쌓기 -> 거부 구간 -> 접수 검증), N x C 격자의 거부 속도 표, 속도 x C 일정함. 시험이 잡은 버그: 정리 시험 경합(durableSeq를 올리는 시점), 복구 시험이 SELL을 빼먹은 빈틈, 분석 스크립트가 첫 보고 줄을 버리던 것.

### "같은 접수 속도 숫자가 서로 다른 질문에 답하고 있었다": 상한을 정하려는 측정에서
- **훅·핵심 주장**: 숫자가 나왔다고 목적에 맞는 것은 아니다. 필요한 것은 C를 고정한 상태의 속도였는데, 처음 읽은 값은 C가 자라는 중의 평균이나 N이 같이 변하는 값이었다.
- **context**: 계좌당 미체결 상한을 정하는 근거. 비교 대상은 C 하나여야 하고 N, 주문 종류, 빌드, 부하 방식, 창 길이는 고정해야 한다는 Jack의 지적.
- **어떻게(서사·근거)**: 각 측정이 실제로 답한 질문(정리 호출 효과, 같은 합에서의 N 영향, C 고정 상태의 속도)과 한계를 나란히 놓는다. 한계: 체결 없는 상태, 접수 대신 거부로 잰 대리값, 주문을 모든 계좌에 돌려 보내는 접근 패턴, 한 대 맥.
- **재료(커밋·도식·수치)**: 성장 곡선 표(ov-N, ml-N), 같은 전체 합 비교 표, 사다리 표. 시간 어림을 시계로 재지 않고 적었다가 두 번 정정한 일, 시험 RED를 보려고 하네스 스크립트를 실제 실행해 도커·앱이 뜬 일(내 PID만 정리)도 과정 재료.
