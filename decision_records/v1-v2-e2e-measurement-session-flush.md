# v1/v2 전 과정 측정 — 하루 종일 세션 플러시 (dc 기준)

멀티세션(2b 조정·39 설계리뷰·a4 계측구현·ec 입력생성·dc 통합실행) 협업으로 진행한 v1/v2
전 과정(e2e) 측정 트랙의 마무리 flush. 개별 결정은 이미 `v1-v2-e2e-measurement.md`·
`e2e-measurement-driver-integration.md`·`dc-handoff-2026-09-16.md`에 있다 — 이 파일은
그 사이사이 코드·다른 결정 기록엔 안 남는 **판단의 흐름**을 남긴다.

## ADR 네타

### 측정 설계가 실측으로 두 번 틀린 걸 잡은 과정 — 지연 단일지표 → A/B 분리
- **context**: 39의 원설계는 "끝점을 접수·예약 반영까지 옮기고, 그 지연(p50/p95/p99)을
  주지표로 삼는다"였다. 10만 건을 한 번에 쏘고 재는 계획으로 구현까지 마쳤다.
- **왜(문제)**: 실제로 돌려보니 v1(order-engine)의 DB 반영 속도가 API 접수 속도보다
  압도적으로 느렸다(뒤에 A에서 확인: 초당 수백 건 vs 수천 건). 도착률이 처리 용량을
  넘는 상태에서 지연을 재면, 그 지연은 "한 건 처리에 걸리는 시간"이 아니라 "밀린 줄에서
  기다리는 시간"이다 — Little의 법칙(이용률이 100%에 가까워지면 대기시간이 발산)대로
  패스를 거듭할수록 p50이 18초→48초→85초→118초로 불어났다. 설계 자체가 "포화 아래에서
  재야 한다"는 전제를 안 걸어서 생긴 결함이었다(39도 사후에 인정).
- **어떻게(대안·결정)**: 측정을 **A(용량 — 부하를 최대한 밀어넣고 완전 소화까지 기다린
  뒤 총건수÷총시간)**와 **B(지연 — A에서 나온 용량 이하로 도착률을 고정, k6
  constant-arrival-rate)**로 분리했다. B의 표본은 10만 건에서 1만 건으로 낮췄다(39
  검증: p99 추정엔 상위 1%에 100개 표본이면 충분, 10만 건을 저속 도착률로 흘리면
  패스당 수십 분이라 비현실적).
- **무엇을**: `replay-e2e.js`에 `N`(건수 제한)·`RATE`(도착률 고정) 옵션 추가.
  `decision_records/v1-v2-e2e-measurement.md`를 A/B 설계로 개정(39).
- **결과·수치**: A로 v1 실제 용량(동시성9=384.6건/초)을 먼저 재고, 그 절반(192건/초)을
  B의 기준 도착률로 확정. 재설계 후 v1 B 측정은 4패스 전부 보낸 건수=반영 건수 정확히
  일치, 실패율 0%로 클린한 데이터를 얻었다.

### 동시성 3→9배인데 처리량은 1.7배만 — v1에게 "제 실력"을 낼 기회를 준 이유
- **context**: v1의 order-engine을 기본 설정(Kafka 파티션3·컨슈머 동시성3)으로 재니
  용량이 227.3건/초였다. 이 수치만으로 리포트를 냈으면 "동시성을 안 올려본 거 아니냐"는
  반박에 답이 안 된다(2b 지적).
- **왜**: v1 아키텍처(ADR-004, accountId 파티셔닝으로 병렬화 가능한 구조) 자체의 한계인지,
  단순히 설정을 기본값으로 방치한 것인지 구분해야 결과가 방어된다.
- **어떻게**: 파티션·컨슈머 동시성을 9로 올려 재측정. 227.3→384.6건/초로 1.7배만 올랐다
  (순수 컨슈머 병렬성 부족이었다면 3배에 가깝게 올라야 함) — DB(비관적 락 경합 또는
  insert 자체 단가)가 이미 일부 벽으로 작용 중이라는 결론. 어느 쪽이 더 큰 비중인지는
  프로파일링하지 않아 미확인으로 명시.
- **무엇을**: 이후 모든 B(지연) 측정은 동시성9 기준으로 진행(v1에게 유리한 설정에서
  비교).
- **결과·수치**: A절 표, 위 참고.

### B-2(v2 고도착률)의 꼬리 지연이 측정 불가였던 이유 — 단일 머신 측정의 한계
- **context**: v2를 자기 용량 추정치(≥4000/초)의 절반(2000/초)까지 밀어 "본질 지연"을
  재려 했다. 1차 실행에서 특정 패스의 p99가 튀었다(9.36ms→20.5ms).
- **왜**: 재실행에서는 다른 패스들도 튀었다(p99 62ms·58ms). CPU 샘플링을 붙여보니
  RATE=2000 부하가 몰리는 구간(약 5초)에 **k6 자체가 CPU 54~69%를 쓰고, 전체 CPU idle이
  11~26%까지 떨어졌다** — 측정 대상(v2)과 부하 생성기(k6)가 같은 노트북의 CPU를 놓고
  실제로 경쟁하고 있었다.
- **어떻게(판정)**: 이 구간의 꼬리 지연(p95/p99/max)은 v2의 값이 아니라 "경쟁의 값"이라
  판단해 **"이 장비에서 측정 불가"로 명시**하고 결론에서 뺐다. 중앙값(p50, 0.36~0.92ms)은
  이 경쟁에 상대적으로 덜 흔들려서 그대로 인용했다 — 두 번의 실행 모두 v1(12~13ms)보다
  압도적으로 낮아 헤드라인 결론(v2가 훨씬 빠르다)은 안 흔들렸다.
- **무엇을**: 헤드라인은 경쟁이 없는 B-1(초당 192건, 양쪽 동일)로 확정, B-2는 보조로
  p50만 인용.
- **결과·수치**: "제대로 재려면 부하 생성기를 다른 장비에 둬야 한다"를 남겨 — 실패가
  아니라 단일 머신 측정의 한계를 실측으로 드러낸 것으로 프레이밍.

### main이 실수로 fast-forward된 사고 — 재발 방지
- **context**: 측정 트랙(feat/c7-load-harness)이 완성됐다고 판단한 시점에, "측정은 main
  기준" 관례를 따르려고 곧바로 main에 병합하고 그 위에서 측정을 시작했다.
- **왜**: main이 이미 그 브랜치의 조상이라 병합이 **fast-forward**로 처리돼(새 머지 커밋
  없이 포인터만 이동) 아무 잡음 없이 조용히 넘어갔다. main=측정 브랜치가 돼버려 "어디까지가
  확정된 main인가"가 사라졌다 — 이후 측정 도중 버그를 고치면 그게 main 바로 옆에 붙는
  상황이 됐다. 39가 `git log`의 머지 커밋 메시지 방향("Merge branch 'main' into
  feat/c7-load-harness"가 main HEAD에 남아있는 것)을 보고 잡아냈다.
- **어떻게**: main을 사고 이전 커밋(`2544421`)으로 `git reset --hard`(파괴적 명령 —
  2b·Jack 승인 하에 `CLAUDE_GIT_OK=1` 플래그로 실행) 하고, `feat/c7-load-harness`를
  `--no-ff`로 다시 병합 — 커밋 `448dd47`, 병합 커밋 메시지에 트랙 전체 요약을 담았다.
- **무엇을**: 이후 규약 — **검증(측정·실험) 브랜치는 확정되기 전 main에 fast-forward로
  들어가지 않는다. main은 `--no-ff`로만 움직인다.**
- **결과·수치**: 재병합 후 `./gradlew build` main에서 BUILD SUCCESSFUL, 토폴로지
  확인(`git log --oneline --graph`)으로 병합 커밋이 정상적으로 남아있음을 확인.

## 블로그 네타

### "부하 테스트를 하다가 부하 테스트 도구를 의심하게 된 이야기"
- **훅·핵심 주장**: v1과 v2, 두 아키텍처의 진짜 격차를 재려다가 세 번이나 "재는 방법
  자체"가 틀렸다는 걸 실측으로 알게 됐다 — 도착률이 처리 용량을 넘으면 지연이 아니라
  대기 줄을 재게 된다는 것, 컨슈머 동시성만 올려선 안 되고 v1에게도 최선의 설정을 줘야
  한다는 것, 그리고 부하 생성기 자신이 CPU를 먹어 측정 대상과 경쟁할 수 있다는 것.
- **context**: 학습 프로젝트에서 v1(Kafka+Postgres 비관적 락)과 v2(Aeron+인메모리
  single-writer)의 실제 처리 능력·지연을 대조하는 게 목표였다. 이력서에 넣을 수치라
  방어 가능해야 했다.
- **어떻게(서사·근거)**: ①처음엔 그냥 10만 건 쏘고 지연을 봤는데 패스를 거듭할수록
  지연이 18초→118초로 폭주 — Little의 법칙을 실측으로 재발견 → A(용량)/B(지연) 분리.
  ②v1을 기본 설정으로 재고 "v2가 압도적으로 빠르다"고 하려다, 동시성을 안 올려본 채
  비교하면 반박당한다는 걸 깨닫고 3→9로 올려 재측정(3배 아니라 1.7배만 올라 DB가 벽임을
  발견). ③v2를 한계까지 밀어보려는데 그 부하를 만드는 k6 자신이 CPU 절반 이상을 먹어
  측정값이 흔들림 — CPU 샘플링을 붙여 "이건 v2 문제가 아니라 내 노트북 문제"임을 확인.
  ④측정 결과 자체와 별개로, 완성됐다고 판단한 순간 브랜치를 main에 병합했다가 그게
  fast-forward라 조용히 사고가 나서 되돌리고 다시 병합하는 일도 있었다.
- **재료(커밋·도식·수치)**: `448dd47`(재병합 커밋, 전체 트랙 요약), `docs/
  _c7_v1_v2_throughput_report.html` 9절(확정 수치 전체), CPU 샘플링 로그(`loadtest/
  results/cpu-v2-b2*-*.log`), Kafka 백로그 48만 건 재발견 사례(order-engine이 group-id를
