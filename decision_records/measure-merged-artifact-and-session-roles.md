# 병합 먼저, 측정 나중 — 수치가 가리키는 코드를 일치시키기 / 그리고 멀티세션 역할 분리

> 조정·문서 세션 기록. 코드 변경은 병합 커밋 하나(`7c5369a`).

## ADR 네타

### 부하 수치는 병합된 산출물에서 잰다 — 측정 대상 브랜치를 먼저 확정

- **context(무슨 상황)**: v2 접수 경로(주문 → 202 응답, 계좌 워커 반영)의 처리량·지연을 재서 v1 실측(2026-09-04, 479/649 req/s)과 나란히 놓고 이력서에 쓰려 했다. 부하 하네스(기동 스크립트·k6 시나리오·메트릭 리스너)는 별도 브랜치 `feat/c7-load-harness`에 있었고, 그 브랜치는 어제 밤 기준점 `5a65cd3`에서 분기했다. 계획은 "측정 → 수치 삽입 → 병합" 순서였다.
- **왜(문제·동기)**: Jack이 "코드도 계속 수정 중인데 뭘 측정하느냐"로 짚었다. 확인해 보니 측정 브랜치에는 같은 시각 다른 브랜치에 있던 **주문 발신 버퍼 재사용 수정**(`9b76720`, `AeronMatchingOrderSender`가 주문마다 256B direct 버퍼를 새로 잡던 것 제거)이 빠져 있었다. 이 수정은 주문 전달 핫패스에 있고 부하에서 차이가 날 수 있는 지점이라, 빠진 채 재면 v2를 실제보다 낮게 재게 된다. 동시에 다른 세션이 계좌 상태·이벤트 핸들러(검증·체결 반영 핫패스)를 고치는 중이었다. 즉 "README에 박을 숫자"와 "링크를 열면 보이는 코드"가 처음부터 어긋나는 구조였다.
- **어떻게(대안·결정·트레이드오프)**: 세 선택지. ①측정 브랜치에 자원 관리 브랜치를 rebase해 조합으로 측정 ②`5a65cd3` 기준으로 재고 "이 수치는 커밋 X 기준"만 명시 ③제출 범위 브랜치를 먼저 main에 병합하고 병합된 main에서 측정. ③을 택했다. 수치의 근거가 "지금 링크가 가리키는 코드"가 되어야 이력서에서 방어된다. 대가는 병합이 제출 작업의 첫 단계가 되어 순서가 바뀌는 것이다. 제출 범위 밖 작업(주기 스냅샷·tradeId 세대 가지치기)은 병합하지 않고 계속 진행하되, README에 "이 수치는 커밋 X 기준"을 적어 나중에 그 코드가 들어가도 어긋나지 않게 한다.
- **무엇을(실제 변경·파일·커밋)**: main을 `fix/v2-resource-management`로 fast-forward(38커밋 = 체결 Aeron 이관·v2 게이트웨이·udp 전환·계좌 상태 프로젝션·체결 fan-out·멱등 상한 + 자원 관리 수정 2건), 그 위에 `feat/c7-load-harness`를 merge(`7c5369a`). main 전용 작업 폴더를 worktree로 따로 만들어 진행했다(다른 세션이 쓰는 폴더의 브랜치를 바꾸지 않기 위해).
- **결과·수치**: 병합된 main에서 `./gradlew test` 전체 GREEN(2분 32초, 73 태스크 실행). 부하 수치는 아직 **미측정** — 이 병합 위에서 잰다. 원격 push와 PR은 아직 안 함(`main 직접 푸시 금지` 규칙, Jack 결정 대기).

### 멀티세션 역할 분리 — 설계·구현·측정·조정을 창 단위로 못 박는다

- **context(무슨 상황)**: 한 프로젝트를 창 다섯 개(설계·리뷰 / 자원 관리 구현 / tradeId·스냅샷 구현 / 부하 측정 / 조정·문서)가 나눠 맡아 같은 밤에 병렬로 돌렸다. 작업 폴더는 git worktree로 분리했다.
- **왜(문제·동기)**: 역할이 섞였다. ①조정 세션이 설계 결정(자료구조·스냅샷 주기·범위)을 대신 내려 구현 세션에 넘겼다 ②구현 세션이 설계 질문을 조정 세션에 했다 ③결정 기록을 누가 쓰고 어느 브랜치에 넣을지 정해두지 않아 설계 세션이 혼란 ④설계 세션의 작업 폴더가 다른 세션 브랜치로 바뀌어 있었다 ⑤측정 대상 코드를 아무도 안 정해 옛 코드를 잴 뻔했다.
- **어떻게(대안·결정·트레이드오프)**: 창마다 하나의 책임만 준다. 설계 세션 = 설계 확정·리뷰·커밋 승인·결정 기록 텍스트, 자기 폴더를 갖지 않고 리뷰할 세션의 폴더를 읽는다. 구현 세션 = 구현만, 설계 질문은 설계 세션에 직접(조정 세션 경유 금지). 측정 세션 = 측정과 리포트만. 조정 세션 = 병합·브랜치·순서·이력서 문서만, 설계 기본값을 정하지 않는다. 결정 기록은 그 코드가 올라가는 브랜치에 코드와 같은 커밋으로. 대가는 왕복이 늘어나는 것(조정 세션이 대신 답하면 빠르지만 결정 출처가 흐려진다).
- **무엇을(실제 변경·파일·커밋)**: 코드 없음. worktree 5개(원본=자원 관리, `-c7`=하네스, `-docs`=문서, `-durability`=스냅샷 구현, `-main`=병합·측정).
- **결과·수치**: 역할표는 Jack 승인 대기. 재설정 전까지 실제로 발생한 손실 = 구현 세션이 조정 세션의 임의 기본값으로 착수했다가 설계 세션 확정값으로 갈음한 것 한 건.

## 블로그 네타

### "무엇을 측정했는가 — 브랜치가 여러 개일 때 수치는 어느 코드의 것인가"
- **훅·핵심 주장**: 성능 수치는 숫자보다 "어느 커밋에서 쟀는가"가 먼저다. 브랜치가 여럿이면 측정 하네스가 있는 브랜치가 곧 측정 대상이 되고, 그 브랜치에 정작 핫패스 수정이 빠져 있을 수 있다.
- **context**: 이력서에 넣을 v1/v2 처리량 비교를 준비하던 중, 측정 브랜치에 주문 발신 버퍼 재사용 수정이 빠져 있던 것을 발견.
- **어떻게(서사·근거)**: 측정 하네스를 별도 브랜치로 뺀 결정이 낳은 부작용, "병합 먼저 측정 나중"으로 순서를 뒤집은 근거, README 수치에 기준 커밋을 박는 습관.
- **재료(커밋·도식·수치)**: `9b76720`(버퍼 재사용), `7c5369a`(병합), v1 실측 479/649 req/s, 병합 후 전체 테스트 2분 32초 GREEN.

### "창 다섯 개로 한 레포를 돌렸더니 — 역할이 섞이는 지점은 정해져 있다"
- **훅·핵심 주장**: 여러 에이전트 세션을 병렬로 돌릴 때 깨지는 건 코드 충돌이 아니라 결정권이다. 조정 역할이 답을 대신 내리는 순간 설계의 출처가 사라진다.
- **context**: 제출 마감을 앞두고 설계·구현 둘·측정·조정을 창 다섯으로 나눠 돌린 밤.
- **어떻게(서사·근거)**: 섞인 다섯 지점, worktree로 파일 충돌은 막았지만 결정권 충돌은 안 막힌 것, 창마다 책임 하나와 통신 라인을 고정한 규칙.
- **재료(커밋·도식·수치)**: worktree 5개 구성, 역할표.
