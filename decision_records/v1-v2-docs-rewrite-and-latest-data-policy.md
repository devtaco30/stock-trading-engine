# v1·v2 비교 문서 재작성과 최신 측정값만 쓰는 기준

이 flush는 속도 비교 리포트와 구조 비교 문서를 읽히는 구조로 다시 쓰고, 측정값을 최신 실행으로 한정한 과정을 담는다. 측정 자체(비교 지점을 체결 완료로 옮김, v2 대기 설정 50µs)는 `v1-v2-compare-match-complete-and-idle-strategy.md`에 있다.

## ADR 네타

### 비교 문서를 「결론, 핵심 수치, 범위, 제한사항, 부록」 세 층으로 다시 쓴다
- **context(무슨 상황)**: 속도 리포트는 12절, 50KB였고 표가 연속으로 나왔다. 결론이 첫 화면에 없었고 실행 폴더명·해시·내부 단계 표가 본문 흐름을 가렸다. 구조 문서 초안도 처리 단계 표, 불변조건 표, 평가 기준 표가 연속이었다. 독자는 Jack과 기술 면접관이다.
- **왜(문제·동기)**: Jack이 "읽기 어렵다", "산문을 하나하나 읽고 있으려니 지친다"고 반복 지적했다. 사실관계는 맞아도 독자가 30초 안에 「무엇이 어느 구간에서 빠른가, 어떤 조건에서 유효한가, 무엇을 아직 비교하지 않았는가」에 답할 수 없었다.
- **어떻게(대안·결정·트레이드오프)**:
  - 대안 A: 기존 파일을 부분 수정한다. 문장·표를 고치는 것만으로는 순서와 정보 계층을 못 바꾼다.
  - 대안 B: 요약 페이지를 앞에 추가한다. 본문의 표 연속과 부록 섞임이 그대로 남는다.
  - 결정: 새 파일로 재작성해 교체한다. 속도 문서는 독자용 요약(결론 문장, 숫자 카드 4개, 포함·미포함 구간, 제한사항 3개), 검토용 본문(핵심 결과 표 하나, 범위 다이어그램, 구간 A~D, 자원, idle strategy 별도 실험, 제한사항 표, 결론), 재현용 부록(접는 영역)으로 나눈다. 시각 요소는 숫자 카드, 범위 다이어그램, M p50·p99 막대그래프 셋만 만든다. 구조 문서는 한 문장 결론과 핵심 차이 카드 4개를 첫 화면에 두고, 구현 경로·내부 큐 이름·FIFO 크기·줄번호는 접는 부록으로 내린다.
  - 대가: 부록이 길어진다(속도 문서 부록 A~I). 원문 표를 쪼개거나 부록으로 옮기는 과정에서 숫자를 빠뜨릴 위험이 있어, 본문 숫자와 이전 문서의 숫자 목록을 대조해 확인했다.
- **무엇을(실제 변경·파일·커밋)**: `docs/_v1_v2_structure_REWRITTEN.html`(구조, 새 파일), `_workspace/portfolio/V1_V2_SPEED_REPORT.html`(속도, 새 구조로 교체), `_workspace/portfolio/legacy/V1_V2_SPEED_REPORT_before_rewrite.html`(교체 전 원본). 커밋 없음(문서 폴더는 커밋 제외).
- **결과·수치**: 속도 문서 본문 숫자는 이전 문서에 있던 값뿐이고 새로 만든 값은 없다(측정 기준일만 추가). 빠진 값은 비율(약 0.10, 약 2.2배)과 초 환산(약 14.7초, 약 20.3초)으로 재계산 금지 지시에 따라 뺐다. 태그 검사 오류 0건. 렌더는 맨 위부터 결론, 부록 A·D 펼침까지 직접 확인했다. 모바일 폭 렌더는 확인하지 않았다.

### 측정값은 최신 코드·구성의 실행만 근거로 쓰고 과거 실행은 legacy로 옮긴다
- **context(무슨 상황)**: 속도 문서에 초당 4,000건 측정과 v1 속도 단계 측정이 「비교 불가」 표시와 함께 남아 있었다. 질문에 답할 때도 과거 코드의 실행(`c-db2` 등)을 찾아 수치를 인용했다.
- **왜(문제·동기)**: 과거 코드의 값이 문서에 있으면 독자가 현재 구현의 값과 섞어 읽는다. Jack이 "테스트값 죄다 최신화, 과거 데이터 전부 legacy에 옮기고 언급도 하지 마"라고 지시했다.
- **어떻게(대안·결정·트레이드오프)**:
  - 대안: 「비교 불가」 표시를 붙여 유지, 부록으로 내림, legacy로 이동하고 문서에서 제거.
  - 결정: legacy 이동과 문서 제거. 최신 실행은 `c-m1`, `c-m2`, `c-x1`, `c-x2` 넷이다.
  - 대가: 초당 4,000건 이상의 v2 한계와 부하 증가 시 포화 시점이 문서에서 사라진다. Jack은 "4,000건/초 이상은 지금 스펙으로 못 버틸 테니 해봐야 가치가 없다"고 판단했다. 이 판단의 근거 데이터는 없고, v2 hot path의 천장은 최신 구성으로 측정하지 않았다.
- **무엇을(실제 변경·파일·커밋)**: 워크트리 `stock-trading-engine-segments`의 `loadtest/results/c-*` 17개와 `k6-solo-*` 2개, `stock-trading-engine-sfid`의 `c-db4-*` 2개를 각 `results/legacy/`로 이동(`mv`, 되돌릴 수 있음). 결과 폴더는 gitignore라 git 변경 없음.
- **결과·수치**: 속도 문서 안의 과거 실행 이름·4,000건 값은 0건.

### 공개·제출 문서에는 자기 부정 어휘를 쓰지 않고, 한계는 조건 문장과 접는 영역에 둔다
- **context(무슨 상황)**: 구조 문서 초안 1절에 「가장 큰 위험 3개」를 걸고 「구멍」「공백」「미구현」「확인 필요」 태그와 「합의된 목표값이 없다」를 썼다. 이 문서는 이력서에 붙는다.
- **왜(문제·동기)**: Jack이 "이런 걸 이력서에 첨부하겠냐"고 지적했다(2026-09-28 「자폭」 재발). 지원자가 자기 설계를 판정하는 문장을 먼저 꺼내면 안 된다.
- **어떻게(대안·결정·트레이드오프)**: 사실은 숨기지 않고 어조와 위치를 바꾼다. 1절 위험 항목을 삭제하고 태그를 제거했고, 목표는 「정합성, 지연, 재시작 뒤 상태 이어받기」와 각각의 확인 방법으로 다시 썼다. 속도 문서의 제한사항 표(제한사항, 왜 중요한가, 이 문서에서 할 수 있는 말)는 측정 보고서의 한계 공개 의무라 유지했다.
- **무엇을(실제 변경·파일·커밋)**: `docs/_v1_v2_structure.html`(초안, 위 표현 제거), `~/.claude/rules/jack-repeated-mistakes.md`·메모리 `feedback_public_doc_no_self_critique.md`에 규칙 기록.
- **결과·수치**: 구조 문서 새 판에서 「위험·공백·미구현·확인 필요」 0건.

### 컨슈머를 3배로 늘렸을 때 처리량이 1.7배인 이유는 파티션별 몫의 차이와 DB 경합의 합이 후보이며 원인은 분리하지 못했다
- **context(무슨 상황)**: `v1-v2-e2e-measurement.md`의 용량 측정에서 v1 컨슈머·파티션 3개는 227.3건/초, 9개는 384.6건/초였다. 원인은 「락 경합인지 insert 단가인지 미확인」으로 남았고 이력서 문장이 이 값을 사용한다.
- **왜(문제·동기)**: Jack이 「카프카 스펙을 늘렸는데 왜 1.7배냐」, 「테스트 데이터가 한 파티션에만 많으면 효과가 없는 것 아니냐」고 물었다.
- **어떻게(대안·결정·트레이드오프)**: 후보 다섯을 정했다(DB 커밋·쓰기 경합, 같은 노트북의 CPU 경쟁, 파티션 분배 불균형, `holdings` 행 락 경합, 합계 쿼리 비용)을 세웠다. 접수 단계 키가 accountId라 접수끼리의 계좌 락 경합은 후보에서 빠진다. 파티션별 몫의 차이는 입력 파일 계좌 100개를 Kafka 기본 파티셔너(murmur2) 방식으로 나눠 직접 계산했다. 원인을 가르는 측정(컨슈머 3과 9에서 단계 시간·스레드별 처리 건수·CPU 비교)은 제안만 하고 Jack이 하지 않기로 했다. 분배를 고르게 하는 방법 넷(계좌 수 늘리기, 파티션 수를 컨슈머보다 크게, 커스텀 파티셔너, 키 제거)은 대가와 함께 제시했고 Jack이 "됐어"로 끝냈다.
- **무엇을(실제 변경·파일·커밋)**: 코드 변경 없음. 계산은 `stock-trading-engine-sfid/loadtest/results/e2e-input.jsonl`(100,000건, 계좌 100개, 계좌당 1,000건)을 읽어 수행.
- **결과·수치**: 앞 30,000건 기준 가장 바쁜 파티션 ÷ 평균이 3개일 때 1.11, 9개일 때 1.42(앞 10,000건 기준 1.13, 1.41). 이상적 3배는 (9/1.42)÷(3/1.11)로 약 2.3배(계산값, 파티션 배정을 실제 Kafka에서 확인하지 않음). 실측 1.7배와의 차이는 미분리. 최신 v1 단계 측정 `c-l1-20261005-2022`는 250건/초에서 첫 포화 신호(지연 증가: 회차 안 p50 3,635에서 6,460µs, dropped 0, drain 8초, 유효 회차 1개)였다. 이 값은 지연 증가 신호이고 처리량 한계를 직접 잰 값이 아니다. 그래서 이력서의 「385건/초」와 「용량의 50%」는 당시 코드의 값으로만 한정해야 한다.

## 블로그 네타

### "표가 열 개인 측정 보고서를 30초에 읽히게 만들기"
- **훅·핵심 주장**: 사실이 맞아도 독자가 결론을 못 찾으면 읽히지 않는다. 결론, 핵심 수치, 범위, 제한사항, 부록 순서로 층을 나누고 시각 요소를 셋으로 제한하니 첫 화면에서 답이 나왔다.
- **context**: 12절 50KB 속도 리포트와 표 연속 구조 문서. 독자는 면접관.
- **어떻게(서사·근거)**: 부분 수정, 요약 추가, 재작성 중 재작성을 고른 이유. 재작성하면서 숫자를 빠뜨리지 않으려고 본문 숫자와 이전 문서 숫자 목록을 자동 대조한 방법. 한계를 숨기지 않고 표(제한사항, 왜 중요한가, 할 수 있는 말)로 한곳에 모은 방법.
- **재료(커밋·도식·수치)**: 새 문서 두 개, 범위 다이어그램(M이 A+B+C+D인 구간 강조)과 막대그래프, 숫자 대조 결과(새 숫자 0).

### "컨슈머를 3배 늘렸는데 처리량은 1.7배였다: 파티션 키가 계좌 100개일 때 파티션별 몫의 차이"
- **훅·핵심 주장**: 병렬도를 올려도 키가 몇 개 안 되면 가장 바쁜 파티션이 전체 처리량을 정한다. 계좌 100개를 파티션 9개에 나누면 가장 바쁜 파티션이 평균의 1.42배를 맡아 이상적 3배가 약 2.3배로 줄어든다.
- **context**: v1 컨슈머 3에서 9, 227에서 385건/초. 원인 미분리.
- **어떻게(서사·근거)**: 후보 다섯과 키 구조(접수는 accountId, 매칭·체결은 stockCode)로 빠지는 후보를 가른 과정. murmur2로 입력 파일을 직접 나눠 계산하고, 계산이 설명하는 범위(3배에서 2.3배)와 설명하지 못하는 범위(2.3배에서 1.7배)를 나눠 말한 점. 분배를 고르게 하는 네 방법의 대가(순서·락 경합·매핑 관리).
- **재료(커밋·도식·수치)**: 파티션별 계좌 수 분포(9개일 때 6~16개), 최대/평균 1.11과 1.42, v2의 슬롯 256칸 방식과의 대비(ADR-031).
