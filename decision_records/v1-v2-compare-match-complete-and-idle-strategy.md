# v1·v2 속도 비교를 체결 완료 지점으로 맞추고 v2의 스레드 대기 설정을 줄인 과정

이 flush는 속도 리포트(`_workspace/portfolio/V1_V2_SPEED_REPORT.html`)를 만드는 동안 바뀐 결정 셋을 담는다. 결정 하나(비교 지점과 v2 대기 설정)는 `adr/ADR-038-…`로 이미 정리했고, 나머지 둘(체결번호 발급기, 측정 중 알게 된 것)은 ADR이 없다.

## ADR 네타

### 체결번호 발급기는 시계가 뒤로 가도 예외 없이 번호가 늘어나게 바꾼다(v2 매칭만)
- **context(무슨 상황)**: 측정 중 컴퓨터 시계가 뒤로 움직인 일이 세 번 있었다. macOS의 시간 맞춤 프로그램(`timed`)이 `settimeofday`로 시계를 −2.14·−1.94·−0.14초 조정한 것이고 시스템 로그로 확인했다. 체결번호는 `(시각 << 22) | (node << 12) | 순번`인데 사용 중인 relops Snowflake는 시각이 직전보다 작으면 예외를 던진다. 결과로 v1 order-engine에서 주문 번호 발급이 37건 실패했고, v1 정산에서 10건 실패했고, v2 matching-worker는 체결을 처리하는 소비자 스레드가 멈춰 그 뒤 회차에서 체결이 0건이 됐다. 처음에는 「프로세스가 28초 멈췄다」고 잘못 해석했는데 Hikari의 「약 28초」는 점검 주기 30초에서 조정 크기를 뺀 값이었다.
- **왜(문제·동기)**: 측정이 시계 사건 때문에 무효가 됐고, 엔진 안에서 현재 시각(wall clock)을 읽는 것 자체가 위험하다. ADR-023이 계좌 워커의 orderId를 이미 현재 시각을 읽지 않고 (nodeId, 카운터)로 바꿔 두었다. 매칭의 체결번호에도 같은 원칙(2c)을 적용해 구현했다가 롤백했다. 카운터는 저널 끝이 날아가면(Archive 파일 동기화 수준 0, 전원 장애) 이미 낸 번호보다 작은 값으로 복구되고, 계좌가 새 체결을 「이미 처리한 번호」로 보고 버린다. 에러 없이 잔고가 틀어지는 경우라 증명으로 위험이 0이 되지 않는 변경은 구현하지 않기로 했다.
- **어떻게(대안·결정·트레이드오프)**: 해결안 다섯을 견줬다(`_workspace/portfolio/LLD_F_SNOWFLAKE_OPTIONS.html`). A는 번호 형식을 그대로 두고 논리 시계를 사용한다(직전 시각 `last`와 순번을 들고, 읽은 시각이 `last`보다 클 때만 시각을 따르고 아니면 순번만 올리며, 순번이 4095를 넘으면 `last`를 1 올린다). B는 카운터(위험 증명 불가), C는 두 주문 번호에서 체결 번호를 계산(63비트에 안 들어가 충돌 확률이 10억 건에서 약 5%), D는 기다렸다 재시도(한도보다 큰 조정에는 여전히 죽음), E는 바꾸지 않음. A를 골랐다. 새 위험이 테스트와 코드 검색으로 없어지고, 재시작 뒤 번호 유일성은 지금 있는 위험 그대로 남는다. 범위는 v2 매칭 프로그램만이고 공용 `SnowflakeIdGenerator`와 v1은 바꾸지 않았다(비교 대상인 v1을 건드리지 않기 위해). Jack은 「애초에 Snowflake를 엔진 안에서 사용하는 것이 위험하다」고 짚었고, 카운터의 위험이 증명되지 않아 롤백한 상태라 발급기만 고치기로 정했다.
- **무엇을(실제 변경·파일·커밋)**: `matching-worker/.../id/MonotonicSnowflakeIdGenerator`(공용 클래스를 상속해 `AccountFillPublisher`와 Holder 타입을 유지, 부모의 relops 인스턴스는 사용하지 않음), `SnowflakeConfig` 배선, 테스트 12개(시계 −136ms·−1,833ms·−30초 역행, 같은 ms 4097번째 번호, 100만 호출 유일성, 8스레드 유일성, 번호에서 시각을 읽는 코드가 없는지 소스 검사). 커밋 1509af9·56554ce·93fd861.
- **결과·수치**: 측정 중 실제 역행이 두 번 있었다. 2026-10-05 10:14:54 −1.916초(c-m1 v2 7회차 도중)와 13:55:53 −1.880초(c-m2 v2 2회차 도중)이고, 둘 다 matching-worker 로그에 예외가 없었고 그 회차의 M 기록이 4,775건이었다. 발급 호출이 역행 시점과 실제로 겹쳤는지는 호출 시각 분포로 확인하지 않았다(체결이 초당 약 90건 발급되던 구간이라 겹쳤을 가능성이 높다는 추정). 재시작 뒤 같은 번호가 다시 나올 위험은 해결하지 않았다(복구가 체결을 재발급하지 않아 지금은 문제가 아니다).

### 비교 지점을 접수·예약 시점에서 주문 발행부터 체결 완료(M)로 옮긴다
- **context(무슨 상황)**: ADR-036은 접수·예약 시점에서 v1과 v2를 비교했다. 이후 헤드라인을 계좌 반영 완료까지(F)로 바꿔 측정했는데 반영의 뜻이 달랐다(v1 정산 트랜잭션 DB 커밋, v2 account-worker의 메모리 갱신).
- **왜(문제·동기)**: 같은 이름의 값이 다른 일의 시간이라 한 표에 놓을 수 없었다. ADR-036은 체결 시점이 한 주문에 귀속되지 않는다는 이유로 제외했는데, 입력이 같은 가격·수량의 매수·매도 쌍이라 총 체결 건수가 고정되고, 지연을 체결을 일으킨 주문(나중에 도착해 매칭을 일으킨 쪽)의 첫 체결에 귀속시키면 한 건에 값이 하나 생긴다.
- **어떻게(대안·결정·트레이드오프)**: 비교 지점 셋(접수·예약 / 계좌 반영 / 체결 완료) 중 두 구현이 매칭 결과를 받는 같은 지점에서 끝나는 체결 완료(M)를 골랐다. 대가는 계좌 반영과 DB 반영, 클라이언트 전달이 값에 들어 있지 않다는 것이다. 도착률 초당 192건은 v1 용량 384.6건(컨슈머·파티션 9개)의 절반이라 v1 이용률 약 50%에서 큐가 쌓이지 않는다.
- **무엇을(실제 변경·파일·커밋)**: v1 `MatchingConsumer`에 `fill = result.get()` 직후 시각 한 번(계측을 켰을 때, 체결을 일으킨 주문의 첫 체결만)과 `MatchingSegmentStages`의 `M`·`D_match`, v2 `MatchingSegmentStages.recordFirstFill`의 `M`(방출 시각 W-P14 − W-P0), 분석기의 「발행~체결 완료(M) 비교」 절. 커밋 f16363c·6ac9441·ee9389b·f69770e.
- **결과·수치**: 초당 192건, M p50/p95/p99는 v1 4,964/6,500/14,610µs(유효 10회차), v2 기본 대기 설정 5,171/7,125/8,030µs(유효 10), v2 변경 설정 515/681/1,564µs(유효 9)다. 구간 B p50은 v1 3,105µs, v2 37.0µs(기본)·53.0µs(변경). 기본 설정에서는 중앙값이 비율 1.04로 같았고, 구간 A·C(프로세스 사이 이동)가 v2에서 약 2.5ms였다(v1 888·1,014µs). 앱 JVM CPU 합계는 0.93 / 1.11 / 2.09코어.

### v2의 수신 스레드 대기 상한을 1ms에서 50µs로 줄인다
- **context(무슨 상황)**: v2의 이동 구간 A(발행부터 account-worker의 첫 읽기)와 C(접수 완료부터 matching-worker의 첫 읽기)가 각각 약 2.5ms라서 접수 처리(B)에서 얻은 3ms 이득이 상쇄됐다. 코드를 읽어 보니 api의 `order-dispatcher`, account-worker의 `aeron-account-order-receiver`와 `aeron-matching-order-publisher`, matching-worker의 `aeron-order-receiver`가 읽을 일이 없으면 `BackoffIdleStrategy`로 기다린다(Agrona 상수: spin 10번, yield 5번, park 1µs에서 최대 1ms). Aeron 드라이버의 sender·receiver·conductor도 기본이 같은 Backoff이고, 세 프로세스(api, account-worker, matching-worker) 모두 임베디드 MediaDriver를 따로 띄운다.
- **왜(문제·동기)**: 초당 192건이면 주문 간격이 평균 약 5ms라 스레드가 깊은 대기에 있는 시간이 길고, 주문이 오면 대기에서 돌아오는 시간이 지연에 더해진다. v1의 Kafka consumer는 `poll`이 데이터가 오면 바로 돌아오는 조건(Kafka 클라이언트의 일반 동작, 이 프로젝트의 v1 설정에서 별도 확인은 못 함)이라 대기 조건이 다르다. v2 기본 설정을 비교 대상에 그대로 두면 「설정이 잘못된 v2」와 비교하는 셈이 된다는 것이 Jack의 판단이었다.
- **어떻게(대안·결정·트레이드오프)**: 대안 넷: 기본 유지 / 우리 스레드 네 곳만 park 상한 50µs / 네 곳과 드라이버 sender·receiver를 50µs / busy-spin(쉬지 않고 확인). 환경 변수 `EXPERIMENT_IDLE`(default·threads·driver)로 같은 빌드에서 켜고 끌 수 있게 했다. 알 수 없는 값은 시작을 막고, 켜면 프로세스 시작 때 WARN 한 줄을 남긴다. 켠 설정은 park 상한만 50µs로 줄인 Backoff다(busy-spin은 스레드 10개가 10코어 노트북에서 k6·Postgres와 코어를 다퉈 새 지연이 섞일 수 있어 먼저 사용하지 않았다). 세 번째 안을 채택했다. 「최적」이라고는 적지 않는다 — 50µs 한 값만 측정했다.
- **무엇을(실제 변경·파일·커밋)**: core `support/IdleStrategies`(모드 해석과 전략 생성), 네 스레드 클래스가 `IdleStrategy`를 주입받는 생성자, 세 드라이버 Context를 정적 메서드로 뺀 리팩터링과 driver 모드의 sender·receiver 설정, 하네스가 `EXPERIMENT_IDLE`을 `env.txt`에 기록하고 분석기가 실험 표시를 맨 위에 적는 변경. 테스트는 헬퍼 7개와 스레드 네 곳, 드라이버 Context 세 곳, 하네스·분석기까지 각각 먼저 썼다. 커밋 5827d13·455d0bc·a4ad54f·be35ebc·6cedb82·9a68581. 설정은 측정 브랜치의 환경 변수이고 제품 코드의 기본값으로는 올리지 않았다.
- **결과·수치**: 3회차 별도 실험(유효 2회차)에서 우리 스레드만 바꾼 세트(c-x1)는 A 1,188µs·C 1,222µs·M 2,567µs, 드라이버까지 바꾼 세트(c-x2)는 A 190µs·C 180µs·M 477µs였다. 드라이버 스레드의 대기가 이동 시간의 큰 몫이었다. 11회차 정식 측정(c-m2, 유효 9)은 A 202·C 191·M 515µs, 앱 JVM CPU 0.93코어에서 2.09코어. 3회차 실험의 상위 1% 값은 표본이 작아 신뢰하기 어렵다. 미측정: 50µs 외의 값(10µs·200µs·busy-spin), v1 Kafka 설정의 조정 여지(적용 중인 producer 설정은 `acks=all`·`enable.idempotence=true`·`retries=2147483647`·`linger.ms=0`, kafka-clients 3.8.1), 장시간·고부하에서의 영향, 초당 4,000건에서의 처리 한계, 확장 성능.

## 블로그 네타

### "v2가 빠르다는 말이 안 나올 때: 비교 지점을 같은 곳으로 맞췄더니 중앙값이 같아졌다"
- **훅·핵심 주장**: 계좌 반영 지연으로 비교하면 v2가 2.3배 빨라 보이지만, 두 구현이 같은 지점에서 끝나는 체결 완료까지로 맞추면 중앙값이 비율 1.04로 같다. 속도 비교는 값보다 「끝나는 지점이 같은가」가 먼저다.
- **context**: v1(DB 락+Kafka)과 v2(single-writer+Aeron)를 같은 입력으로 비교했다. 반영의 뜻이 구현마다 달랐다.
- **어떻게(서사·근거)**: 접수 시점 → 계좌 반영 → 체결 완료로 지점을 옮기며 값이 달라지는 과정. 구간 A·B·C·D로 쪼개 보니 v2가 접수 처리(B)에서 3ms를 줄이고 이동 구간(A·C)에서 늘렸다. 원인을 판정하기 전에 코드로 확인한 사실(스레드 네 곳과 드라이버 스레드가 Backoff로 대기)과 가설(대기에서 돌아오는 시간)을 분리해서 적었다.
- **재료(커밋·도식·수치)**: `V1_V2_SPEED_REPORT.html`의 구간 표, `docs/_resume_basis_qa.html`의 M 구간 도식, M p50 4,964 대 5,171µs.

### "스레드의 대기(park) 시간이 지연이 된다: Aeron 드라이버의 idle strategy를 50µs로 줄인 실험"
- **훅·핵심 주장**: 프로세스 사이를 한 번 넘을 때마다 받는 스레드가 최대 1ms까지 대기(park)해서, 초당 192건에서는 그 시간이 이동 구간 약 2.5ms로 나타난다. 우리 스레드와 Aeron 드라이버의 대기 상한을 50µs로 줄이자 M 중앙값이 5,171µs에서 515µs로 줄었고, 대가로 CPU가 1.11코어에서 2.09코어로 늘었다.
- **context**: 처음에는 우리 스레드만 바꿨다. 이동 구간이 절반으로 줄고(1.2ms 안팎) 나머지는 드라이버 스레드의 대기였다.
- **어떻게(서사·근거)**: 코드로 확인한 것과 가설을 구분하며 읽는 과정(Agrona `BackoffIdleStrategy` 상수, Aeron 드라이버 기본 전략, 세 프로세스의 임베디드 드라이버), 한 가지 변수(대기 상한)만 바꾸는 실험 설계(환경 변수 세 모드, 기본 모드에서 동작이 같다는 테스트), 두 단계 측정(우리 스레드만 / 드라이버까지), 「최적」이라고 쓰지 않은 이유(한 값만 측정).
- **재료(커밋·도식·수치)**: 커밋 5827d13~9a68581, c-x1·c-x2·c-m2 값 표, CPU 표(0.93 / 1.11 / 2.09코어), 한계(3회차 별도 실험, 50µs 외 값 미측정).

## 이력서·리포트 문안 판단 (2026-10-16 추가)

### 문안에서 대가와 범위 결정을 가른 기준
- **context(무슨 상황)**: v1·v2 속도 비교 문안(리포트 요약, 이력서 항목)에 「대가는 두 가지」 뒤로 장애 시 계좌 처리 정지와 Failover 미구현 문단이 붙었다.
- **왜(문제·동기)**: 읽는 사람이 「두 가지라더니 셋째가 있다」로 읽는다. 장애 정지는 대가로 세울 만큼 크지 않다는 Jack의 판단이 있었다.
- **어떻게(대안·결정·트레이드오프)**: 대가는 v2 구조를 택해서 따라오는 값(CPU 0.93→2.09코어, 순서·중복 방지·재전달·복구를 애플리케이션이 직접 구현·검증하는 부담)만 센다. 장애 시 정지는 Failover를 구현하지 않은 범위 결정이라 「범위에서 뺀 것도 있습니다」로 시작하는 별도 문단에 둔다. idle strategy는 CPU 증가의 원인이자 측정 조건이라 대가로 따로 세우지 않고 측정 도해 문단에 둔다.
- **무엇을(실제 변경·파일·커밋)**: 문안만 정리했고 코드·ADR 변경 없음. 복구에 걸리는 시간은 이 flush에서 확인하지 않았다.
- **결과·수치**: 측정 도해 문단에는 「park 상한 50µs는 측정 브랜치의 `EXPERIMENT_IDLE=driver` 설정이고 제품 기본값(1ms)이 아니다」가 들어가야 한다(ADR-038:60). 이 문장과 기본값 1ms를 남길지는 Jack 결정 대기.
