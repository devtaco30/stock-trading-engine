# v2 남은 작업 설계와 이력서 제출 트랙 — 무엇이 남았고, 왜 이 순서로, 무엇을 먼저 제출하나

> 설계·조정 세션(stock-trading-engine-2b) 기록. 코드 변경 없음. 산출물 = `docs/_v2_progress_map.html`(진행 지도), `docs/_v2_remaining_work_design.html`(남은 다섯 묶음 설계, 유닛 21개), README v2 절, ADR-020·021·031·033 정식화 초안.
> 세션 넷(39 설계·리뷰 / dc 구현 / ec 자원 관리 / a4 내구성)의 상태를 SendMessage로 취합해 반영했다.

## ADR 네타

### v2 완료 범위와 남은 작업의 순서 — 운영 내구성 → 조회 완결 → fork2 → C7 → 문서

- **context(무슨 상황)**: 9월 7일부터 9일 동안 코드 커밋 84개로 v2의 왕복 경로(주문 접수 → 계좌 검증·예약 → 매칭 → 체결 fan-out 반영 → T+2 정산 → 계좌 조회모델)가 다 만들어졌고 3-JVM UDP 라이브 왕복이 로그로 확인됐다(`4905c7b`). main에는 매칭 코어·계좌 워커·저널·스냅샷·정산 워커까지만 병합돼 있고 그 뒤 35개 커밋이 브랜치 6개 스택으로 남아 있다. "어디까지 왔고 무엇이 남았나"를 한 장에 모아야 했다.
- **왜(문제·동기)**: 남은 항목이 메모리 여러 블록에 흩어져 있고, 일부는 코드 확인 없이 적혀 있었다(예: "옛 부하 인프라 T0 폐기" 라고 썼는데 실제로는 2026-09-04 k6 실측 리포트가 있었다). 오늘 코드를 열어 줄번호까지 확인한 것만 남은 항목으로 세웠다. tradeId 멱등 집합 무상한(`AccountState.java:42`), 주기 스냅샷 없음(graceful만, `@Scheduled` 0건), 발신마다 direct buffer 할당(`AeronMatchingOrderSender.java:98`, `AeronAccountOrderSender.java:60`), fan-out 이후 복구 다중화 미착수(`AccountFillReplayer.java:23-31` 단일 recording 가정), fork2 HA 코드 0, 주문상태 폴링 조회 API 없음(202 응답이 requestId도 안 돌려줌, `OrderAcceptedResponse.java:8`), C7 부하 미착수, ADR 020 이후 정식 파일 없음.
- **어떻게(대안·결정·트레이드오프)**: 다섯 묶음으로 나누고 의존 순서로 배열했다. ①운영 내구성(주기 스냅샷 + tradeId 세대 prune, 버퍼 재사용, 체결 recording 다중 복구) ②조회 완결(주문상태 프로젝션 + 폴링 GET) ③fork2 HA·리밸런싱(설계 세부 5개 확정 → 슬롯 소유 모델 → 부분 드레인 → Kafka 그룹 제어 평면 → standby → 로컬 kill 데모) ④C7(기동 스크립트, k6, 1샤드 vs 2샤드 기울기, v1 대비) ⑤문서. 근거: 주기 스냅샷은 fork2 핸드오프(revoke 때 스냅샷 → assign 때 replay)의 전제이고, tradeId 상한은 C7 부하 중 OOM을 막는 전제다. fork2가 C7 앞에 있어야 최종 토폴로지(standby 포함)에서 측정된다. 조회 완결은 독립이라 위치가 자유롭다. 39가 이미 만든 tradeId·주기 스냅샷 설계(`docs/_tradeid_snapshot_prune.html`, 세대 prune·경계 키 = 저널 적용 순번)는 그대로 채택하고, 그 설계에 없던 "러닝 중 스냅샷을 어떻게 찍나"를 채웠다. `AccountEngine.snapshot()`(:151-155)은 quiescent 전제라 러닝 중 호스트 스레드가 부르면 찢어진 상태를 읽고, `AccountEventType`에 컨트롤 이벤트가 없다. 결정: 소비자 스레드가 seq % N == 0에서 직렬화(메모리 복사)만 하고, SPSC 큐로 전용 쓰기 스레드에 넘겨 tmp → fsync → rename, 쓰기 스레드가 volatile durableSeq를 갱신, 소비자가 다음 이벤트에서 그 값을 읽어 두 세대 전을 prune(durable-before-prune). 기각: 호스트 스레드 락(single-writer 위반, 매 이벤트 락 비용), copy-on-write 맵(계좌마다 참조 교체가 핫패스에). 전제 유닛: fill 이벤트에 수신 위치(`image.position()`, 링 슬롯 필드, 와이어 변경 없음)를 실어 소비자가 마지막 적용 fill 위치를 기록해야 스냅샷 헤더의 fillConsumedPosition이 정합. 39가 코드 근거 3개를 직접 확인해 이견 없음.
- **무엇을(실제 변경·파일·커밋)**: 코드 변경 없음. `docs/_v2_progress_map.html`(브랜치 스택·토폴로지·남은 항목 표), `docs/_v2_remaining_work_design.html`(묶음별 유닛·RED 테스트·결정 필요 항목 ⑩). Jack 결정 대기 항목: tradeId 세대 자료구조 안 A(세대별 Set)/B(단일 LinkedHashMap), N 임시값, 주문 생애주기 출구 안 A(리스너 확장)/B(별도 인터페이스), fork2 세부 5개(P·맵 전달·standby tailing (a) live replay/(b) replicate·fencing epoch·standby 배정), 부하 스크립트 커밋 위치.
- **결과·수치**: 남은 유닛 16~21개, 지난 9일 속도(코드 커밋 84개, 하루 유닛 4~5개)를 대입하면 4~5일. 실측 아님. fork2가 가장 불확실.

### 이력서 제출 트랙 "길 C" — 수치 확보 후 제출, 나머지는 제출 뒤 계속

- **context(무슨 상황)**: Jack이 "구현만 빨리 하고 이력서에 첨부하면 어떠냐"고 물었다. 이력서에 첨부되는 건 레포 링크 하나이고 심사자는 README와 폴더 구조를 본다. README는 v2를 한 줄도 안 다루고(오늘 확인) main에는 v2 후반 35커밋이 없다. 그 상태의 링크는 v1 Spring 프로젝트에 이름 모를 모듈이 붙은 것으로 보인다.
- **왜(문제·동기)**: v2의 서사는 "락 기반 v1이 속도 천장 → single-writer + Aeron v2가 정합성을 유지하며 속도까지"인데, 속도 수치가 없으면 근거 없는 주장이 된다. 반면 fork2·주기 스냅샷은 제출 뒤 레포에 쌓여도 면접 시점에는 있게 된다. 마감이 다음날 오전이라 코드 전부(4~5일)는 불가능하다.
- **어떻게(대안·결정·트레이드오프)**: 세 길. A 다 끝내고 제출(약 6일, 가장 늦음). B 지금 제출·계속 구현(1일, 속도 수치 없음 → 서사 근거 공백). C 수치만 먼저(내구성 최소 → C7 → 최소 문서 → 제출 → 나머지). Jack이 C를 골랐다. 마감에 맞춰 C를 더 잘랐다. tradeId 상한은 k6 3000요청 규모면 집합이 수천이라 OOM과 무관해 제출 전 불필요. 2샤드 기울기는 api가 endpoint 하나로만 보내서(`AccountOrderPublishConfig.java:52-53`) 불가. 그래서 측정 = v1 vs v2(1샤드) × 단일 계좌(HOT=1) vs 50계좌(HOT=0), 매칭 미발생, 3-JVM UDP. 이 넷이 "락 없는 v2가 핫스팟에서도 처리량을 유지하나"를 답한다. v1 기준선은 2026-09-04 k6 실측(접수 479 req/s 50계좌 / 649 req/s 단일 계좌, p99 1,465 / 452 ms, 주문 유실 11 / 180건)이 있고, 같은 밤 같은 머신에서 v1도 다시 돌린다. 최소 문서 = README v2 절 + main 병합(PR 6개) + 이력서 한 줄 숫자 + ADR 4개(020 전송 반전·021 계좌 영속·031 샤딩·033 하이브리드 복원). 블로그·나머지 ADR 정식화는 제출 뒤. 수치의 이름은 "v2 접수 경로, 1샤드, 2026-09-16"이고 README와 리포트에 범위를 그대로 적는다. 범위를 숨기지 않으면 미완성 상태의 측정도 근거로 성립한다.
- **무엇을(실제 변경·파일·커밋)**: 세션 배치와 worktree 분리. 한 레포를 세션 넷이 같은 작업 디렉터리에서 쓰면 브랜치 switch가 서로를 깨뜨리므로 `git worktree`로 폴더를 나눴다. 원본(`fix/v2-resource-management`, ec: 자원 관리 4건) / `../stock-trading-engine-c7`(`feat/c7-load-harness`, dc: 기동 스크립트·MetricsAccountResultListener·k6 buy-v2.js·50계좌 시드·측정·리포트) / `../stock-trading-engine-docs`(`docs/v2-resume-minimum`, 2b: README·ADR·대비 문서·PR) / `../stock-trading-engine-durability`(`fix/account-tradeid-snapshot-bound`, a4: 묶음 1). 세 브랜치가 만지는 파일이 겹치지 않아 충돌 없음. ec ④(`AccountSnapshotLifecycle` AtomicBoolean)와 a4의 1-3만 같은 파일이라 ④ 커밋 뒤 착수. 병합 순서: 기존 스택 6개 → resource-management → c7-load-harness → docs(해시·수치가 앞 둘을 참조하므로 마지막). 39가 문서 4종을 사실 검증(해시·태그·시드·JMH·v1 수치 전부 원천과 대조)하고 수정 3건(미존재 ADR 번호 참조 → decision_records 경로 표기, 커밋 제외 파일 링크 → 수치 인라인, JMH 실측 환경 표기)을 냈고 반영했다.
- **결과·수치**: 제출용 v2 수치는 2026-09-16 측정 후 삽입(미측정). 문서 4종은 리뷰 통과, 커밋은 Jack 승인 대기.

### fork2의 이력서 가치 판정 정정 — "한 줄 가치"에서 "데모가 있으면 C7 수치와 같은 급"으로

- **context(무슨 상황)**: 남은 묶음의 이력서 가치를 매기면서 fork2(HA·리밸런싱)를 "이력서 한 줄 이상 가치가 없다"고 적었다. Jack이 "왜?"라고 물었다.
- **왜(문제·동기)**: 근거 없이 판정했다. 같은 답변에서 면접관이 찌를 약점으로 "프로세스 하나 죽으면?"을 적어 놓고, 그 질문의 답인 fork2를 낮게 매긴 것이라 앞뒤가 안 맞았다.
- **어떻게(대안·결정·트레이드오프)**: 상태를 든 프로세스(인메모리 잔고)의 소유권을 안전하게 넘기는 문제는 토이 프로젝트에 거의 없는 재료다. single-writer를 지키며 페일오버할 때 옛 주인이 되살아나 두 번 반영하는 것(split-brain)을 fencing으로 막고, 새 코디네이터 없이 Kafka 컨슈머 그룹으로 풀며, Kafka Streams standby replica와 같은 패턴이라는 근거가 있다. 가치가 나뉘는 조건은 데모 유무다. 로컬에서 계좌 프로세스 둘을 띄우고 주문 중에 하나를 kill해 standby가 이어받고 잔고가 두 번 반영되지 않았음을 테스트로 보이면 C7 수치와 같은 급이 된다. 데모 없이 decision record만 남으면 그때가 "한 줄"이다.
- **무엇을(실제 변경·파일·커밋)**: 정정을 `~/.claude/rules/jack-repeated-mistakes.md`에 P4+P6 재발로 기록. Jack이 fork2를 v2 완료 범위에 포함하기로 결정.
- **결과·수치**: 없음(판정 정정).

## 블로그 네타

### "다 만들었는데 이력서에 쓸 게 없다 — 측정 없는 아키텍처 서사의 구멍"
- **훅·핵심 주장**: 코드 커밋 84개, 모듈 16개, 왕복 경로 완성. 그런데 링크 하나로 심사자에게 보이는 건 README와 숫자 한 줄이다. "속도 때문에 다시 만들었다"는 서사는 속도 수치가 없으면 주장에 그친다.
- **context**: v2 완료 범위를 정하고 이력서 제출 마감이 다음날 오전으로 잡힌 밤. 코드 전부(4~5일)와 제출 사이에서 무엇을 먼저 할지.
- **어떻게(서사·근거)**: 세 길(다 끝내고 / 지금 제출 / 수치만 먼저)의 대가를 놓고 C를 고른 과정. "측정 대상은 완성된 v2가 아니라 지금 코드의 접수 경로"라는 재정의 — v1 리포트도 같은 경로만 쟀다. 못 재는 것(2샤드 기울기·스냅샷 비용·standby 비용)을 이름에 박아 "v2 접수 경로, 1샤드, 2026-09-16"으로 부르기. 범위를 숨기지 않으면 미완성 측정도 근거가 된다.
- **재료(커밋·도식·수치)**: `docs/_v2_progress_map.html`, `docs/_v2_remaining_work_design.html`, v1 k6 실측(479/649 req/s), `4905c7b` 3-JVM 왕복.

### "세션 넷이 한 레포를 — git worktree로 브랜치 충돌 없이 병렬 작업"
- **훅·핵심 주장**: 여러 세션이 같은 작업 디렉터리에서 브랜치를 switch하면 서로의 체크아웃을 깨뜨린다. 파일이 겹치지 않는 작업을 worktree로 폴더째 나누면 브랜치 셋이 형제로 자라고 병합 순서만 정하면 된다.
- **context**: 제출 트랙에서 ec(자원 관리)·dc(부하 하네스)·2b(문서)·a4(내구성)가 같은 밤에 같은 레포를 만짐. dc가 잠깐 공유 디렉터리를 switch했다가 되돌린 사고가 계기.
- **어떻게(서사·근거)**: 브랜치별 파일 소유 표, 유일한 겹침(`AccountSnapshotLifecycle`)을 순서로 푼 것, 병합 순서(스택 6 → 형제 3, 문서가 마지막인 이유 = 해시·수치 참조).
- **재료(커밋·도식·수치)**: `git worktree list` 셋, 브랜치 소유 표(설계 문서 ①).

### "근거 없는 가치 판정 — 내가 적은 약점의 답을 낮게 매긴 날"
- **훅·핵심 주장**: "이력서 한 줄 가치"라는 등급을 근거 없이 매겼다. 같은 답변의 약점 목록이 그 판정을 반박하고 있었다.
- **context**: fork2 가치 판정과 정정.
- **어떻게(서사·근거)**: 판정에 조건(데모 유무)을 붙이면 등급이 바뀌는 것. 가치·우선순위 판정에도 "무엇을 닫는가, 보여줄 수 있는가"라는 근거가 필요하다는 규칙.
- **재료(커밋·도식·수치)**: `jack-repeated-mistakes.md` P4+P6 항목, 설계 문서 ⑦ 3-5 kill 데모 스펙.
