# 계좌 샤딩과 조정 — 상황 가정에서 결정을 끌어낸다 (고정 슬롯 + 정적 라우팅, 무중단은 설계만)

> 설계 단계 기록(미구현). C5 다중 프로세스 샤딩 착수 전 근거를 못 박아 삽질을 막는다.
> 앞선 결정 위에 선다: 전송 반전(ADR-020, `transport-inversion.md`) · 호스트 프레임워크(ADR-018) · durability(ADR-019).
> 도식: `docs/_sharding_coordination_plan.html`(평면 분리) · `docs/_coordinator_options.html`(코디네이터 4안) · `docs/_ondemand_handoff.html`(무중단 교체 절차).

## ADR 네타

### ADR-031 계좌 샤딩·조정 — 상황 가정 우선, 고정 슬롯 + 정적 라우팅, 무중단·코디네이터는 설계만

- **context(무슨 상황)**: v2 계좌 워커는 accountId로 소유를 나눠 여러 프로세스가 각자 맡는다(샤딩). 한 계좌는 한 프로세스만 만져야(single-writer) 정합성이 산다. "슬롯(계좌 묶음) → 어느 프로세스가 주인"이라는 라우팅 지도를 sender가 봐야 주문을 보낸다. 프로세스가 늘거나 죽으면 지도가 바뀌고 인메모리 상태를 옮겨야 한다(리샤딩). "이 지도를 누가·어떻게 관리하나"가 조정 문제다.

- **★ 상황 가정 (이 결정의 앵커 — 여기서 모든 게 따라나온다)**:
  - **종목 수**: 한정(수천 규모). 상장/상폐는 드물고 통제된 이벤트.
  - **계좌 수**: 한정·완만한 증가, 폭증 없음 → 알려진 수로 샤딩을 미리 프로비저닝한다.
  - **부하**: 장중 피크(개장)는 예측 가능·반복적 → 피크 기준 정적 프로비저닝. 모르는 부하에 대비한 오토스케일은 불필요.
  - **배포·용량 변경**: 평소 장 마감 후 통제된 창에서 한다. 장중 무중단은 예외적 상황.
  - **목적**: 거래 엔진 이해 — 1차 정합성·신뢰성, 2차 속도. 확장성은 "검증(C7)" 대상이지 상시 탄력 운영 대상이 아니다.

- **왜(문제·동기)**: 판단 기준은 "어떤 기술이 재밌나/최신인가"가 아니라 "위 상황 가정에서 어떤 선택이 최선이고 무엇을 얻고 무엇을 버리는가"다(Jack, 2026-09-14). "확장성 대비"라는 명분으로 코디네이터·무중단·오토스케일을 미리 다 까는 건, 검증도 안 된 가정 위에 복잡도만 쌓는 over-engineering이다.

- **어떻게(결정)**:

  1. **샤딩 스킴 = 고정 슬롯.** `hash(accountId) % P`로 P개 고정 슬롯에 계좌를 넣고, 프로세스는 슬롯의 부분집합을 소유. P는 프로세스 수가 아니라 큰 고정값(예: 256). `%(프로세스 수)`는 스케일 시 전 계좌 재배치라 기각. 일관해시 링은 복잡도만 오르고 실효 없어 보류. 근거 — Kafka 파티션, Redis Cluster의 16384 고정 해시 슬롯이 같은 방식.

  2. **분배 = 정적 라우팅 테이블 (본선).** 계좌 워커는 폭증 안 하니 알려진 수로 고정 프로비저닝한다. 그럼 남는 건 "sender가 accountId → 슬롯 → 워커로 라우팅"뿐이고, 이건 동적 코디네이터가 아니라 사실상 정적 config다. 체결의 fan-out(매수·매도 두 워커로)도 같은 테이블을 재사용한다. 데이터(주문·체결)는 Aeron, 이 지도는 제어 평면(가끔·통제된 갱신).

  3. **페일오버 = 안정 신원 재시작 + replay (구현).** StatefulSet 안정 신원 + PV + 저널 replay면, `pod-2` 크래시 → K8s가 같은 `pod-2`로 재시작 → PV 붙여 replay → 자기 슬롯 재개. 라우팅 테이블이 안 바뀐다(슬롯→pod-2 그대로). sender는 pod-2 복귀까지 잠깐 대기. 저널·스냅샷(ADR-019)이 이미 있어 대부분 갖춰짐. survivor-takeover(다른 pod가 즉시 인수, 복구 더 빠름)는 선택적 뒤 최적화.

  4. **리밸런싱은 필요하다 — 단 통제·저빈도.** 유니버스가 한정돼도 리샤딩은 필요하다. 이유는 부하 폭증이 아니라 ① 페일오버 ② 확장성 검증(C7: 프로세스 늘리면 처리량 오르나) ③ 상장/상폐·계좌 증가(드문 통제된 변경)다. **C7용 통제된 리샤딩(스냅샷+저널 재사용 + 라우팅 플립)은 구현한다** — 상태 이동하며 정합성 유지되나 + 처리량 오르나가 학습 핵심.

  5. **무중단 배포/스케일 = 온디맨드 핸드오프 (설계만).** 평소엔 장 마감 후 배포(정적으로 충분, 무중단을 타이밍으로 달성). "장중에 꼭 해야 할 때"만 5단계 절차 — 새 pod 예열(replay) → 원 pod 드레인 → 꼬리 catch-up → 라우팅 플립 → 재개. single-writer 안전을 위해 찰나의 pause(대개 1초 미만)를 두므로 "무중단에 근접"이지 완전 0은 아니다. 새로 짤 건 라우팅 플립 한 곳뿐(replay는 ADR-019 재사용). 지금은 구현 안 하고 절차로 문서화만(`docs/_ondemand_handoff.html`).

  6. **상시 자동 코디네이터 = 안 짓는다 (후보로만).** Kafka 컨슈머 그룹 재사용 / etcd·ZK / 가십+일관해시는 완전 자동 온라인 탄력이 목표가 될 때만 등판. 상황 가정이 바뀌면 그때 적합성으로 고른다. (주의: "Kafka 재사용"은 KRaft 직접이 아니라 컨슈머 그룹 프로토콜을 쓰는 것 — KRaft는 Kafka 내부 전용.) 4안 비교 `docs/_coordinator_options.html`.

  7. **stockCode 축(매칭)도 같은 논리.** 종목 한정·상장/상폐 드묾. 단 핫 종목은 그 한 종목의 호가창을 못 쪼갠다(LMAX single-writer) → 부하 분산은 "종목 통째를 덜 바쁜 프로세스로 이동". 역시 통제·저빈도.

- **원칙(못 박음)**: 상황 가정이 앵커다. 거기서 결정이 따라나온다. "확장성 대비"를 명분으로 검증 안 된 가정 위에 코디네이터·무중단·오토스케일을 미리 도입하지 않는다(= 주니어 over-engineering). 필요해지는 순간(상황 가정이 바뀔 때)에 딱 필요한 것만 꺼낸다.

- **트레이드오프(버리는 것)**: 정적 라우팅은 장중 무중단 배포/스케일을 못 준다(재배포·리샤딩 시 그 슬롯 잠깐 멈춤). 페일오버도 survivor-takeout 없이는 pod 재시작 동안(수 초) 그 계좌 불가용. 이 대가를 "평소 장 마감 후 작업 + 예외 시 온디맨드 핸드오프"로 수용한다.

- **정정 이력(이 세션에서 내가 과하게 잡았다가 좁힘)**: 처음엔 "온라인 탄력성이 정직한 목표"라 결론냈으나 — Jack이 "account 수는 알고 있고 부하 폭증은 주문 rate지 계좌 수가 아니다"로 잡음 → 장중 무중단 오토스케일은 우리(및 실제 거래 엔진)에 안 맞음을 확인. 결론을 "페일오버 + 통제된 리샤딩은 구현 / 무중단·상시 코디네이터는 설계만"으로 좁혔다.

- **미결(재샤딩 단위 착수 때)**: 슬롯 수 P, 라우팅 테이블 갱신 채널(config reload vs compacted 토픽), 통제된 리샤딩의 드레인·플립 구현 상세.

## 블로그 네타

### "확장성 대비라는 미명 — 상황 가정에서 설계가 나온다"
- **훅·핵심 주장**: "나중에 커질 수 있으니 코디네이터·무중단·오토스케일을 미리 깔자"는 검증 안 된 가정 위에 복잡도만 쌓는 주니어 over-engineering이다. 설계는 상황 가정에서 따라나와야 한다.
- **context**: v2 계좌 샤딩의 조정 방식을 정하며 코디네이터(Kafka그룹/etcd/가십)까지 갔다가, "우리 상황에서 뭐가 실제로 필요한가"로 되돌아와 정적 라우팅으로 좁힌 과정.
- **어떻게(서사·근거)**: 상황 가정(종목·계좌 한정, 피크 예측 가능, 목적=엔진 이해) → 결정(고정 슬롯+정적 라우팅, 페일오버·통제 리샤딩만 구현, 무중단·코디네이터는 설계만). 내가 "온라인 탄력성이 목표"라 과하게 잡았다가 Jack이 "부하 폭증은 계좌 수가 아니라 주문 rate"로 잡아 좁힌 정정 서사(정직한 실패).
- **재료**: 도식 3종(`_sharding_coordination_plan`·`_coordinator_options`·`_ondemand_handoff`).

### "무중단은 코어 핫스왑이 아니라 타이밍이다 + 리밸런싱이 필요한 진짜 이유"
- **훅·핵심 주장**: 거래 엔진의 "무중단 배포"는 코어를 핫스왑하게 만드는 게 아니라 장 마감 후에 하는 것으로 달성한다. 그리고 리밸런싱이 필요한 이유는 부하 폭증이 아니라 페일오버·배포·상장폐지다.
- **context**: 장중 무중단이 요구사항인지 따지다, 실제 필요 트리거를 셋(페일오버·확장성 검증·상장폐지)으로 좁힘.
- **어떻게(서사·근거)**: single-writer라 리밸런스 하나 = 상태 이동 하나(비쌈) → 불필요한 리밸런스(배포 churn·flapping)를 줄이는 게 설계 포인트(정적 멤버십·sticky·standby). 무중단이 진짜 필요할 때만 온디맨드 핸드오프(예열→드레인→catch-up→플립→재개), single-writer 안전 위해 찰나 pause.
- **재료**: `docs/_ondemand_handoff.html` 5단계, ADR-019 저널·스냅샷 재사용.
