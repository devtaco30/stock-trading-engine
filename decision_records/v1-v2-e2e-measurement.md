# v1/v2 전 과정 측정 설계 — 공정한 끝점과 순서 무관 입력

지금까지의 처리량 측정(dc `_c7_v1_v2_throughput_report.html`)은 "HTTP 요청 → 검증 2개 → 메시지 발행 1회 → 202"까지만 잰다. 발행 뒤의 일 — v1은 Kafka 브로커까지 TCP로 보내 디스크에 쓰고 컨슈머가 poll, v2는 공유 버퍼에서 UDP로 계좌 워커 도달 — 이 전부 측정 밖이다. 두 아키텍처가 "발행 뒤에 남긴 일의 양"이 달라, 일을 뒤로 미룬 쪽(v1)이 앞에서 빨라 보인다. 이 설계는 측정 끝점을 downstream으로 옮기고(축 1), 같은 입력이 실행마다 같은 결과를 내도록 입력을 짜서(축 2) 비교를 공정하게 만든다. 구현·실행은 dc, 설계는 이 문서.

## 축 1 — 측정 끝점을 downstream으로 옮긴다

### 문제
시계를 "버퍼에 넣었다"에서 멈추면 v1이 미뤄둔 일(브로커 durable 쓰기 + 컨슈머 poll + DB 비관적 락 + DB insert)이 측정에서 빠진다. v2가 미룬 일(UDP 홉 + 인메모리 예약)과 비대칭이다.

### 파이프라인 대응 단계 (코드로 확인)
- v1: HTTP → `OrderApiService.placeBuyOrder`가 `OrderRequestEvent`(필드 `requestedAt`=Instant, `Instant.now()`) 발행 → `OrderRequestConsumer`(order-engine, group=order-engine)가 poll → `OrderCommandService.placeBuyOrder`가 잔고 검증(DB `PESSIMISTIC_WRITE`)·주문 저장 → `orders.{stockCode}`로 `OrderPlacedEvent` 발행 → 매칭 컨슈머 → 체결 → 정산.
- v2: HTTP → `AeronAccountOrderSender.send`가 `DecodedAccountOrder`(시각 필드 없음) UDP 발신 → `AccountOrderReceiver` → 계좌 엔진 소비자 스레드가 인메모리 예약 → 매칭 Aeron 발신 → 체결 → 정산.

세 지점이 대응한다: ①주문 접수·예약(v1 placeBuy 반영 후 / v2 계좌 엔진 예약 반영 후) ②체결 ③정산.

### 대안 (끝점 후보)
- **①주문 접수·예약**: 두 아키텍처가 "주문 하나를 받아 잔고를 예약하는" 같은 일을 하는 첫 공통 지점. v1이 미뤄둔 브로커·DB 작업이 정확히 이 구간에 들어간다.
- **②체결**: 매칭까지 포함. 다만 체결은 도착 순서에 따라 상대가 달라져(축 2 문제) 주문 하나에 지연을 귀속시키기 어렵다 — 지연보다 처리량(체결/초)으로 재는 게 맞다.
- **③정산**: T+2 비동기라 주문 접수 지연과 시간 스케일이 다르고, 이 측정의 관심(발행 뒤 접수까지의 숨은 비용)과 안 맞다.

### 트레이드오프 — 주 지표를 무엇으로
- **①접수 지연은 도착 순서와 무관**하다. 주문 하나의 예약 경로 길이는 다른 주문의 도착 순서에 안 좛인다(단, 잔고 고갈로 인한 거부가 없어야 경로가 균일 — 시드로 넉넉히 보장, 축 2 참조). 그래서 축 2의 비결정성이 이 지표를 오염시키지 않는다.
- **②체결 처리량은 도착 순서에 좌우**된다(체결 상대가 바뀌어 총 체결 건수가 달라짐). 이 지표는 축 2의 순서 무관 입력이 있어야 비교가 성립한다.

### 결정
- **주 지표 = 끝점 ①(주문 접수·예약)에서의 지연 분포 p50/p95/p99/max.** 지금 측정의 불공정이 "끝점을 앞에서 잘랐다"는 것이므로, 끝점을 접수·예약으로 옮겨 백분위를 직접 보고하는 게 "어느 쪽이 주문을 더 빨리 접수·예약하나"에 정면으로 답한다. 헤드라인은 p99(트레이딩은 꼬리 지연이 중요).
- **보조 지표 = 처리량 두 가지**: (a) 접수 처리량(초당 예약된 주문 수, 끝점 ①) — 순서 무관 입력 불필요. (b) 체결 처리량(초당 체결 수, 끝점 ②) — 순서 무관 입력 필요(축 2).
- **측정 기법**: 양쪽 downstream 소비자(v1 `OrderRequestConsumer`, v2 계좌 엔진 소비자)에 측정 훅을 두되 **측정 플래그/프로파일(`-Dmeasure.latency=true` 또는 프로파일 `measure`)로 게이트**하고 기본 off — 정상 실행 핫패스에 영향 없게 한다. 훅은 `now - publishedAt`을 계산해 소비자 스레드별 HdrHistogram에 record(핫패스 비용 ~ns), 테스트 종료 시 병합해 p50/95/99/max·count를 덤프한다.
- **시각 값 = wall-clock epochNanos(long).** 프로젝트 규칙(이벤트·저장 시간은 절대시각 long, LocalDate/zone 금지)을 지키되 **밀리초가 아니라 나노초 해상도**로 간다. 이유: v2 접수 지연은 UDP 로컬 + 인메모리라 sub-ms(수백 µs)일 수 있어 1ms 해상도면 분포가 뭉개진다. 단일 머신이라 두 프로세스의 wall-clock(`Instant.now()`, 에폭 기반)은 서로 비교 가능하고 최신 JVM에서 µs 이하 해상도를 준다 — nanoTime은 JVM 상대값이라 프로세스 간 비교 불가라 못 쓴다. epochNanos도 절대 UTC 기반 long이라 zone 드리프트가 없어 규칙의 취지(LocalDate 금지)를 충족한다.
- **필드**: v1은 `requestedAt`(Instant)에서 `getEpochSecond()*1_000_000_000 + getNano()`로 epochNanos를 읽는다(이벤트 스키마 변경 불필요). v2는 `DecodedAccountOrder`에 `long publishedAtEpochNanos`를 추가하고 `AccountOrderCodec`(와이어)·인코딩/디코딩에 반영한다. 발행 직전(HTTP 스레드) 같은 시점에 찍는다.

## 축 2 — 같은 입력이 같은 순서 무관 결과를 내게 한다

### 문제
난수 시드를 고정해 주문 목록을 파일로 미리 만들고 v1·v2에 같은 파일을 먹여도, 가상 사용자 여러 개가 병렬로 쏘면 서버 도착 순서가 실행마다 다르다. 매칭은 도착 순서로 체결 상대가 갈려 v1·v2의 총 체결 건수 자체가 달라진다 → 체결 처리량 비교가 오염된다.

### 대안 (회피 방향)
- **A. 순서 무관 입력(2b 제시)**: 종목마다 같은 가격·같은 수량의 매수·매도를 짝으로 생성. 누가 먼저 오든 각 매수는 같은 가격의 매도와 전량 체결 → 총 체결 건수가 도착 순서와 무관하게 고정. 병렬성(동시 주입)을 그대로 유지한다.
- **B. 단일 스레드 직렬 주입(1 VU)**: 도착 순서 비결정성을 아예 없앤다. 대가 = 동시성·처리량 현실성이 사라져 부하 측정의 의미가 준다(처리량 비교엔 부적합).
- **C. 지연 지표는 원래 순서 무관(축 1)**: 끝점 ① 접수 지연은 체결 결과에 안 좌우된다. 즉 순서 비결정성은 체결 처리량(②)만 오염시키고 접수 지연(주 지표)은 오염 안 시킨다.

### 트레이드오프
- A는 체결 처리량 비교를 성립시키면서 병렬성을 유지한다. 대가 = 입력 생성이 짝 구조에 묶이고, 시드가 넉넉해 거부가 안 나야 한다(거부되면 짝이 깨져 체결 건수가 흔들림).
- B는 확실하지만 부하 측정을 포기한다.
- C는 주 지표(지연)엔 축 2가 애초에 불필요함을 뜻한다 — A는 보조 지표(체결 처리량)에만 필요하다.

### 결정
- **주 지표(접수 지연)엔 고정 시드 입력 파일이면 충분**(같은 주문 집합·같은 requestId, 병렬 주입 허용). 도착 순서 비결정성은 접수 지연에 영향 없다(대안 C).
- **보조 지표(체결 처리량)엔 대안 A(순서 무관 짝 입력)를 쓴다.** 종목마다 (매수 P·수량 Q, 매도 P·수량 Q) 짝을 매수자≠매도자로 생성, 매도자는 그 종목을 보유. 어느 순서로 와도 전량 체결 → 총 체결 = 종목당 짝 수 × 2(양쪽)로 고정.
- **입력 파일 형식**: 결정론 순서열의 주문 목록(side, accountId, stockCode, price, quantity, requestId). requestId도 시드에서 결정론적으로 만들어 양쪽 멱등이 동일하게 동작하게 한다. v1·v2가 같은 파일을 읽는다.
- 대안 B(직렬 주입)는 안 쓴다.

## 규모 — 종목·계좌·주문 수와 시드

### 문제
현재 데모 시드는 계좌 2개(90001 매수·90002 매도)뿐이다. 이 규모로는 (a) v1의 계좌별 직렬화(Kafka accountId 파티셔닝 + DB 비관적 락)와 v2의 accountId 샤딩이 몇 계좌에만 몰려 "아키텍처 처리량"이 아니라 "소수 계좌 경합"을 재게 된다. 규모를 근거와 함께 정한다.

### 결정과 근거
- **종목 30개** (Jack 언급). 근거: 매칭은 종목별 호가창(order book)이라 종목 수가 매칭의 병렬 단위다. 30개면 호가창 하나의 직렬화가 유일 병목이 되지 않고, v2가 stockCode로 매칭을 샤딩할 여지도 준다.
- **계좌 100개**(매수자 50 + 매도자 50). 근거: (a) v1은 Kafka를 accountId로 파티셔닝하고 매수에 계좌 행 비관적 락을 잡는다 — 계좌가 적으면 계좌별 직렬화·락 경합이 처리량을 지배해 아키텍처가 아니라 경합을 측정하게 된다. (b) v2는 accountId로 샤딩한다 — 계좌가 적으면 쓰는 샤드가 적다. 동시 주입 스레드(k6 VU 통상 10~50)보다 넉넉히 많은 100계좌면 계좌당 동시성이 낮아 경합이 지표를 지배하지 않는다. 짝수라 매수자·매도자 균등 분할·짝 생성이 깔끔하다.
- **주문 100,000개**(매수 50k + 매도 50k, 짝). 근거: p99가 안정되려면 측정 셀당 표본이 대략 1만 이상 필요하다(HdrHistogram 백분위 안정성) — 10만이면 p99가 흔들리지 않고, 측정 처리량(직전 dc 기준 초당 수천) 기준 정상상태 구간이 수십 초로 잡혀 실행이 1분 내로 끝난다.
- **시드 데이터**: 입력 파일과 **같은 난수 시드로 함께 생성**한다. 매수자 계좌 잔고 ≥ 그 계좌 매수들의 Σ(price×quantity×marginRate)로 넉넉히(거부 0 보장 — 거부가 나면 접수 경로가 불균일해지고 짝이 깨진다). 매도자 계좌 holdings ≥ 그 계좌·종목 매도들의 Σ(quantity). marginRate는 현재 데모값 0.40 유지. 시드 계좌 목록은 `application-*.yml`의 `seed-accounts`(현재 2개)를 이 100계좌로 교체하는 별도 프로파일로 만든다(운영 데모 시드는 건드리지 않음).

## 결과
- dc 구현 대상 산출물: ①시각 필드 추가(v2 `DecodedAccountOrder.publishedAtEpochNanos` + `AccountOrderCodec`), ②양쪽 소비자에 측정 게이트 훅(HdrHistogram, 플래그 off 기본), ③고정 시드 입력 생성기(순서 무관 짝 + 결정론 requestId)와 100계좌 시드 프로파일, ④종료 시 p50/95/99/max·처리량 덤프.
- 주 지표는 끝점 ①의 접수 지연 p99, 보조는 접수 처리량과 (짝 입력에서의) 체결 처리량.
- 미해결·범위 밖: 끝점 ②(체결)·③(정산)의 지연은 이번 범위 밖(체결은 처리량으로만 잰다). v1 `OrderRequestEvent`의 `requestedAt`은 Instant 그대로 두고 읽을 때 epochNanos로 환산 — 이벤트 스키마 통일(전면 long화)은 별도 트랙.
- 관련: [[account-idempotency-cache-bound]](시간값 epochMillis 규칙의 근거), 그리고 이번에 나노초로 확장한 사유는 위 축 1 결정에 기록. a4의 `AeronAccountOrderSender` 버퍼 할당(ThreadLocal 채택)은 이 측정과 별개 트랙 — 그 결정은 해당 리뷰에 있다.
