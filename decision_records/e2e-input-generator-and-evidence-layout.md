# e2e 측정용 결정론 페어 입력 생성기 + 확정 근거 디렉터리 구조

## ADR 네타

### ADR 후보: 도착 순서와 무관하게 체결 건수가 고정되는 입력을 만든다(결정론 페어)

- **context**: 39 설계(v1-v2-e2e-measurement.md)에 따라 v1·v2 아키텍처를 같은 입력으로 비교해야 했다. 가상 사용자(VU)가 병렬로 주문을 쏘면 서버 도착 순서가 매 회 달라지고, 매칭은 도착 순서에 따라 체결 상대가 달라져 v1·v2의 체결 건수 자체가 달라질 수 있었다.
- **왜**: 체결 건수가 실행마다 달라지면 "같은 조건으로 비교했다"고 말할 수 없다 — 비교가 오염된다.
- **어떻게(대안·결정·트레이드오프)**: 종목마다 같은 가격·같은 수량(quantity=1)의 매수·매도를 정확히 같은 건수만큼 만들면, 어떤 순서로 도착하든 그 종목의 매수·매도가 전량 소진된다(단일 가격대라 우선순위 다툼이 없다). 대안(무작위 가격 분포로 현실적인 호가창 재현)은 이번 목적(순수 접수·처리량 비교)에 불필요한 복잡도라 기각 — 매칭 자체의 현실성은 이 측정 범위 밖이다.
- **무엇을**: `loadtest/generate-e2e-input.py`. 종목 30개(`market/.../quotes.sql`의 실제 previousClose 그대로 사용 — 가격제한폭 ±30% 검증에 안 걸리게), 계좌 100개(매수자 2001~2050·매도자 2051~2100, 기존 HTTP 처리량 테스트의 1001~1050과 안 겹치게), 주문 10만 건(매수 5만+매도 5만). 종목별 매수=매도 건수를 라운드로빈으로 배정. requestId는 파일 내 순번(`e2e-000001`~) 기반이라 결정론적. 파일 순서는 고정 시드(`random.seed(20260916)`)로 섞어 실제 혼재 트래픽처럼 보이되 재현 가능하게 했다.
- **결과·수치**: 재실행 시 바이트 단위로 동일한 출력을 diff로 확인(결정론 검증). 실제 매칭 결과(체결 건수 고정 여부)는 dc의 통합 측정에서 실기동으로 확인됨(상세는 `v1-v2-e2e-measurement.md`).

### ADR 후보: 잔고·보유는 짐작치가 아니라 생성된 주문에서 역산한다

- **context**: 거부(reject) 없는 측정이 되려면 매수자 잔고·매도자 보유가 항상 충분해야 했다. 계좌·종목 배정이 라운드로빈이라 매도자별로 실제 어떤 종목을 몇 건 파는지 손으로 미리 계산하기 어려웠다.
- **왜**: 큰 숫자를 아무렇게나 채워 넣는 것("100억이면 충분하겠지")도 통과는 하지만, "왜 충분한지"를 보여주지 못하고 우연히 부족할 경우를 못 잡는다.
- **어떻게**: 생성기가 주문 리스트를 먼저 전부 만든 뒤, 그 결과를 집계해서(accountId, stockCode)별 실제 필요 수량·금액을 세고, 그 집계값으로 시드를 만든다. 나중에 "재기동 없이 4패스(워밍업1+측정3) 연속 재생"으로 측정 방식이 바뀌면서 필요량이 4배가 됐는데, 이 설계 덕분에 상수(`PASSES = 4`) 하나만 곱하면 됐다 — 재계산 로직을 새로 안 짜도 됐다.
- **무엇을**: `aggregate_buyer_cost`(매수자별 `Σ price×quantity`)·`aggregate_seller_holdings`(계좌·종목별 `Σ quantity`) 두 함수, `PASSES` 배수. v1 SQL(`api/.../e2e-seed.sql`)·v2 YAML(`account-worker/.../application-e2e.yml`) 양쪽에 같은 집계값을 쓴다.
- **결과·수치**: dc의 실측 통합에서 거부율 0% 확인(상세는 dc 쪽 결정 기록).

### ADR 후보: 확정 측정 근거는 파일명 gitignore 예외 목록이 아니라 별도 디렉터리로 분리한다

- **context**: 측정이 끝난 뒤 `docs/_c7_v1_v2_throughput_report.html`이 인용하는 원본 결과 파일(k6 요약·지연 히스토그램·CPU 로그)이 `loadtest/results/`(gitignore 대상)에만 있어 이 머신 밖에서는 근거를 확인할 수 없었다.
- **왜**: 결과 디렉터리에는 확정 측정과 함께 폐기된 초기 시도·중간 덤프가 섞여 있어(같은 세션에서 80개 파일이 나옴, 그중 리포트가 실제로 이름을 지목해 인용하는 건 일부) 전부 커밋할 수도, 아무 기준 없이 고를 수도 없었다.
- **어떻게(대안·결정·트레이드오프 — 이 항목의 핵심)**: ①첫 시도는 `loadtest/.gitignore`에 `results/*`를 막고 확정 파일 57개를 하나씩 `!파일명`으로 예외 처리하는 방식이었다(정확했지만 89줄). ②리뷰(2b)가 이 방식의 문제를 짚었다 — 다음 측정 때 이 목록을 손으로 관리해야 하고, 목록만 봐서는 "왜 이 57개만 예외인지" 알 수 없고, 파일 하나 이름이 바뀌면 조용히 빠진다. ③최종적으로 `loadtest/results/`는 통째로 계속 무시(측정할 때마다 새로 쌓이는 작업 공간)하고, 확정 근거 57개만 `loadtest/evidence/`라는 별도 디렉터리로 옮겨 평범하게 추적하는 방식으로 바꿨다. `evidence/README.md`에 무엇이 어느 측정의 근거인지, 어떻게 재현하는지를 적었다 — "커밋 메시지는 파일을 열어본 사람에게 안 보인다"는 게 이 결정의 근거였다.
- **무엇을**: `git mv loadtest/results/<파일> loadtest/evidence/<파일>` 57개, `loadtest/.gitignore`를 `logs/`·`pids/`·`results/` 세 줄로 원복, `loadtest/evidence/README.md` 신설, 리포트·`decision_records/v1-v2-e2e-measurement.md`의 인용 경로를 `loadtest/evidence/`로 갱신. 어떤 파일을 넣고 뺄지는 dc가 타임스탬프로 80개를 재구성해 확정/폐기를 가려줬다(리포트에 이름이 없어도 실제로 인용되는 근거인 것 13개, 리포트 어디에도 안 나오는 폐기 잔재 22개는 로컬 `results/`에만 남김).
- **결과·수치**: 최종 커밋 59개 파일(확정 근거 57 + README + gitignore), 전부 diff로 원본과 바이트 동일 확인(값을 다시 계산하지 않았다).

## 블로그 네타

### "예외 목록이 아니라 서랍을 따로 만든 이유"

- **훅·핵심 주장**: `.gitignore`에 예외 규칙을 하나씩 추가하는 건 "지금은" 정확하지만 "다음에도" 정확할 거란 보장이 없다 — 규칙이 아니라 장소를 분리하면 그 문제가 통째로 사라진다.
- **context**: 부하 측정이 끝나고 결과 파일들을 커밋하려는데, 같은 디렉터리에 확정 데이터와 버려야 할 중간 시도가 뒤섞여 있었다.
- **어떻게(서사·근거)**: ①처음엔 "지울 파일과 남길 파일"을 구분해서 남길 파일 이름을 `.gitignore`에 하나씩 적었다. 정확했다 — 딱 그 순간까지는. ②동료의 지적: 다음에 측정을 다시 돌리면 새 파일이 생기고, 그 파일이 확정본인지는 또 사람이 판단해서 목록에 손으로 추가해야 한다. 이름이 바뀌면 아무도 모르게 목록에서 빠진다. ③해법은 규칙을 정교하게 다듬는 게 아니라 규칙 자체를 없애는 것이었다 — "이 폴더는 작업 공간, 저 폴더는 확정본"으로 장소를 나누면, 확정본 폴더에 뭔가 있다는 사실 자체가 "이건 의도적으로 옮겨진 것"이라는 뜻이 된다.
- **재료(커밋·도식·수치)**: `.gitignore` 3줄로 축소(89줄→3줄), `loadtest/evidence/` 신설 + README, 커밋 `7a482e0`→`06b77e9`.
