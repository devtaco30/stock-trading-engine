# 매칭 shard N개 시험을 위한 하네스와 종목 균등 선택

## ADR 네타
### 종목을 shard마다 같은 수로 고르는 규칙
- **context(무슨 상황)**: 매칭 shard를 1·2·4·8개로 늘려 접수 속도를 비교하려 한다. 종목 30개를 고르는 기존 방식(`codes-many 64 0 30`)은 000001~000030이고 종목 slot이 겹친다(slot 27이 3개, 21·42·58이 각 2개). shard별 종목 수는 보장되지 않는다.
- **왜(문제·동기)**: shard마다 호가창 크기와 주문 수가 다르면 shard 수에 따른 속도 차이와 종목 분포 차이를 구분할 수 없다.
- **어떻게(대안·결정·트레이드오프)**: 기동 뒤 slot→shard 표를 읽어 shard별 할당량(몫 + 나머지는 정렬 앞쪽 주소부터)대로 %06d 코드를 오름차순으로 고르고 slot은 겹치지 않게 했다. 30은 4·8로 안 나뉘므로 8·8·7·7, 4×6+3×2가 되어 호가 수 차이가 최대 약 14%·33%다. 종목 수를 8의 배수(32)로 바꾸면 해결되지만 mix.sh의 C·RATE 검사 규칙이 같이 바뀐다 — 결정 대기.
- **무엇을(실제 변경·파일·커밋)**: loadtest/s0b_multi/stock_select.py + 시험 23개(f250b3d). slot 계산은 StockSlotHasher를 Python으로 옮겼고 ec의 slots.txt(Java 계산) 30개와 일치함을 시험으로 확인.
- **결과·수치**: 시험 23개 통과. 실제 기동에서의 효과는 미측정.

### 하네스 공통 블록을 lib.sh로 모으는 변경안(패치로만)
- **context**: ec의 run.sh·mix.sh·ladder.sh가 같은 기동 블록(Kafka 컨테이너, jar, 매칭 기동)을 복사해 쓴다. ec가 mix.sh를 쓰는 중이라 직접 수정할 수 없었다.
- **왜**: 매칭 N개 기동과 배정 완료 대기를 세 곳에 따로 넣으면 어긋난다.
- **어떻게**: lib.sh 한 곳에 넣고 세 스크립트가 부르게 한 변경을 패치 3개로 남겼다. 외부 호출(docker, java, gradle)을 가짜로 바꿔 Docker 없이 시험했다. N=1이고 BALANCED_STOCKS가 없으면 매칭 java 인자가 기존과 글자 그대로 같게 했다. 포트는 입구 20020+i, 제어 8100+i, 단 계좌 워커 2개일 때 8100·8101과 겹쳐 8200+i로 비킨다.
- **무엇을**: patches/0001~0003, README.md의 ec와 맞출 점 10개(eb68820).
- **결과·수치**: lib.sh 시험 51개 통과, 패치는 ec 444e248에 `git apply --check`와 임시 복사본 적용으로 확인. 실제 docker·java 기동은 미확인.

## 블로그 네타
### "서버를 늘리는 시험에서 입력을 같게 맞추는 법"
- **훅·핵심 주장**: shard 수를 바꿔 비교할 때 종목 분포가 다르면 비교가 성립하지 않는다. 종목 코드를 해시한 slot의 소유 shard를 보고 고른다.
- **context**: 종목 코드는 해시로 slot에 배정되고 slot은 Kafka 조정 토픽으로 shard에 배정된다. 코드 번호 순서로 고르면 shard마다 수가 다르다.
- **어떻게(서사·근거)**: 배정 표를 읽는 도구, 할당량 규칙, 30이 4·8로 안 나뉘는 문제, 완전히 같게 하려면 32로 바꾸고 그 대가로 검사 규칙이 바뀌는 점.
- **재료(커밋·도식·수치)**: f250b3d, eb68820. 같은 기계에서 매칭 4·8개를 부하 없이 띄운 측정(JVM당 rss 약 290MB, idle CPU 합 4개 약 45%, 8개 약 131%, 기계 unused 메모리 211MB까지). 부하 때 수치는 미측정.
