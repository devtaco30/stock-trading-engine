# 조정 세션 — 구멍을 하나씩 따라가다 전수 점검으로 바꾼 날, 그리고 어디서 멈출지 정한 날

> 이 세션은 코드를 쓰지 않았다. 세션 넷(39 설계·리뷰 / a4·ec 구현 / dc 측정·구현)에 작업을 나누고, 설계를 잡아 넘기고, 커밋을 승인하고, 포트와 디스크 같은 공유 자원을 조정했다. 남길 값어치가 있는 것은 **작업 목록 자체가 어떻게 바뀌었는가**다.

## ADR 네타

### 하나를 따라가면 하나가 더 나온다 — 질문 응답을 멈추고 전수 점검으로 바꾼 지점

- **context(무슨 상황)**: 남은 작업 문서(`docs/_v2_remaining_work_design.html`)는 2026-09-15에 "남은 다섯 묶음"으로 쓰였다. 그 문서를 갱신하며 Jack이 항목을 하나씩 짚었고, 짚을 때마다 코드를 열어 확인했다. 그 과정에서 문서에 없던 구멍이 연달아 나왔다 — 계좌가 매칭으로 보내다 주문을 버리는 것(I2), 매칭에 복구 경로가 없는 것(I3), 계좌가 안 살아나면 매칭이 통째로 멈추는 것(I4), Archive 기록이 디스크에서 줄지 않는 것(I5). Jack이 "이슈 하나 파니까 다른 게 나오고 그거 파니까 또 나온다"고 했다.
- **왜(문제·동기)**: 질문에 답하는 방식으로는 끝이 안 난다. 묻는 자리만 보고 그 옆은 안 보기 때문이다. 그리고 그렇게 나온 목록은 "이게 전부인가"를 아무도 모른다.
- **어떻게(대안·결정·트레이드오프)**: 파이프라인 전 구간을 한 번에 훑었다 — 전송 지점 여섯 곳(각각의 실패 처리 방식), 복구 경로 네 곳(무엇을 읽어 되살리나), 메모리·디스크가 상한 없이 늘 수 있는 자리 전부. 그 결과를 이슈 아홉 개(I1~I9)로 정리하고, 각 이슈에 **"왜 지금은 안 터지나"**를 같이 적었다(조건이 바뀌면 터진다는 뜻이다 — 예: 매칭이 하나뿐이면 I1이 안 드러난다). 그리고 이슈를 하나씩 고르는 대신 **같은 코드·같은 데이터를 만지는 것끼리 여섯 트랙으로 묶었다**. 따로 하면 같은 자리를 두 번 만지기 때문이다(실제로 I1과 I5는 "recording마다 어디까지 처리했나"라는 같은 값을 쓴다).
- **무엇을(실제 변경·파일·커밋)**: 문서를 "남은 다섯 묶음의 설계"에서 "v2에 남은 이슈 — 전수 점검"으로 다시 썼다. 파이프라인 구간별 상태 도식, 이슈 표(근거 코드·터지는 조건·크기), 트랙별 묶음과 "지금 작업 중인 것과 파일이 겹치나" 줄을 넣었다. 코드 변경 없음.
- **결과·수치**: 전수 점검 이후 새로 나온 것은 둘뿐이다(I10·I11). 그 전까지는 질문마다 나왔다. 점검이 대부분을 잡았다는 근거로 본다.

### 목록에 끝을 주는 법 — "고칠 수 있는 것 전부"에서 "이 프로젝트가 필요한 것"으로

- **context(무슨 상황)**: 이슈를 닫는 동안 새 이슈가 늘었다. 오늘 닫은 것 둘(I1·I6), 늘어난 것 둘(I10·I11). 순증 0인데도 Jack이 "손댈수록 커진다"고 했다.
- **왜(문제·동기)**: 목록이 "고칠 수 있는 것 전부"이면 끝이 안 난다. 실제로 늘어난 둘의 성격도 달랐다 — I10(테스트가 임시 폴더를 안 치움)은 원래 있던 문제가 디스크가 차서 드러난 것이고, **I11(발행자별 위치 목록이 늘기만 함)은 I1을 고치면서 우리가 만든 것**이다. 고치면 새로 생길 수 있다는 것까지 감안하면 기준 없이는 수렴하지 않는다.
- **어떻게(대안·결정·트레이드오프)**: 이 프로젝트의 목적(학습·이력서)을 기준으로 셋으로 나눴다. ①**돈이 틀어지는 것** — I2(주문을 버려 예약만 묶임)·I4(계좌 하나 죽으면 매칭 전체 정지)·I5(진행 중) ②**보여줄 것** — I8 첫 단계(프로세스를 늘리면 처리량이 오르는가, 아직 근거 없는 주장)와 GitHub 반영 ③**나머지** — I7(조회 기능)·I9·I10·I11(운영 위생). Jack이 ①+②까지로 선을 그었고 **I7을 명시적으로 버렸다.** ③은 목록에만 남긴다 — 면접에서 물으면 "알고 있고 목록에 있다"가 답이 된다.
- **무엇을(실제 변경·파일·커밋)**: 문서 ⓪-b 맨 앞에 범위 결정 배너를 넣었다. I7을 버려서 따라오는 결과도 같이 적었다 — **유실 후보4(보내다 실패하면 거절)는 알릴 통로가 없어 고를 수 없는 선택지가 된다.**
- **결과·수치**: 남은 범위 넷. 버린 것 넷.

### 세 이슈를 하나로 묶은 전제가 절반만 맞았다 — 내구성 축과 가용성 축

- **context(무슨 상황)**: I2·I3·I4를 "원본을 누가 갖고 있다가 다시 주느냐" 하나로 묶어 ec에 설계를 맡겼다.
- **왜(문제·동기)**: ec가 코드를 열어 대조하니 전제가 절반만 맞았다. 계좌→매칭(I2)은 **이미 전용 스레드로 분리돼 있어** 재시도로 바꿔도 계좌 엔진이 안 멈춘다. 매칭→계좌(I4)는 매칭의 유일한 소비자 스레드가 직접 재시도 루프를 돈다. 같은 "정책 차이"로 보였지만 **구조가 다르다.**
- **어떻게(대안·결정·트레이드오프)**: 두 축으로 나눴다 — ①내구성(메시지를 잃지 않는가) ②가용성(재시도가 파이프라인을 막는가). "원본을 어디 두나" 결정은 ①만 고친다. **네 후보 어느 것으로도 I4는 안 닫힌다.** I4를 닫으려면 매칭에도 계좌처럼 아웃박스+전용 스레드 구조를 넣어야 하고, 그건 별개 작업이다.
- **무엇을(실제 변경·파일·커밋)**: `decision_records/i234-transport-loss-design.md`(ec 작성, 브랜치 `docs/i234-transport-loss-design`, `6c33703`). 후보1(받는 쪽 보관)로 결정하고 계좌 발신 재시도를 같이 붙이기로 했다.
- **결과·수치**: 후보2(보내는 쪽 보관 후 당겨오기)는 **지금 고를 수 없는 것으로 판명**됐다 — Aeron의 해당 기능이 "읽어가기"가 아니라 복제이고, 두 프로세스가 서로 접속하는 배선이 아직 없다(코드 주석이 스스로 나중 단계로 미뤄 놓았다).

### 조정 세션이 실제로 한 일 — 공유 자원과 증명 기준

- **context(무슨 상황)**: 세션 셋이 동시에 돌면서 충돌 지점이 둘 드러났다.
- **왜(문제·동기)**: ①Aeron Archive 제어 포트(8010)를 계좌·매칭이 공유해 통합 테스트를 동시에 못 돌린다 ②디스크가 찼다.
- **어떻게(대안·결정·트레이드오프)**: 포트는 매번 `lsof`로 직접 확인하고 순서를 정해 넘겼다("a4가 먼저 쓴다, dc는 그동안 단위 테스트만"). 디스크는 원인을 추적해 **임시 폴더에 쌓인 Aeron 작업 디렉터리 3,203개(각 46MB)**를 찾았고, Jack 승인을 받아 한 시간 지난 것만 3,798개 지웠다. 그 과정에서 dc가 **Kafka 브로커도 같이 죽어 있었다**는 것을 찾아냈다(저장 공간이 없어 스스로 내려감).
- **무엇을(실제 변경·파일·커밋)**: 코드 변경 없음. 디스크 여유 924Mi → 120Gi(119GB 회수).
- **결과·수치**: 임시 폴더 증가 실측 — 계좌 쪽 전체 회귀 1회당 69개, 매칭 쪽 1회당 17개, 좁힌 테스트 3회에 5개. 이 수치가 I10의 근거다.

### 증명할 수 없는 테스트를 증명 가능하게 — 두 세션이 같은 벽에 부딪힌 것

- **context(무슨 상황)**: a4(매칭 주기 스냅샷)와 dc(디스크 회수)가 각자 마지막 단계에서 같은 성격의 문제를 만났다.
- **왜(문제·동기)**: a4 — 정상 종료 스냅샷이 켜져 있으면 주기 스냅샷을 꺼도 종료 시점이 같은 상태를 한 번 더 찍어버려 **"고치기 전엔 실패한다"를 보일 수가 없다.** dc — Aeron 세그먼트 기본 크기(128MB)로는 테스트 데이터가 세그먼트를 하나도 못 채워서, 회수를 불러도 **지울 게 없어 통과한다.** 둘 다 "통과했지만 아무것도 증명 못 한" 상태가 될 뻔했다.
- **어떻게(대안·결정·트레이드오프)**: 둘 다 **프로덕션에 스위치를 하나 열어 테스트에서만 덮어쓰는** 방식으로 갔다(기본값은 기존 동작이라 운영 무변경). a4는 정상 종료 스냅샷을 끄는 property, dc는 세그먼트 길이 property. 대안(별도 프로세스를 띄워 강제 종료 / 데이터를 대량으로 밀어 넣기)은 전례가 없거나 거짓 통과 위험이 커서 뺐다. **스위치에는 운영에서 켜면/끄면 무엇이 나빠지는지를 javadoc에 적게 했다.**
- **무엇을(실제 변경·파일·커밋)**: a4 — `matching.worker.graceful-snapshot-enabled`(`f8a3d8f`). dc — `account.worker.archive.segment-file-length`(U3 진행 중).
- **결과·수치**: a4의 RED 확인 — 트리거를 빼면 "1만에 도달하지 않음(현재 0)"으로 실패, 되돌리면 통과. dc의 U1 RED — 회수를 안 부르면 파일이 5→9로 쌓이기만 하고, 부르면 9→5로 줄어든다.

### 기다리는 값이 틀렸는데 구현을 의심한다 — 같은 모양이 한 트랙에서 두 번

- **context(무슨 상황)**: dc가 I5(Archive 기록 회수)를 만들며 테스트에서 두 번 막혔다. 둘 다 "진행을 기다리는 코드"가 엉뚱한 값을 보고 있었다.
- **왜(문제·동기)**: ①U2 — 보내는 쪽의 `publication.position()`이 목표에 닿은 걸 "발행 끝"으로 보고 세그먼트 파일 수를 셌다. REMOTE 녹화는 네트워크를 거쳐 비동기로 디스크에 쓰이므로 보내는 쪽 위치와 실제 기록 위치 사이에 시차가 있었고, 테스트가 됐다 안 됐다 했다(기대 8, 실제 9). ②U3 — 같은 requestId를 2만 번 재전송시키고 `AccountState.seq()`가 오르기를 기다렸는데 30초 타임아웃이 났다. 그 값은 **실제로 상태가 바뀔 때만 오르고, 걸러지는 재전송은 저널에 기록돼도 그 경로를 안 탄다.** 처리는 멀쩡히 되고 있었다.
- **어떻게(대안·결정·트레이드오프)**: ①은 `getRecordingPosition`(Archive가 실제로 기록한 위치)을 폴링하도록 고쳤다. ②는 `AccountSnapshotWriter.durableSeq()`(핸들러의 전역 처리 순번이 반영되는 값)를 폴링하도록 고쳤다. ②에서 dc는 먼저 세그먼트·term 크기를 의심해 1MB까지 올려보고 나서야, 로그에 "요청 재전송 무시"가 정확히 2만 번 찍힌 걸 보고 **구현이 아니라 관찰 신호가 틀렸다**는 걸 확인했다.
- **무엇을(실제 변경·파일·커밋)**: 테스트 폴링 대상 변경. `AccountArchivePurgeRecoveryIntegrationTest`(신규), U2 신규 테스트.
- **결과·수치**: 둘 다 고친 뒤 연속 통과. **틀린 데를 파느라 쓴 시간이 이 함정의 크기다** — 세그먼트 크기를 의심해 값을 바꿔가며 재현을 시도한 구간이 그것이다.

### 조정 세션이 비워지면 다음 세션이 감을 못 잡는다 — 상태 말고 지침을 남긴다

- **context(무슨 상황)**: 이전에 조정 창을 비운 뒤 새 세션이 무엇을 해야 할지 못 잡았다고 Jack이 지적했다.
- **왜(문제·동기)**: 메모리에는 **"무엇을 했나"**만 있었다. 조정 세션이 열자마자 필요한 건 그게 아니라 **"내가 누구고, 지금 무엇을 기다리고, 보고가 오면 어떻게 판단하나"**다. 상태는 있는데 실행 지침이 없었다.
- **어떻게(대안·결정·트레이드오프)**: 상태(진행 중인 세션 표)와 지침(판단 기준·명령어)을 분리해 지침을 별도 파일로 만들고, 메모리 인덱스 **맨 첫 줄**에 박았다 — 인덱스는 새 세션에 자동으로 실리므로 열자마자 보인다. 담은 것: 조정 세션이 하는 일 넷, 열자마자 읽을 것 셋, **보고가 오면 확인할 것 넷**(RED 확인했나 / 조용히 넘어가는 코드 없나 / 유닛 경계가 맞나 / 테스트가 진짜 뭘 재고 있나), 포트·디스크 중재 명령어, 내가 정할 것과 Jack에게 물을 것의 경계, 세션에 일을 넘기는 절차.
- **무엇을(실제 변경·파일·커밋)**: `memory/coordinator_handoff.md` 신설, `MEMORY.md` 최상단 등록.
- **결과·수치**: 미검증 — 다음 clear 후에 실제로 감을 잡는지가 검증이다.

## 블로그 네타

### "구멍을 하나씩 따라가면 끝이 안 난다 — 질문 응답에서 전수 점검으로"
- **훅·핵심 주장**: 이슈 하나를 파면 옆에서 하나가 더 나온다. 그건 시스템이 나빠서가 아니라 **묻는 자리만 보기 때문**이다. 한 번에 훑고 목록을 고정해야 "이게 전부인가"에 답할 수 있다.
- **context**: 남은 작업 문서를 갱신하다 문서에 없던 구멍이 넷 연달아 나온 날.
- **어떻게(서사·근거)**: 전송 지점 여섯·복구 경로 넷·무한 증가 지점을 한 번에 훑은 방법. 각 이슈에 "왜 지금은 안 터지나"를 붙인 이유(조건이 바뀌면 터진다). 이슈를 트랙으로 묶은 기준(같은 데이터를 쓰는 것끼리 — I1과 I5가 같은 값을 쓴다). 그리고 점검 이후 새로 나온 게 둘뿐이었다는 결과.
- **재료(커밋·도식·수치)**: `docs/_v2_remaining_work_design.html`(전수 점검판), I1~I11 표, 트랙별 겹침 표시.

### "고치면서 만든 구멍 — I1을 닫고 I11을 열었다"
- **훅·핵심 주장**: 상한 없는 목록을 하나 닫으면서, 같은 모양의 목록을 다른 자리에 하나 만들었다. 무한 증가를 고치는 코드가 무한 증가를 만드는 일은 생각보다 쉽다.
- **context**: 체결을 어디까지 반영했는지를 발행자별로 기억하게 바꾼 뒤, dc가 다른 작업 중에 발견.
- **어떻게(서사·근거)**: 넣는 코드만 있고 빼는 코드가 없다는 것(put은 두 곳, remove는 0건). 그 목록이 스냅샷 파일에 그대로 저장돼 **파일 크기까지 같이 커진다**는 것. 오늘 닫은 체결 번호 목록 릭과 정확히 같은 모양이라는 것. 닫는 방법이 "기록을 완전히 지우는 API는 멈춘 기록에만 쓸 수 있다"는 제약과 한 덩어리로 묶인다는 것.
- **재료(커밋·도식·수치)**: `AccountEventHandler:79`(put 289·311, remove 0), `AeronArchive.purgeRecording` javadoc(stopped 전용), 항목당 12바이트.

### "목록에 끝을 주는 법 — 무엇을 안 할지 정하기"
- **훅·핵심 주장**: 남은 일 목록이 "고칠 수 있는 것 전부"이면 영원히 안 끝난다. 프로젝트의 목적을 기준으로 **버릴 것을 명시**해야 끝이 생긴다.
- **context**: 이슈를 둘 닫고 둘 늘려 순증이 0이 된 날, "손댈수록 커진다"는 말이 나온 자리.
- **어떻게(서사·근거)**: 돈이 틀어지는 것 / 보여줄 것 / 운영 위생으로 나눈 기준. 버린 것이 만드는 파급을 같이 적은 것(조회 기능을 버리니 유실 후보 하나가 고를 수 없는 선택지가 됐다). "안 한다"를 기록에 남기면 면접에서 그게 답이 된다는 것.
- **재료(커밋·도식·수치)**: 범위 결정 배너, 닫은 것 둘·늘어난 것 둘의 대조.

### "기다리는 값이 틀렸을 때 — 구현을 의심하기 전에 관찰 신호를 의심하라"
- **훅·핵심 주장**: 테스트가 타임아웃 났다. 구현을 뒤졌다. 실제로는 **처리가 멀쩡히 되고 있었고 지켜보는 값이 틀렸다.** 같은 모양이 한 트랙에서 두 번 나왔다.
- **context**: Aeron Archive 기록 회수를 만들며 겪은 두 번의 삽질.
- **어떻게(서사·근거)**: ①보내는 쪽 position과 실제 기록 위치의 시차(비동기 녹화) ②걸러지는 재전송은 상태 카운터를 안 태운다는 것. 둘 다 "겉보기 진행"과 "내가 기다리는 진행"이 다른 값이었다는 공통점. 로그에 2만 번이 정확히 찍힌 걸 보고서야 방향을 바꾼 과정.
- **재료(커밋·도식·수치)**: `getRecordingPosition` 폴링으로 교체, `AccountSnapshotWriter.durableSeq()` 폴링으로 교체, 기대 8 대 실제 9, 30초 타임아웃.
