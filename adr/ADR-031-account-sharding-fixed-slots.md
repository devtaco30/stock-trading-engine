# ADR-031 계좌 샤딩·조정 — 상황 가정에서 출발, 고정 슬롯 + 정적 라우팅

- 날짜: 2026-09-14
- 상태: 채택(샤딩 스킴·라우팅 테이블 구현, 페일오버·리밸런싱은 설계)
- 관련: ADR-020(전송 반전) · K8s StatefulSet + PV 결정(ADR-026 네타, `decision_records/ha-k8s-statefulset-pv.md`) · C5 조정 결정(ADR-034 네타, `decision_records/c5-multiprocess-coordination.md`)

## 문제

v2 계좌 워커는 accountId로 소유를 나눠 여러 프로세스가 각자 맡는다. 한 계좌는 한 프로세스만 고쳐야(single-writer) 정합성이 유지된다. 그러려면 "이 계좌는 어느 프로세스 소유인가"라는 라우팅 지도가 필요하고, 주문을 보내는 api와 체결을 보내는 matching-worker가 그 지도로 목적지를 계산한다. 프로세스가 죽거나 늘면 지도가 바뀌고 인메모리 상태를 옮겨야 한다(리샤딩).

이 지도를 누가 어떻게 관리하느냐를 정하는 자리다. 처음에는 "언젠가 커질 수 있으니" 코디네이터·무중단 리샤딩·오토스케일까지 한 번에 설계하려 했다. 검증되지 않은 가정 위에 복잡도만 쌓는 방향이었다.

### 상황 가정 (이 결정의 출발점)

- 종목 수는 수천 규모로 한정되고 상장·상폐는 드문 통제된 이벤트다.
- 계좌 수는 한정되고 완만하게 는다. 폭증은 없다. 알려진 수로 미리 프로비저닝한다.
- 부하 피크(개장)는 예측 가능하고 반복된다. 피크 기준 정적 프로비저닝이면 되고 오토스케일은 불필요하다.
- 배포·용량 변경은 장 마감 후 통제된 창에서 한다. 장중 무중단은 예외 상황이다.
- 목적은 거래 엔진 이해다. 1차 정합성·신뢰성, 2차 속도. 확장성은 C7에서 검증할 대상이지 상시 탄력 운영 대상이 아니다.

## 대안

**샤딩 스킴**
1. `hash(accountId) % 프로세스 수`: 프로세스가 늘면 전 계좌가 재배치된다.
2. 일관 해시 링: 재배치는 줄지만 구현 복잡도가 오르고 이 규모에서 실효가 없다.
3. `hash(accountId) % P` 고정 슬롯(P는 프로세스 수와 무관한 큰 고정값, 예 256), 프로세스는 슬롯 범위를 소유: Kafka 파티션·Redis Cluster 16384 슬롯과 같은 방식.

**지도 관리**
1. 정적 라우팅 테이블(config): 통제된 변경만 가능.
2. 상시 코디네이터(Kafka 컨슈머 그룹 재사용 / etcd·ZooKeeper / 가십 + 일관 해시): 온라인 재배정 가능, 구현·운영 비용.

## 트레이드오프

| 기준 | 정적 라우팅 | 상시 코디네이터 |
|---|---|---|
| 장중 무중단 스케일 | 불가(재배포 시 그 슬롯 잠깐 멈춤) | 가능 |
| 새 의존성 | 없음 | Kafka 그룹 재사용이면 없음, etcd·ZK면 추가 |
| 구현 난도 | 최저 | 중~고 |
| 상황 가정과의 부합 | 장 마감 후 배포 전제에 맞음 | 폭증·오토스케일 전제에 맞음(우리 가정과 다름) |

고정 슬롯은 "슬롯 → 프로세스"만 바뀌고 "계좌 → 슬롯"은 영원히 고정이라, 리샤딩 단위가 슬롯 범위로 좁아진다.

리밸런싱 자체는 필요하다. 이유는 부하 폭증이 아니라 ① 페일오버 ② 확장성 검증(C7) ③ 상장·상폐·계좌 증가다. 세 경우 모두 통제된 저빈도 이벤트다.

## 결정

1. 샤딩 스킴 = `hash(accountId) % P` 고정 슬롯. 해시는 murmur3 fmix64(accountId가 Snowflake라 하위 비트에 순차 증가분이 몰리는 쏠림 방지).
2. 지도 = 정적 라우팅 테이블이 본선. sender가 `slotFor(accountId) → endpoint`를 계산해 Aeron unicast로 보낸다. 체결 fan-out(매수·매도 두 계좌)도 같은 테이블을 재사용한다.
3. 페일오버 = K8s StatefulSet 안정 신원 재시작 + PV의 Archive 저널 replay(`decision_records/ha-k8s-statefulset-pv.md`). 라우팅 테이블은 바뀌지 않는다.
4. C7용 통제된 리샤딩(스냅샷 + 저널 재사용 + 라우팅 플립)은 구현 대상이다. 장중 무중단 핸드오프(예열 → 드레인 → 꼬리 catch-up → 플립 → 재개)와 상시 코디네이터는 설계 문서로만 둔다.
5. stockCode축(매칭)도 같은 논리다. 핫 종목의 호가창은 쪼갤 수 없으므로 종목 통째로 이동한다.

원칙: 상황 가정이 출발점이고 거기서 결정이 따라나온다. "확장성 대비"를 명분으로 검증 안 된 가정 위에 코디네이터·무중단·오토스케일을 미리 넣지 않는다.

## 결과

- 구현: `core/.../aeron/ShardRoutingTable`(슬롯 계산, 범위 갭·중복 fail-fast), matching-worker의 `ShardRoutingConfig`(체결 fan-out 목적지), fork3 `d0faeb6` `8990873` `c9ff306` `d42f033`. 로컬 2샤드 UDP 크로스샤드 체결 테스트로 각 샤드가 자기 소유 계좌만 반영함을 검증.
- 아직 없는 것: api의 account-intake 라우팅(지금은 endpoint 하나), account-worker의 슬롯 소유 개념(지금은 seed-accounts 목록으로 소유 판정).
- 이 ADR을 쓴 뒤 C5 조정 결정(2026-09-14, `decision_records/c5-multiprocess-coordination.md`)이 HA를 cold 재시작에서 warm standby로 올리고 조정을 Kafka 컨슈머 그룹 재사용으로 정했다. 슬롯 스킴·정적 테이블·상황 가정 원칙은 그대로다.
- 정정 이력: 처음 "온라인 탄력성이 목표"로 과하게 잡았다가 "부하 폭증은 계좌 수가 아니라 주문 rate"라는 지적으로 좁혔다.
- 미결(리샤딩 착수 때): P 값 확정, 지도 갱신 채널(config reload vs compacted 토픽), 드레인·플립 구현 상세.
