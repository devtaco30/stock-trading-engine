# ADR-042: 계좌 서버와 매칭 서버의 기동 순환 의존을 없앤다

상태: 제안 (Jack이 방향 D를 결정, 세부 승인 대기) · OpenSpec 변경 `break-account-matching-startup-cycle`

## 문제

계좌 서버와 매칭 서버는 기동할 때 서로를 요구한다.

- 계좌 서버는 기동할 때 배정 맵 토픽(`matching-shard-map`)의 파티션 목록을 읽고, 없으면 기동을 중단한다(`MatchingDestinationResolver.java:150-157`). 이 토픽은 매칭 서버가 만든다.
- 매칭 서버는 기동할 때 계좌 주소로 체결·거부 회신 Publication을 연다(`MatchingFillPublishConfig.java:42-71`, `MatchingRejectReplyConfig.java:28-32`). Aeron은 이때 주소 이름을 풀기 때문에 계좌 파드가 없으면 `UnknownHostException`으로 실패한다(kind 첫 실행).

맥 시험은 `mix.sh`가 매칭 서버를 먼저 띄우고 8초 기다리는 순서로 이 순환을 가려 왔다. 쿠버네티스에서는 init 컨테이너 두 개와 실행 스크립트의 문 열기 단계로 순서를 맞췄고, 계좌 파드가 새로 만들어지면 사람이 문을 다시 열어야 했다. 서로를 기동 조건으로 요구하는 구조는 상대 주소 찾기를 실행 중 의존으로 두지 않고 기동 의존으로 만든 형태이고, 배포 도구의 순서 지정으로도 풀리지 않는다(두 자원을 모두 상대보다 앞에 둘 수 없다).

함께 드러난 문제: 매칭 서버는 목적지를 모르는 체결을 버린다(`AccountFillPublisher.java:48-53`, 코드 주석에 미해결로 적혀 있음).

## 대안

1. **기동 순서를 바깥에서 맞춘다** (지금 k8s 구성, 또는 init 컨테이너가 배정을 확인, 또는 실패하게 두고 재시작). 제품 코드를 바꾸지 않지만 순환은 그대로다.
2. **계좌 서버가 배정을 기다리고(D1), 매칭 서버가 체결 채널을 MDC dynamic으로 바꾼다.** 계좌 서버가 매칭 서버 제어 주소로 자기 주소를 등록한다.
3. **계좌 서버가 배정을 기다리고(D1), 매칭 서버가 계좌 shard 맵을 보고 Publication을 나중에 연다(D2).** 목적지를 모르는 체결은 보관한다.
4. **D1 + 매칭 서버가 Publication 생성을 이름이 풀릴 때까지 재시도.**

## 트레이드오프

- 대안 1은 순환이 남아 증설 시험에서 재시작마다 순서를 다시 맞춰야 한다.
- 대안 2는 같은 체결 스트림이 모든 계좌 shard로 가서, shard마다 자기 계좌가 아닌 체결을 저널에 기록하고 NOT_OWNED로 거르는 비용이 shard 수만큼 는다. 주소별 아웃박스가 없어져 느린 shard 하나가 다른 shard의 체결을 막는다. 체결 녹화를 찾는 채널 문자열이 바뀌고, 계좌 서버가 매칭 서버 주소를 알아야 하는 새 의존이 생긴다. 이전 결정(`decision_records/c5-multiprocess-coordination.md`: MDC는 목적지가 체결마다 달라 부적)과 맞지 않는다.
- 대안 3은 이미 있는 장치(계좌 쪽 주문 보관 경로, 매칭 쪽 계좌 shard 맵 구독)를 그대로 사용한다. 새로 만드는 것은 런타임 Publication 생성과 매칭 서버의 체결 보관 목록이다. 체결은 버릴 수 없으므로 보관 한도를 넘었을 때 새 주문 접수를 멈추는 신호가 필요하다. 첫 체결은 Publication 연결 시간만큼 늦다.
- 대안 4는 변경이 가장 작지만, 매칭 서버가 기동 때 계좌 주소 목록을 아는 구조가 남아 계좌 shard를 늘릴 때 매칭 서버 설정 변경과 재시작이 필요하다.

## 결정

대안 3. 2026-11-05 독립 검토로 아래 범위를 넓혔다.

- 원칙: 상대 서버와의 연결은 전부 실행 중에 Kafka 맵으로 찾아서 연다. 기동은 Kafka 브로커 말고는 기다리지 않는다.
- 계좌 서버도 매칭 서버행 주문 Publication을 기동 때 열지 않는다(`account-worker MatchingShardRoutingConfig.java:93-100`).
- 매칭 서버 동적 모드가 계좌 서버의 토픽을 60초 기다리는 의존(`ShardSlotCountSource.java:44-58`)과, 맵 토픽 재조회·자동 생성 미차단을 함께 고친다.
- Publication은 프로세스가 살아 있는 동안 닫지 않는다.
- 계좌 서버도 동적 모드(`account-shard.coordination.enabled=true`)로 바꾼다.
- api 서버도 같은 원칙을 따른다. 계좌 서버행 Publication을 기동 때 열지 않고(`AccountOrderPublishConfig.java:83`, `:108`), 계좌 서버 토픽 60초 대기(`api ShardRoutingConfig.java:66-79`)를 매칭 서버와 같은 방식으로 바꾼다. 최종 측정은 api를 거치므로 범위에 넣는다.
- Jack 결정(2026-11-05): 조정·맵 토픽은 인프라(토픽 생성 Job)가 만들고 서버는 읽기만 한다. 체결 보관 한도 초과는 매칭→계좌 새 신호로 그 매칭 서버행 주문만 멈춘다. 주소는 허용 목록 대신 규칙으로 검사한다. NOT_OWNED 체결 유실 결함은 별도 변경으로 먼저 고친다. api 서버는 목적지를 모르는 동안의 주문을 보관한다.


- D1: 계좌 서버는 배정 맵이 없거나 비어 있어도 기동하고, 배정을 모르는 slot의 주문은 보관 경로에 둔다.
- D2: 매칭 서버는 계좌 shard 맵에 주소가 올라온 뒤 그 주소로 체결·거부 회신 Publication을 연다. 목적지를 모르는 체결은 보관하고, 목적지가 생기면 보낸다.
- 체결 fan-out은 unicast 2번을 유지한다(c5 결정 유지).
- 체결 보관 한도 값과 한도 초과 때 접수 중지 방식은 OpenSpec 작업 1.3에서 정한다.

## 결과

- k8s 매니페스트에서 `wait-start-gate`, `wait-account-dns`, `run.sh`의 문 열기 단계를 지운다.
- 매칭 서버는 k8s에서 동적 모드를 사용한다. 맥 시험이 사용하는 정적 모드(`shard-routing.shards`)는 남긴다.
- 목적지를 모르는 체결이 버려지던 미해결 동작이 보관으로 바뀐다. 보관은 메모리에만 있어 매칭 프로세스가 죽으면 사라진다.
- 검토에서 따로 나온 결함: NOT_OWNED 체결은 수신 위치를 올린 뒤 버려진다(`AccountEventHandler.java:385-392`). 이 ADR 범위 밖이며 별도로 다룬다.
- 기동 직후 매칭 서버가 늦게 뜨는 동안 주문 지연이 생기고, 보관 한도를 넘으면 `MATCHING_HOLDING_FULL`로 거부된다(지금과 같은 거부 사유).
