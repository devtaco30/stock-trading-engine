# ADR-041: 시험용 로컬 쿠버네티스 도구로 kind를 직접 설치해 쓴다

상태: 제안 (Jack 승인 대기)

## 문제

계좌 서버·매칭 서버의 한계 측정과 증설 시험을 쿠버네티스로 옮긴다(OpenSpec 변경 `k8s-scale-test-local`). 측정은 EKS에서 하지만, 매니페스트와 이미지 디버깅은 돈이 들지 않는 맥에서 끝내야 한다. 그래서 맥에서 띄울 로컬 쿠버네티스 도구를 골라야 한다.

이 결정에 걸린 우리 상태(2026-11-05 확인):

- 맥은 M1 Pro(arm64)이고, EKS 노드 후보도 c7g(Graviton, arm64)다. 이미지를 arm64 하나로 만들면 로컬과 EKS에서 같은 이미지를 사용한다.
- Docker Desktop 4.71.0이 깔려 있다. 가상 머신 자원은 CPU 10개, 메모리 약 6.2GB, 디스크 상한 16GB(사용 6.4GB)다. 로컬 쿠버네티스는 어떤 도구를 쓰든 이 가상 머신 안에서 돈다.
- 같은 Docker 안에 다른 프로젝트 컨테이너(`sentinel-db-1`)가 돌고 있다. 이 컨테이너는 건드리면 안 된다.
- 쿠버네티스 도구는 `kubectl`만 깔려 있다.
- 시험은 시험마다 새 에이전트가 실행한다(컨텍스트 압축으로 세션 기억이 사라지는 문제 때문에 Jack이 정함). 그래서 클러스터 생성·삭제가 사람 손 없이 명령줄로 돼야 한다.
- 실행 스크립트는 수명이 지나면 구성을 지워야 한다(`k8s-scale-test-local` spec). 이 동작도 명령줄로 돼야 한다.
- 계좌 서버와 매칭 서버는 Aeron UDP로 주고받는다. 파드 사이 UDP가 EKS와 비슷한 네트워크 구성에서 확인돼야 EKS로 넘어갔을 때 다시 디버깅하지 않는다.

## 대안

1. **kind 직접 설치** (`brew install kind`)
   쿠버네티스 노드를 Docker 컨테이너 하나로 띄우는 쿠버네티스 공식 프로젝트(kubernetes-sigs) 도구다. 노드 수, 쿠버네티스 버전, 포트 매핑을 설정 파일(`kind-config.yaml`) 하나에 적고 `kind create cluster --config`로 만든다. 지울 때는 `kind delete cluster`를 실행한다.
2. **Docker Desktop 내장 쿠버네티스 (kind 방식)**
   Docker Desktop 설정 화면에서 켠다. 4.38 이상은 내부적으로 kind를 써서 노드를 여러 개 만들 수 있다고 공식 문서에 나온다. 이 방식을 쓰려면 Docker 계정 로그인이 필요하다고 같은 문서에 나온다.
3. **k3d**
   가벼운 배포판 k3s를 Docker 컨테이너로 띄운다. 기본 CNI가 flannel이고 Traefik이 같이 깔린다.
4. **minikube** (Docker 드라이버)
   쿠버네티스 공식 로컬 도구다. 노드 여러 개를 만들 수 있고 애드온을 명령으로 켤 수 있다.

## 트레이드오프

| 기준 | kind 직접 | Docker Desktop(kind) | k3d | minikube |
|---|---|---|---|---|
| 에이전트가 명령줄로 만들고 지우기 | 된다 | 설정 화면에서 켜는 방식. 명령줄 제어는 확인하지 않았다 | 된다 | 된다 |
| 클러스터 설정을 파일로 레포에 남기기 | `kind-config.yaml` | 설정 화면 값이라 레포에 남지 않는다 | 설정 파일 있음 | 확인하지 않았다 |
| EKS와 구성 차이 | 표준 kubelet, 기본 CNI kindnet | kind와 같다 | 배포판이 k3s라 차이가 가장 크다 | 표준 구성 |
| 추가 설치 | kind 하나 | 없음 | k3d 하나 | minikube 하나 |
| 계정 로그인 | 필요 없음 | 필요(문서 기준) | 필요 없음 | 필요 없음 |
| 메모리 사용 | 측정하지 않았다 | 측정하지 않았다 | k3s가 구성 요소를 줄인 배포판이라 적을 것으로 본다(미측정) | 측정하지 않았다 |

네 도구 모두 같은 Docker 가상 머신의 CPU와 메모리를 나눠 사용한다. 그래서 어느 도구에서 나온 처리량도 성능 값으로 인정할 수 없다. 가상 머신 메모리도 어느 도구를 고르든 늘려야 한다. Jack이 8GB로 정했다.

kind 직접 설치와 Docker Desktop의 kind 방식은 내부가 같다. 둘의 차이는 만들고 지우는 방법뿐이다. 우리는 에이전트가 수명 만료 삭제까지 명령줄로 해야 하므로 이 차이가 결정에 영향을 준다.

로컬 클러스터에서 확인하는 것은 「매니페스트와 이미지로 뜨고 판정을 통과하는가」뿐이다. 처리량은 재지 않는다. 그래서 도구 사이 차이 중 결정에 영향을 주는 것은 EKS와 구성이 얼마나 다른가와, 노드 구성을 레포에 남길 수 있는가 두 가지다. kind와 minikube는 둘 다 표준 쿠버네티스라서 이 확인 범위에서 결과가 달라질 이유가 없다. 둘의 기동 시간이나 메모리를 재서 차이가 나와도 결정이 바뀌지 않으므로 비교 측정은 하지 않는다.

kind 기본 CNI(kindnet)는 EKS 기본 CNI(Amazon VPC CNI)와 다르다. 그래서 파드 사이 Aeron UDP가 kind에서 되더라도 EKS에서 다시 확인해야 한다. 이 점은 네 도구 모두 같다.

## 결정

kind를 직접 설치해 쓴다.

- 표준 쿠버네티스 구성이라 EKS와 차이가 적다. k3d는 k3s 배포판(기본 CNI flannel, Traefik 기본 설치)이라 이 기준에서 뺐다.
- 노드 구성을 `k8s/kind-config.yaml` 파일 하나로 레포에 남겨, 누가 만들어도 같은 클러스터가 나온다. Docker Desktop의 kind 방식은 설정 화면 값이라 레포에 남지 않고, 계정 로그인도 필요하다(공식 문서 기준).
- minikube도 표준 쿠버네티스라 확인 범위에서는 kind와 차이가 없다. 둘 중 하나만 있으면 되므로 kind를 골랐고, minikube가 더 나쁘다는 근거는 없다.
- 명령줄로 만들고 지우는 것은 kind·k3d·minikube 모두 된다. 이 항목은 Docker Desktop 방식과 비교할 때만 차이가 난다.

## 결과

- `brew install kind`가 필요하다. 비용은 없다.
- Docker Desktop 메모리를 8GB로 늘린다(Jack 결정, 맥 전체 32GB). 파드별 메모리 사용량은 kind에서 먼저 재고, 모자라면 잰 값을 근거로 다시 정한다. 맥 시험에서 계좌 서버 힙은 GC 직후 최대 2,260MB였고, 맥 스크립트에는 `-Xmx`가 없어 JVM 기본값(물리 메모리의 1/4)이 적용됐다(`mix.sh:74`).
- kind 노드 이미지(`kindest/node`)가 Docker 디스크 16GB 상한 안에 함께 들어간다. 이미지 크기는 작업 2.3에서 측정한다.
- kind 클러스터 컨테이너는 이름이 `<클러스터>-control-plane`, `<클러스터>-worker` 형태로 뜬다. `sentinel-db-1`과 이름이 겹치지 않고, `kind delete cluster`는 kind가 만든 컨테이너만 지운다.
- kind에서 확인한 것은 「뜨고 판정을 통과한다」까지다. Aeron UDP와 처리량은 EKS에서 다시 확인한다.
