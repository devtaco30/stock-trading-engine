# ADR-023 orderId는 계좌 워커가 발급하고, 값은 발급 시각을 빼고 (nodeId, 카운터)로만 만든다

- 날짜: 2026-09-08(발급 위치) · 2026-09-09(발급 방식)
- 상태: 채택
- 관련: ADR-008(v1 주문 재전송 멱등) · ADR-014(single-writer 계좌) · ADR-020(전송 반전) · ADR-025(엔진 journal과 replay) · ADR-035(멱등 장부 상한) · 원문 `decision_records/id-idempotency-determinism.md`

## 문제

이 레포에는 같은 매매 엔진이 두 벌 있다. v1은 주문이 들어오면 DB에서 계좌 행에 비관적 락을 걸고 잔고를 확인해 매수 대금을 예약한다. v2는 그 락을 걷어낸 구현이다. 계좌 하나의 상태를 한 스레드가 메모리에 두고 들어온 순서대로만 고친다(ADR-014). v2에서 주문 한 건은 api → 계좌 워커(잔고 확인과 매수 대금 예약) → 매칭 워커(호가창에서 체결) → 계좌 워커(체결 반영) 순으로 지나간다. 이 구간을 핫패스라 부르고, 여기서는 DB도 외부 캐시도 건드리지 않기로 했다(ADR-020).

### 용어

- **requestId** — 클라이언트가 주문 요청마다 붙여 보내는 식별자. 네트워크 재시도로 같은 주문이 두 번 도착했는지를 서버가 이 값으로 판단한다.
- **orderId** — 접수된 주문 한 건에 서버가 붙이는 식별자. 체결·취소·조회가 전부 이 값으로 주문을 가리킨다.
- **계좌 워커(account-worker)** — 계좌 상태를 메모리에 두고 단일 스레드로 고치는 프로세스. v2에서 주문 검증과 매수 대금 예약을 여기서 한다.
- **핫패스** — 주문 한 건이 api → 계좌 워커 → 매칭 워커 → 계좌 워커로 지나는 구간. 여기서는 DB도 외부 캐시도 건드리지 않는다(ADR-020).
- **journal · replay** — journal은 엔진이 받은 입력을 받은 순서대로 적어 둔 기록이고, replay는 그 기록을 처음부터 다시 적용해 상태를 만드는 복구 방식이다(ADR-025).
- **Snowflake id** — 발급 시각·노드 번호·순번을 한 long에 담는 분산 id 생성 방식. v1과 v2 초기에 썼다.
- **nodeId** — 워커 프로세스마다 다르게 주는 번호. 여러 대를 띄워도 발급값이 겹치지 않게 한다.
- **single-writer** — 한 상태를 한 스레드만 고치는 규칙(ADR-014). 락 없이 정합성을 지키는 v2의 토대다.
- **멱등 장부** — 이미 반영한 체결·정산·요청을 기록해 두고 같은 것이 또 오면 버리는 집합.
- **호가창(order book)** — 한 종목의 미체결 매수·매도 주문을 가격과 도착 순서로 줄 세운 자료구조. 매칭 엔진이 종목마다 하나씩 메모리에 들고 있다(ADR-006).
- **스냅샷(snapshot)** — 어느 한 시점의 엔진 상태 전체를 통째로 직렬화해 파일로 남긴 것(ADR-030). 복구할 때 이 파일을 먼저 읽고 그 뒤 입력만 replay한다.

그래서 v1이 DB에 맡겼던 일을 v2에서 하나씩 다시 정해야 한다. 이 ADR은 그중 orderId를 다룬다. v1에서는 주문을 `orders` 테이블에 저장하는 순간 orderId 값이 생겼고, 같은 주문이 두 번 들어오는 것은 `request_id` UNIQUE 제약이 막았다(ADR-008). v2 핫패스에는 그 테이블도 그 제약도 없다. 그래서 orderId를 누가 발급할지부터 정해야 한다.

발급 위치를 정한 다음 날 두 번째 문제가 나왔다. v2는 프로세스가 죽으면 journal replay로 복구한다(ADR-025). 이 복구는 엔진이 같은 입력에서 항상 같은 값을 내야 성립한다. 그런데 처음 쓴 Snowflake id는 발급 시각을 값 안에 섞는다. 재시작하면 같은 입력에서 다른 orderId가 나온다. 그러면 복구된 계좌 워커는 그 주문을 새 orderId로 들고, 매칭 워커의 호가창에는 옛 orderId로 남는다. 사용자가 그 주문을 취소해도 호가창에서 지워지지 않는다.

## 대안

**발급 위치**

1. **게이트웨이(주문을 받는 api 서버)가 발급한다.** requestId와 orderId의 짝을 게이트웨이가 보관하고 재전송을 입구에서 거른다.
2. **계좌 워커가 발급한다.** 같은 requestId를 이미 봤는지 기록하는 집합(`processedRequestIds`)이 이미 계좌 워커 안에 있다.
3. **Redis에 짝을 둔다.** 게이트웨이가 Redis를 조회해 재전송을 거른다.

**발급 방식**

- **A. 게이트웨이가 값을 붙여 입력에 실어 보낸다.** 입력에 id가 들어 있으면 replay는 그 값을 다시 읽기만 하면 된다. 발급 위치 결정을 되돌리는 안이다.
- **B. 계좌 워커가 발급하고 곁journal을 둔다.** 곁journal은 발급한 orderId만 따로 적는 두 번째 기록이다. 복구할 때 입력 journal과 이 기록을 같이 읽는다.
- **C. 계좌 워커가 발급하되 값을 카운터로 만든다.** 발급 시각을 값에 섞지 않는다.

## 트레이드오프

| 기준 | 1. 게이트웨이 | 2. 계좌 워커 | 3. Redis |
|---|---|---|---|
| 재전송 판정의 권위 | api 인스턴스가 여럿이면 나뉨 | 계좌 하나당 한 곳 | 외부 저장소 |
| 핫패스 외부 I/O | 없음 | 없음 | 네트워크 왕복(ms) |
| 복구 때 발급 상태 | 게이트웨이가 따로 보관하고 복구 | 계좌 스냅샷에 같이 실림 | 외부 저장소가 보관 |
| 클라이언트 응답 | 입구에서 바로 orderId 반환 | 왕복 뒤에 값이 생김 | 입구에서 바로 반환 |

앞단에서 걸러도 계좌 워커의 가드는 없앨 수 없다. 게이트웨이가 죽거나 api 인스턴스끼리 경합하면 같은 requestId가 그 뒤로 새어든다. 1과 3을 고르면 같은 판정을 두 곳에서 하게 되고, 어느 쪽이 권위인지가 흐려진다. 3은 여기에 더해 ADR-020이 핫패스에서 걷어낸 네트워크 왕복을 되돌려 놓는다. Redis를 나중에 입구의 best-effort 필터로 둘 수는 있지만 권위는 될 수 없다.

| 기준 | A. 게이트웨이 부여 | B. 곁journal | C. 결정론 카운터 |
|---|---|---|---|
| replay 재현 | 입력에 값이 실려 있어 성립 | 곁journal을 같이 읽어야 성립 | 입력 journal만으로 성립 |
| 발급 위치 결정 | 되돌려야 함 | 유지 | 유지 |
| 새로 만들 것 | 게이트웨이 발급·보관 | 기록 하나 더 | 없음 |

## 결정

발급 위치는 2(계좌 워커), 발급 방식은 C(카운터)다.

**orderId는 계좌 워커가 발급한다.** 한 계좌에 관한 상태가 모두 한 곳에 있으므로 스냅샷에 같이 저장되고, 복구할 때 따로 맞춰야 하는 외부 상태가 생기지 않는다.

**값은 `(nodeId << 53) | counter`다.** nodeId는 워커 프로세스마다 다르게 주는 10비트 번호(0~1023)이고, 계좌 워커를 여러 대 띄워도 발급값이 겹치지 않게 한다. counter는 53비트이며 엔진 객체의 필드다(`AccountOrderIdGenerator.java:29`). 맨 앞 부호 비트는 0으로 남아 값이 항상 양수 long이다. 주문이 들어온 시각은 `orderAt` 필드가 따로 담으므로 id에 시각을 섞을 이유가 없다.

**카운터는 엔진 상태로 다룬다.** 스냅샷에 `generatorCounter`로 저장되고(`AccountSnapshot.java:21`), journal replay에서도 같은 횟수만큼 올라간다. 재전송으로 판정된 요청은 발급 자체를 건너뛰므로 카운터가 움직이지 않는다.

이 결정은 계좌 워커의 orderId까지다. 매칭 워커가 체결에 붙이는 tradeId에도 같은 방식을 적용하려 했지만 지금 코드는 그대로 Snowflake다(`AccountFillPublisher.java:66`). 그래서 매칭 엔진을 replay하면 같은 체결에 다른 tradeId가 붙는다. 이 사실은 뒤에 tradeId를 다루는 결정(ADR-035)의 전제가 된다.

## 결과

- `AccountOrderIdGenerator`를 추가하고 계좌 워커의 `SnowflakeConfig`를 지웠다(`e1fdd73`). 새로 만든 엔진 둘에 같은 입력을 넣어 같은 id가 나오는지 보는 테스트가 있다(`AccountOrderIdGeneratorTest`).
- 재전송 멱등은 그 전날 들어갔다(`362f05d`). `AccountEventHandler.handleBuy`는 계좌를 확인한 뒤 검증에 들어가기 전에 requestId를 보고, 이미 본 값이면 orderId를 발급하지 않고 `onDuplicateRequest`로 알린다(`AccountEventHandler.java:277`).
- 설계 단계에서는 requestId와 orderId의 짝을 맵으로 보관해 재전송에 원래 orderId를 돌려줄 생각이었다. 그 값을 읽는 코드가 실제로 없어서 "봤다"만 기록하는 집합으로 줄였다(`AccountState.java:73`). 이 집합을 어디서 자를지는 ADR-035에서 정한다.
- 대가는 응답 시점이다. orderId는 주문이 계좌 워커까지 가야 생기므로 api가 입구에서 돌려주지 못한다. 지금 202 응답 본문에는 메시지 하나만 들어 있고(`OrderAcceptedResponse`), 클라이언트가 결과를 찾아갈 키를 돌려주는 일은 ADR-021에 남은 과제로 적혀 있다.
