# ADR-011 종목별 토픽을 단일 파티션 분할 토픽으로 전환

## 문제

`orders.{stockCode}`·`fills.{stockCode}` 처럼 **종목마다 토픽을 하나씩** 쓴다. 같은 종목의 주문을 한 스레드가 순서대로 처리(single-writer)하려는 목적이었다.

상장 회사는 코스피 약 900 + 코스닥 약 1,820 = 대략 2,500~2,700개(2026년 기준, 우선주까지 세면 거래 종목은 더 많다). 그래서 토픽이 수천 개, `fills` 까지 하면 5천 개를 넘는다.

**용량 문제는 아니다.** 5천여 파티션은 Kafka(특히 이 프로젝트가 쓰는 KRaft)에 작은 규모라 그냥 동작한다. 실제 문제는 **운영 오버헤드**다.

- 수천 토픽을 만들고 모니터링·설정하는 관리 손
- 파티션이 많을수록 느려지는 컨슈머 리밸런싱
- 패턴 구독(`orders\..*`)이 새 토픽을 메타데이터 갱신 때만 발견 → 콜드스타트 지연(이번 정산 테스트에서 실제로 겪음)
- 새 종목 상장마다 토픽 생성이 필요

핵심은 이거다. 같은 순서 보장을 **파티션 수십 개**로 얻을 수 있는데, 수천 토픽을 유지할 이유가 없다.

## 대안

1. **현행 유지(종목당 토픽).** 종목 격리는 완벽. 대신 위 오버헤드를 계속 부담.
2. **단일 토픽 + 종목으로 파티셔닝.** `orders` 토픽 하나(파티션 N개), `key=stockCode`. 같은 종목은 해시로 항상 같은 파티션 → 같은 컨슈머 스레드 → 순서 보장. 종목이 늘어도 토픽·파티션 수는 고정.

## 트레이드오프

| 기준 | 종목당 토픽 | 단일 파티션 분할 |
|---|---|---|
| 종목 격리(HOL) | 완벽 | 파티션 공유 → 느린 종목이 이웃 지연 |
| 토픽/파티션 수 | 종목 수에 비례(수천) | 고정(예: 50) |
| 새 종목 추가 | 토픽 생성 필요 | 작업 없음 |
| 리밸런싱 | 수천 파티션(느림) | 수십(빠름) |
| 콜드스타트 | 패턴 발견 지연 | 토픽 하나라 즉시 |
| 전환 비용 | — | 일회성(복원 로직 재설계) |

## 결정

**대안 2 채택.** `order-requests` 가 이미 `accountId` 로 하는 방식과 동일하게, `orders`·`fills` 도 단일 토픽 + `stockCode` 파티셔닝으로 맞춘다.

- 토픽: `orders`(파티션 N), `fills`(파티션 N). 발행 시 `key=stockCode`.
- 파티션 수 N: 매칭 병렬 목표(예상 최대 매칭 컨슈머 스레드 수)를 보고 **넉넉히 한 번에** 정한다. 초기값 **50**을 프로퍼티로 두고 환경별 조정(늘리는 건 key 재해시로 순서가 깨지므로 처음에 크게 잡는다).
- 구독: `@KafkaListener(topicPattern="orders\\..*")` → `topics="orders"`. 정산도 동일.
- 토픽 선언: 고정 이름이 되므로 `NewTopic` 빈으로 파티션 수를 코드에 박는다(auto-create 의존 제거).

### 복원 소스 — DB vs Kafka replay (이 구조가 강제하는 트레이드오프)

재시작·리밸런스로 인메모리 호가창을 잃었을 때, 쉬는 주문(PENDING)으로 호가창을 다시 채우는 소스가 둘이다. 그리고 **단일 파티션 토픽으로 갈수록 replay로는 호가창을 정확히 되돌리지 못한다.**

- **Kafka replay(event sourcing)**: 로그는 오프셋으로만 읽힌다 = **파티션 단위**. 그런데 한 파티션엔 여러 종목이 뒤섞여 있어, 종목 하나만 복원하려 해도 파티션 전체를 훑어야 한다(O(종목 하나)에 O(파티션 전체)). 그래서 종목별 지연 복원이 불가능하고, **파티션 전체를 eager replay**해 모든 종목 호가창을 한 번에 재구성해야 한다. 게다가 매칭을 다시 돌려 쉬는 상태를 **재유도**해야 하고(결정성·중복 fill 발행 관리 필요), retention 때문에 스냅샷·오프셋 체크포인트 인프라도 있어야 한다. Kafka가 죽은 상황에선 매칭할 입력 스트림도 없어 "다운 시 replay 복원"은 실효가 거의 없다.
- **DB 로드(채택)**: DB는 쉬는 상태(PENDING)를 **매칭의 파생 결과로 이미 저장**하고 있고 종목 인덱스로 바로 조회된다(`WHERE stock=S`). 재유도가 없고, 종목별 지연 로드와 정확히 맞는다.

근본은 이렇다. 호가창의 쉬는 상태는 매칭의 **파생 결과**다. DB는 그 결과를 직접(종목별로) 들고 있고, Kafka 로그는 원시 이벤트를 파티션에 뒤섞어 담아 상태를 재유도해야 한다. 파티션 게이팅과 종목별 지연을 파고들수록 이 granularity(종목 vs 파티션)·derived-vs-raw 미스매치가 커진다.

**결정: DB를 복원 소스(source of truth)로 유지한다.** replay의 값어치는 감사·재프로젝션에 있으며, 도입하려면 스냅샷+오프셋+DB 백업 조합이 필요해 별도 결정(Phase 3+)이다.

### 복원 트리거 — 지연 로드 vs 선복원

DB 복원을 언제 부를지도 정해야 한다. 단일 토픽에선 `onPartitionsAssigned` 가 주는 건 **파티션 번호**뿐이라(종목 역산 불가), AS-IS처럼 할당 시점에 종목별 복원을 못 한다.

- **지연 로드(권장)**: 그 종목의 메시지가 처음 도착해 종목이 밝혀지면, 호가창이 없을 때 DB에서 PENDING 을 로드해 만든 뒤 처리한다. 파티셔너를 흉내 낼 필요가 없고, 실제로 받는 종목만 로드한다. 쉬는 주문도 교차 주문(메시지)이 올 때 함께 복원되므로 놓치는 체결이 없다.
- **선(先)복원**: `onPartitionsAssigned` 에서 PENDING 전체를 훑어 `partitionFor(stockCode)==할당파티션` 인 것만 복원한다. Kafka 기본 파티셔너(murmur2)와 완전히 동일한 계산을 재현해야 하는 부담이 있다.

지연 로드를 우선한다. 파티셔너 일치 위험이 없고 리밸런싱 시 DB 스파이크도 없다.

## 결과

- 운영비(토픽 관리·리밸런싱·콜드스타트·브로커 리소스)가 종목 수와 무관하게 고정된다.
- 대가로 HOL 블로킹(파티션 공유)을 받아들이고, 복원 경로를 다시 짠다.
- 이 변경은 메시징 구조 자체를 바꾸므로 부하·교차체결 e2e로 반드시 재검증한다.
- `matching-engine` 복원 경로는 Phase 3(DB 분리) 때 Event Sourcing/스냅샷으로 갈 지점과 겹친다. 이번 지연 로드 설계는 그 방향과도 어긋나지 않는다.
- 이 결정은 학습 목적의 개선이다. 현행도 이 규모에선 동작하므로 긴급하지 않다.
