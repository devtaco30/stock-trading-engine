체결 하나를 두 프로세스로 나눠 반영하기

v2는 계좌를 accountId로 샤딩해 계좌마다 한 프로세스가 전담한다(single-writer). 그런데 한 번의 체결은 매수 계좌와 매도 계좌를 동시에 바꾼다. 두 계좌가 서로 다른 프로세스에 있으면, 체결 하나를 두 프로세스에 각각 보내야 한다. 이것이 fan-out이다.

①맥락 — 왜 지금 fan-out인가

지금까지 v2는 계좌 프로세스가 하나라는 가정으로 돌았다. 매칭이 체결을 만들면 그 체결 하나를 계좌 프로세스로 보내고, 그 프로세스가 매수 계좌와 매도 계좌를 둘 다 메모리에서 바꿨다. 두 계좌가 같은 프로세스 안에 있으니 문제가 없었다.

샤딩을 켜면 상황이 달라진다. 계좌 90001(매수)과 90002(매도)가 슬롯 계산 결과 서로 다른 프로세스로 나뉠 수 있다. 이때 체결 하나를 한 프로세스에만 보내면 다른 쪽 계좌는 갱신되지 않는다. 매수자는 주식을 받았는데 매도자의 보유는 그대로 남는 어긋남이 생긴다.

그래서 매칭은 체결의 매수·매도 accountId를 각각 슬롯으로 계산해, 그 체결을 두 목적지 프로세스에 보낸다. 두 프로세스는 각자 자기가 소유한 계좌만 반영한다. 이 문서가 다루는 범위는 라이브 경로까지다. 재기동 복구(매칭이 남긴 기록을 계좌가 다시 재생할 때 기록이 여러 개인 경우)는 여기서 다루지 않는다.

②용어

fan-out 팬아웃

체결 하나를 매수·매도 두 계좌 소유 프로세스에 각각 보내는 것. 각 프로세스는 tradeId로 중복 반영을 막는다.

샤드 shard

accountId로 나뉜 계좌 묶음 하나를 전담하는 계좌 프로세스. 자기 샤드의 계좌만 메모리에 들고 있다.

슬롯 slot

hash(accountId) % P로 나온 고정 번호(P=슬롯 총수). 계좌를 어느 샤드가 맡을지 결정하는 안정적 키다.

라우팅 테이블 routing table

슬롯 번호를 목적지 Aeron endpoint(샤드 주소)로 잇는 정적 표. 매칭이 어디로 보낼지 이 표로 정한다.

unicast 유니캐스트

한 목적지에 1:1로 보내는 방식. fan-out은 unicast를 목적지 수만큼 반복한다(여기선 매수·매도 두 번).

tradeId 멱등 idempotency

계좌마다 이미 반영한 tradeId 집합을 들고 있어, 같은 체결이 두 번 와도 한 번만 반영한다. 여기서도 그대로 재사용한다.

ACCOUNT_NOT_FOUND 격리 self-isolation

자기 샤드에 없는 계좌의 반영 요청이 오면 엔진이 조용히 거부한다. 남의 계좌를 잘못 건드리지 않게 하는 안전망.

④AS-IS — 지금은 한 곳에 한 번

매칭이 체결 하나를 fill 스트림에 1회 발행하고, 계좌 프로세스 하나가 매수·매도를 둘 다 반영한다.

체결 하나가 fill 스트림에 한 번 실려 오고, 계좌 프로세스 하나가 매수·매도 두 계좌를 같은 메모리에서 반영한다. 목적지가 하나라 라우팅이 필요 없다.

⑤TO-BE — 슬롯으로 계산해 두 목적지로

매칭이 매수·매도 accountId를 각각 슬롯으로 바꿔 목적지를 정하고, 같은 체결을 두 샤드에 보낸다. 각 샤드는 자기 소유 계좌만 반영하고 나머지는 격리한다.

매칭이 매수·매도 accountId를 슬롯으로 바꿔 목적지를 정하고, 같은 FilledTrade를 두 샤드에 unicast로 보낸다. 코덱은 그대로 두고, 반영 여부는 각 샤드의 소유 판정에 맡긴다.

⑥수신 모델 A — 같은 바이트, 각자 자기 것만

매칭은 목적지별로 내용을 다르게 만들지 않는다. 같은 FilledTrade를 두 샤드에 그대로 보내고, 각 샤드가 publishBuyFill·publishSellFill을 둘 다 호출한다. 자기 샤드에 있는 계좌만 반영되고 없는 계좌는 ACCOUNT_NOT_FOUND로 거부된다. 코덱에 방향 표시나 분리 레코드를 넣지 않아 FillCodec이 그대로 남는다.

같은 샤드에 매수·매도가 같이 있는 경우. 슬롯 계산 결과 두 계좌의 목적지가 같으면 같은 체결이 그 샤드에 두 번 도착한다. 계좌마다 이미 반영한 tradeId를 들고 있어 두 번째는 그냥 무시된다(processedTradeIds). 발행 쪽에서 목적지가 같으면 한 번만 보내는 최적화도 가능하지만, 두 번 보내도 멱등이 흡수하므로 라이브 경로의 정합성에는 영향이 없다.

⑦고쳐야 할 곳 = LLD 유닛 후보

위 흐름을 실제 코드로 옮기면 손대는 곳은 네 군데다. 아래를 LLD 단위로 잡을 생각이다(확정 전 초안).

  1. 라우팅 테이블 (신규) — hash(accountId) % P로 슬롯을 내고, 슬롯을 목적지 Aeron endpoint로 잇는 정적 표. 슬롯 수 P와 표 형식(config)을 정한다. core 또는 공용 위치 · matching-worker가 참조
  2. 매칭 발행 (변경) — AccountFillPublisher.onFill이 단일 Publication에 1회 offer하던 것을, 라우팅 테이블로 매수·매도 목적지를 계산해 목적지별 Publication에 각각 offer하도록 바꾼다. never-drop·재시도 정책은 유지. matching-worker/.../messaging/AccountFillPublisher · MatchingFillPublishConfig
  3. 수신 구독 (변경) — 지금은 모든 워커가 공유 스트림(6001)을 구독한다. 샤드별 endpoint로 나눠 각 샤드가 자기 목적지만 구독하게 한다. 반영 로직(buy+sell 둘 다 시도 + NOT_FOUND 격리)은 그대로 재사용. account-worker/.../config/AccountFillIntakeConfig · AccountFillReceiver
  4. 로컬 크로스샤드 검증 — account-worker를 두 샤드로 띄워(매수 90001 / 매도 90002 각각 다른 프로세스) 체결 한 건이 두 프로세스에 각각 반영되는지 확인한다. U3b 데모 시드를 두 샤드로 나누는 형태. application-udp.yml 계열 · seed 분할
