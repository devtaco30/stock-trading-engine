v1 병목 진단과 매칭 엔진 설계 코드 리뷰로 잔고 처리의 병목 일곱 개를 정리하고, 종목별 단일 스레드 매칭 엔진을 설계한 기록

매수 주문을 받을 때 계좌에서 돈이 바로 나가지는 않는다. 주문 금액에 증거금률을 곱한 만큼을 예약 증거금으로 기록해 두고, 그만큼 출금 가능 금액이 줄어든다. 실제 차감은 체결과 결제 단계에서 일어난다. 그런데 같은 계좌에 주문이 동시에 들어오면 두 요청이 같은 잔고를 근거로 검증을 통과할 수 있다. v1은 계좌 행에 SELECT FOR UPDATE를 걸어, 한 계좌의 쓰기가 한 번에 하나씩만 실행되게 했다. 이 문서는 그 락이 어디에서 얼마나 잡히는지를 코드로 훑어 병목을 정리하고, 매칭을 DB 대신 메모리에서 하도록 설계한 기록이다. 여기서 정리한 병목이 이후 v1의 Kafka 파이프라인 전환과 v2 엔진 설계의 출발점이 됐다.

이 문서가 적는 것은 Kafka 도입 전 상태다. 진단 대상은 당시의 main과 매칭 기능 브랜치 둘(feature/order-matching·feature/order-api-matching)이고, 두 브랜치는 이후 main에 병합했다. 병목 일곱 개가 지금 어떻게 됐는지는 마지막 절에 표로 정리했다.

먼저 용어

비관적 락 (pessimistic lock)행을 읽을 때 SELECT ... FOR UPDATE로 잠가, 트랜잭션이 끝날 때까지 다른 트랜잭션이 그 행을 건드리지 못하게 하는 방식. 충돌이 잦은 곳에서 확실하지만, 잠근 동안 다른 요청은 기다린다.
TOCTOU (time-of-check to time-of-use)값을 확인한 시점과 그 값을 사용하는 시점이 벌어져, 그 사이에 값이 바뀌면 낡은 값으로 판단하게 되는 문제. 잔고를 락 없이 먼저 읽고 나중에 락을 잡으면 여기에 해당한다.
Single Writer Principle하나의 데이터를 오직 한 스레드만 수정하게 하는 설계 원칙. 수정하는 스레드가 하나뿐이면 자료구조에 락을 걸 필요가 없다. 여기서는 같은 종목의 주문을 항상 같은 스레드가 처리한다.
호가창 (order book)아직 체결되지 않은 매수·매도 주문을 가격별로 모아 둔 자료구조. 매수 호가는 높은 가격부터 꺼내고 매도 호가는 그 반대다. 같은 가격 안에서는 들어온 순서를 지킨다.
Lazy Removal취소된 주문을 그 자리에서 빼지 않고 취소 표시만 해 두었다가, 다음 체결 직전에 큐 앞쪽부터 한꺼번에 걷어내는 방식.
afterCommitSpring이 트랜잭션 커밋을 끝낸 뒤 실행해 주는 콜백. 커밋 전에 다른 스레드로 일을 넘기면 그 스레드가 아직 없는 데이터를 조회하게 되므로, 넘기는 시점을 커밋 뒤로 미룰 때 사용한다.

진단 시점의 구조

모듈은 의존 순서대로 일곱 개였고, 주문 한 건이 api에서 들어와 trading과 account를 거쳐 settlement로 갔다.

모듈역할
coreSnowflake ID 생성, 공통 DTO(ApiResponse·PagedResponse)
userUser 엔티티, Redis 불투명 토큰 인증(SHA-256 키, 7일 TTL)
marketStock·Quote 엔티티. 종목 마스터는 정적이고 실시간 피드는 없다
account계좌와 보유 종목의 생명주기, 비관적 락 기반 잔액 관리
trading주문 접수(PENDING·FILLED·CANCELLED), 증거금 예약, 인메모리 호가창
settlementT+2 미수금 추적, 변제 처리, 체결의 DB 반영
apiHTTP 컨트롤러, 서비스 오케스트레이션, 파사드, 인증 인터셉터

인프라는 PostgreSQL 16(주 DB) · Redis 7(토큰 저장 전용) · H2(로컬 개발 기본값)였다. 메시지 큐는 이 시점에 없었고, 매칭 엔진을 메모리에 올린 뒤 Kafka를 도입하는 순서로 갔다.

병목

일곱 개를 찾았고, 그중 가장 크게 잡히는 것이 계좌 행 락이 잡혀 있는 구간이었다. 매수 주문 접수·입금·출금·변제가 전부 같은 계좌 행에 SELECT FOR UPDATE를 건다. 그래서 같은 계좌에 요청이 동시에 오면 읽기를 포함한 모든 쓰기가 한 줄로 선다. 아래 그림이 주문 한 건이 그 락을 언제 잡고 언제 놓는지, 그리고 잔고 검증이 락 밖에서 일어나 생기는 창이 어디인지다.

주문 한 건이 계좌 행 락을 잡는 구간
트랜잭션이 열리고 닫히기까지 무엇을 하는지, 락을 잡기 전에 읽은 값이 왜 문제가 되는지

이 그림은 진단 시점의 OrderApiService.placeBuyOrder를 따라 그린 것이다. 지금 코드는 미수금 조회가 락 획득 뒤로 옮겨져 TOCTOU 구간이 없다(아래 상태 표 참고).

나머지 병목

  • 매수 체결이 보유 종목을 락 없이 갱신한다. addHoldingOrIncreaseQuantity가 일반 조회로 보유 종목을 읽어 평균 단가와 수량을 고친다. 같은 계좌·종목에 체결이 동시에 들어오면 두 갱신이 서로를 덮어쓴다. 매도 체결이 호출하는 decreaseHolding은 비관적 락을 사용하고 있어 두 경로가 서로 달랐다.
  • 매칭이 DB 위에서 동기로 돈다. runMatch가 주문 접수 트랜잭션 안에서 실행돼, 매칭이 실패하면 주문 저장까지 롤백된다. 매칭 루프는 한 번 돌 때마다 DB 쿼리를 두 번 날린다. 매수와 매도가 동시에 들어오면 서로 다른 순서로 행을 잠가 데드락이 날 수 있다.
  • 트랜잭션 하나가 너무 많은 일을 덮는다. 소유권 확인부터 시세·증거금·미수금 조회, 락 획득, INSERT까지 한 트랜잭션에 들어 있다. 락 점유 시간과 DB 커넥션 점유 시간이 같이 늘어난다.
  • 커넥션 풀을 설정하지 않았다. spring.datasource.hikari.*가 없어 HikariCP 기본값인 최대 10개로 돈다. 비관적 락을 사용하는 상태에서 동시 요청이 늘면 풀이 비어 요청이 타임아웃된다.
  • 계좌 상세 조회가 매번 전부 집계한다. AccountReadFacade.getAccountDetail이 요청마다 보유 종목 전체와 종목별 시세, 예약증거금 합계, 미수금 합계를 모아 계산한다. 보유 종목이 많은 계좌일수록 느려진다.

매칭 엔진 설계

위 병목 중 매칭이 DB 위에서 도는 문제를 먼저 처리했다. 호가창을 메모리에 올리고, 같은 종목의 주문을 한 스레드가 전담하게 했다. 이때 정한 구조는 Kafka로 옮긴 뒤에도, v2 엔진에서도 그대로 사용된다.

Single Writer와 호가창 구조
종목마다 스레드를 하나씩 두어 락을 없애고, 그 스레드 안에서 호가창을 어떻게 들고 있는지

자료구조를 이렇게 고른 이유

// 매수는 높은 가격이 먼저다
TreeMap<BigDecimal, Deque<OrderEntry>> bids = new TreeMap<>(Comparator.reverseOrder());

// 매도는 낮은 가격이 먼저다
TreeMap<BigDecimal, Deque<OrderEntry>> asks = new TreeMap<>();

// 취소를 O(1)에 처리하려고 orderId로 엔트리를 역참조한다
Map<Long, OrderEntry> orderIndex = new HashMap<>();
자료구조고른 이유
TreeMap넣을 때마다 정렬이 유지되므로 최우선 호가를 firstEntry()로 O(log n)에 꺼낼 수 있다.
Deque<OrderEntry>같은 가격 안에서 먼저 들어온 주문이 먼저 체결돼야 한다. 뒤에 넣고(addLast) 앞에서 꺼내는(pollFirst) 것이 둘 다 O(1)이다.
HashMap (orderIndex)취소 요청은 orderId만 들고 온다. 가격을 모르는 상태에서 엔트리를 O(1)에 찾으려고 둔다.

취소된 주문을 바로 빼지 않는 이유

취소된 주문을 큐 중간에서 즉시 제거하면 Deque를 앞에서부터 훑어야 해서 O(n)이 든다. 그래서 cancel()은 표시만 남기고, 체결을 시작하기 직전에 drainInvalid()가 큐 앞쪽의 취소된 엔트리를 한꺼번에 걷어낸다. 유효한 엔트리를 만나면 멈춘다. 큐 중간에 남은 취소분은 그 자리가 앞으로 올 때 정리된다.

커밋이 끝난 뒤에 매칭 스레드로 넘기는 이유

주문을 저장한 트랜잭션이 커밋되기 전에 매칭 스레드로 넘기면, 그 스레드가 체결을 처리하면서 DB에서 주문을 조회할 때 아직 없는 행을 찾게 된다. 그래서 TransactionSynchronizationManager의 afterCommit 콜백에 제출을 걸어, 커밋이 끝난 뒤에 넘긴다.

// 커밋 전에 넘기면
INSERT Order  (아직 커밋 안 됨)
  └─ submitOrder() → 매칭 스레드 → 체결 처리 → DB에서 Order 조회 → 찾지 못한다

// 커밋 뒤에 넘기면
INSERT Order → 커밋 → submitOrder() → 매칭 스레드 → DB에서 Order 조회 → 있다

모듈 사이 의존을 이벤트로 끊은 이유

trading이 체결 결과를 settlement에 직접 넘기면 두 모듈이 서로를 참조하게 된다. 그래서 trading은 OrderFilledEvent를 발행만 하고, settlement의 MatchingFillHandler가 그 이벤트를 구독한다. trading은 settlement를 모르고, settlement는 이벤트 클래스만 안다.

Kafka로 옮길 때 무엇이 바뀌었나

메모리 큐를 Kafka로 바꿀 때 호가창 로직은 그대로 두었다. 바뀐 것은 주문이 어디에 쌓이는가와, 같은 종목을 한 스레드가 맡는 것을 무엇이 보장하는가다.

인메모리 큐에서 Kafka 파티션으로
같은 종목을 한 스레드가 처리한다는 보장을 무엇이 맡는지가 바뀌었다

이 진단 이후 병목이 어떻게 됐나

아래 상태는 지금 코드를 직접 확인해 적었다.

병목지금확인한 것
매칭이 DB 위에서 동기로 돈다해소호가창을 메모리에 올리고 주문 접수 트랜잭션에서 떼어냈다. 이후 Kafka 컨슈머로, v2에서는 Disruptor 링버퍼로 옮겼다.
매수 체결이 보유 종목을 락 없이 갱신한다해소AccountService.addHoldingOrIncreaseQuantity가 findByAccount_IdAndStockCodeForUpdate로 잠그고 갱신한다.
잔고 검증이 락 밖에서 일어난다 (TOCTOU)해소OrderWriter.writeBuyOrder가 계좌 행을 잠근 뒤에 미수금 합계를 조회한다.
트랜잭션 하나가 너무 많은 일을 덮는다좁혔다주문 접수를 오케스트레이터와 OrderWriter로 나눠, 트랜잭션이 저장 구간만 덮는다(ADR-008 「주문 접수 멱등키를 requestId로 교체」).
계좌 행 락 경합v1에 남음v1은 여전히 계좌 행을 잠근다. v2는 계좌를 메모리에서 단일 스레드로 처리해 이 락 자체를 없앴다(ADR-014 「계좌 단일 스레드 워커」).
커넥션 풀 미설정그대로레포의 yml에 hikari 설정이 없다. 기본값으로 돈다.
계좌 상세 조회가 매번 전부 집계한다그대로캐시를 두지 않았다(@Cacheable 없음). v2는 계좌 상태를 메모리에 들고 있어 이 조회 자체가 다른 경로로 바뀐다.
이 문서가 v2로 이어지는 지점. v1에서 계좌 행 락은 잔고 규칙을 지키는 수단이면서 처리 속도의 한계선이기도 했다. v2는 계좌 하나를 스레드 하나가 전담하게 해서 같은 규칙을 락 없이 지킨다. 매칭에서 쓴 Single Writer를 계좌에 그대로 적용했다.
이 문서는 코드 리뷰 기록이라 진단 시점의 코드를 기준으로 서술한다. 마지막 절의 상태만 현재 코드를 확인해 적었다.
