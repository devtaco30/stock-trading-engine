주식 매매 엔진 · 문서

증권 계좌 도메인(증거금 검증 · T+2 결제 · 미수금)을 다루는 Java 매매 엔진입니다. 같은 시나리오를 두 가지 방법론으로 구현했습니다.

v1은 DB 비관적 락으로 정합성을 지킵니다. v2는 그 락을 걷어내고 계좌 상태를 프로세스 메모리에 둔 뒤 단일 스레드에서만 다룹니다. 두 구현이 무엇을 얻고 무엇을 대가로 치렀는지가 이 문서들의 내용입니다.

코드와 결정 기록: github.com/devtaco30/stock-trading-engine

먼저 읽을 것

배경

구조 문서에 나오는 도메인 용어와 숫자가 어디서 오는지 먼저 정리합니다.

도메인 기본 개념

증거금·미수금·T+2 결제가 각각 무엇이고 계좌 잔고를 어떻게 움직이는지 설명합니다.

시나리오

100주 매수 한 건을 따라가며 주문 접수부터 정산까지 숫자가 어떻게 달라지는지 계산합니다.

v1 — DB 락과 Kafka로 만든 구성

v1

계좌 행에 비관적 락을 걸어 정합성을 지키고, 주문과 체결을 Kafka로 넘깁니다.

구조 정본

프로세스 넷과 토픽 셋이 무엇을 맡는지, 상태를 어디에 두고 락을 어디서 잡는지, 그 대가로 처리량과 지연이 어떻게 되는지를 한 장에 담았습니다.

주문에서 체결, 정산까지

주문 한 건이 접수돼 체결되고 이틀 뒤 정산되기까지 어느 프로세스를 어떤 순서로 지나는지 따라갑니다.

Kafka 내부 동작

파티셔너가 종목을 어느 파티션으로 보내는지, 오프셋 커밋과 리밸런스가 매칭 결과에 어떻게 영향을 주는지 설명합니다.

병목 분석

계좌 행 락이 어디서 걸려 무엇을 붙잡는지 짚고, 그 구간을 어떻게 줄일 수 있는지 따집니다.

v2 — 메모리 단일 스레드와 Aeron으로 만든 구성

v2

락을 걷어낸 대신 상태를 메모리에 두고, 잃어버리지 않기 위해 저널과 스냅샷을 씁니다.

구조 정본

계좌와 매칭을 각각 한 스레드가 독점 처리하는 구성과, 그 상태를 디스크에 남겨 재시작 때 되살리는 방법을 담았습니다.

링버퍼 매칭

매칭 코어가 이벤트를 어떤 순서로 집어 처리하는지, 링버퍼가 큐 대신 쓰이는 이유가 무엇인지 설명합니다.

체결 전달 분리

체결 한 건이 매수·매도 두 계좌를 건드리기 때문에 같은 체결을 두 목적지로 나눠 보냅니다. 중복 도착은 tradeId로 걸러냅니다.

스냅샷과 tradeId 삭제

재시작 복구 시간과 메모리 사용량이 서로 맞물려 있습니다. 주기 스냅샷과 오래된 tradeId 삭제로 그 둘을 함께 묶어 두는 방법을 다룹니다.

정산 왕복

정산만 Kafka로 남긴 이유와, 계좌 워커가 가져간 책임이 무엇인지 설명합니다.

v1과 v2 비교

비교

무엇을 무엇으로 바꿨고, 같은 부하에서 용량과 지연이 어떻게 달라졌는지입니다.

v1에서 v2로

어느 부분을 무엇으로 바꿨는지 AS-IS와 TO-BE로 나란히 놓았습니다.

두 구현 비교

같은 시나리오에서 두 구현이 무엇을 다르게 하는지와, 그 선택이 지연과 정합성에 미치는 영향을 정리했습니다.

처리량 측정 결과

도착률을 올려 가며 두 구현이 어디까지 받아내는지 측정한 결과입니다.

부하 측정 리포트

측정을 어떻게 설계했고 무엇을 어떻게 기록했는지, 그리고 결과를 어떻게 읽어야 하는지 담았습니다.

결정 근거는 레포의 adr/에 번호로 남겨 두었습니다. 작업하면서 남긴 검토 기록은 decision_records/에 있습니다.
