주문 접수부터 체결 반영까지 v1에서 프로세스 넷과 Kafka 토픽 셋이 주문 한 건을 나눠 처리하는 순서, 그리고 같은 메시지가 두 번 전달돼도 결과가 같게 만든 장치

사용자가 주식을 사겠다고 요청해도 그 자리에서 거래가 끝나지는 않는다. 사려는 가격과 팔려는 가격이 맞아야 체결되고, 체결된 뒤에도 대금이 한 번에 빠져나가지 않는다. 한국 주식시장은 체결일에서 이틀 뒤에 대금을 결제하고(T+2), 그 사이 금액은 계좌의 빚으로 남는다. v1은 이 과정을 프로세스 넷에 나눠 맡겼다. 주문을 받는 api, 잔고를 검증하고 주문 행을 저장하는 order-engine, 호가창에서 짝을 찾는 matching-engine, 체결을 DB에 반영하는 settlement-engine이다. 넷은 서로를 직접 호출하지 않고 Kafka 토픽으로만 연결된다. 이 문서는 주문 한 건이 그 넷을 지나는 동안 어디에서 무엇이 저장되고 무엇이 발행되는지를 순서대로 적은 것이다.

이 문서가 다루는 것은 v1이다. 잔고는 PostgreSQL 행에 두고 비관적 락으로 지키며, 프로세스 사이 전달은 Kafka가 맡는 구성이다. 같은 도메인을 메모리 단일 스레드와 Aeron으로 다시 만든 v2 엔진은 여기서 다루지 않는다.

먼저 용어

증거금률과 예약 증거금매수 주문을 받을 때 주문 금액 전부를 차감하지 않고, 주문 금액에 증거금률을 곱한 만큼만 예약 증거금으로 잡아 둔다. 그만큼 출금 가능 금액이 줄어들고, 남은 금액은 결제일에 낸다.
미수금 (Unpaid)매수가 체결됐지만 아직 내지 않은 대금. 체결 금액에서 증거금으로 낸 몫을 뺀 값이다. 정산 예정일을 이틀 뒤(T+2)로 적어 두고, 변제하면 SETTLED로 바뀐다.
호가창 (order book)아직 체결되지 않은 매수·매도 주문을 가격별로 모아 둔 자료구조. 매수 호가는 높은 가격부터, 매도 호가는 낮은 가격부터 꺼낸다. 같은 가격 안에서는 먼저 들어온 주문이 먼저 체결된다.
파티션 키 (partition key)Kafka 토픽은 파티션 여러 개로 나뉘고, 메시지를 보낼 때 함께 주는 키의 해시로 어느 파티션에 들어갈지가 정해진다. 같은 키의 메시지는 항상 같은 파티션에 들어가 순서가 유지된다.
at-least-onceKafka 컨슈머가 메시지를 처리한 뒤에 처리 완료 위치를 기록(ack)하는 방식. 처리는 끝났는데 기록 전에 프로세스가 죽으면 같은 메시지가 다시 전달된다. 중복 전달을 전제로 소비하는 코드를 짜야 한다.
멱등 (idempotent)같은 요청을 여러 번 처리해도 결과가 한 번 처리한 것과 같은 성질. 여기서는 요청마다 붙는 멱등키를 저장해 두고, 같은 키가 다시 오면 처리를 건너뛰는 방식으로 만든다.
비관적 락 (pessimistic lock)SELECT ... FOR UPDATE로 행을 잠가, 트랜잭션이 끝날 때까지 다른 트랜잭션이 그 행을 건드리지 못하게 하는 방식. 확실한 대신 잠근 동안 다른 요청은 기다린다.
202 Accepted요청을 접수했고 처리는 아직 끝나지 않았다는 뜻의 HTTP 응답 코드. 이 응답을 받은 시점에는 주문 행이 아직 DB에 없다. 결과는 주문 내역 조회로 확인한다.

주문 한 건이 지나는 길

아래 그림이 전체 경로다. 세로로 놓인 네 칸이 단계이고, 칸 안에서 위에서 아래로 내려가며 Kafka 토픽에서 프로세스로, 프로세스에서 저장소로 이어진다. 다음 단계로 넘어가는 화살표는 오른쪽 칸의 토픽으로 올라간다.

접수부터 체결 반영까지
프로세스마다 무엇을 읽고 무엇을 저장하는지, 다음 단계로 무엇을 어떤 키로 발행하는지
API 서버 주문을 처리하는 프로세스 Kafka 토픽 저장소 시스템 밖 주문이 지나는 주 경로 저장소로 나가는 쓰기

토픽 이름은 order-requests·orders·fills 셋이고, 종목마다 토픽을 따로 만들지 않는다. 종목 구분은 파티션 키가 맡는다.

api가 하는 일은 여기까지다
  • 계좌가 요청한 사용자의 것이고 ACTIVE 상태인지 잠금 없이 읽어 확인한다.
  • 주문 가격이 기준가의 ±30% 안인지 본다. 기준가는 Redis의 최근 체결가이고, 없으면 전일 종가를 사용한다.
  • 잔고 검증은 하지 않고 넘긴다. 그래서 202로 답한 시점에는 주문 행이 아직 없다.
잔고를 지키는 자리와 속도를 내는 자리
  • order-engine은 계좌 행을 잠근 뒤에 미수금과 예약 증거금 합계를 읽는다. 잠그기 전에 읽으면 낡은 값으로 검증이 통과한다.
  • matching-engine은 DB를 쓰지 않는다. 호가창이 메모리에 있고 그 종목을 고치는 스레드가 하나뿐이라 자료구조에 잠금이 없다.
  • 주문 상태와 보유 수량은 settlement-engine에서만 바뀐다.
파티션 키가 중간에 바뀐다
  • order-requests의 키는 계좌 번호여서 같은 계좌의 요청이 한 스레드에 모인다.
  • orders부터는 키가 종목 코드다. 한 종목의 매수와 매도가 같은 스레드로 들어와야 서로 체결될 수 있다.
  • 파티션 수는 order-requests가 3개, orders와 fills가 각각 50개다.

각 단계가 하는 일

1. api — 검증을 둘로 나눈 기준

API 서버가 하는 검증은 두 가지다. 계좌가 요청한 사용자의 것이면서 ACTIVE 상태인지 보고, 주문 가격이 기준가의 ±30% 안인지 본다. 기준가는 Redis에 저장된 최근 체결가를 먼저 사용하고, 그 종목에 아직 체결이 없으면 전일 종가를 사용한다. 둘 다 없는 종목이면 존재하지 않는 종목으로 보고 거절한다.

잔고가 충분한지는 여기서 보지 않는다. 잔고를 제대로 보려면 계좌 행을 잠가야 하고, 그러면 API 서버가 DB 락을 들고 있게 된다. v1에서는 그 검증을 order-engine으로 미뤘고, API 서버는 상태를 들고 있지 않은 채 요청을 받아 넘기는 일만 한다(ADR-004 「API를 상태 없이 두고 주문 처리를 Kafka 파이프라인으로 옮긴다」). 그래서 응답이 202 Accepted다. 사용자는 이 응답만으로 주문이 성립했는지 알 수 없고, 주문 내역 조회로 확인해야 한다.

멱등키도 이 단계에서 정해진다. 클라이언트가 requestId를 보내면 그 값을 그대로 쓰고, 비어 있으면 서버가 UUID를 만들어 붙인다. 이 값이 주문 행의 request_id 컬럼까지 그대로 따라간다.

2. order-engine — 잠근 뒤에 읽는 순서

여기서 주문 행이 처음 DB에 생긴다. 매수 주문의 처리 순서는 이렇다.

// OrderWriter.writeBuyOrder — 트랜잭션 하나
1. 계좌 행 잠금        SELECT ... FOR UPDATE
2. 미수금 합계 조회    (잠근 뒤에 읽는다)
3. 예약 증거금 합계     SELECT SUM(reserved_margin) ...  주문을 하나씩 세지 않고 DB가 더한다
4. 출금 가능 금액 = 잔고 - 예약 증거금 합계 - 미수금 합계
5. 매수 한도 = 출금 가능 금액 / 증거금률
6. 주문 금액 > 매수 한도 이면 거절
7. Order INSERT (PENDING, reservedMargin)

2번이 1번보다 뒤에 있는 것이 중요하다. 잠그기 전에 미수금을 읽으면, 읽은 시점과 그 값을 사용하는 시점 사이에 다른 트랜잭션이 미수금을 바꿔도 검증은 바뀌기 전 값으로 통과한다. 3번을 SUM 쿼리로 둔 것은 락을 잡고 있는 시간을 줄이기 위해서다. 미체결 매수 주문을 전부 읽어 애플리케이션에서 더하면 그동안 계좌 행이 계속 잠겨 있다.

매도 주문에서는 보유 종목 행을 잠근다. 보유 수량만 보면 100주를 가진 계좌가 100주 매도 주문을 여러 건 넣을 수 있으므로, 보유 수량에서 이미 접수된 미체결 매도 잔량을 뺀 값을 가용 수량으로 삼는다(ADR-009 「매도 주문도 매수의 증거금 예약처럼 가용 수량을 따로 계산한다」). 매수의 예약 증거금과 같은 역할을 매도에서 하는 값이다.

취소 요청은 주문 상태를 CANCELLED로 바꾸고 예약 증거금을 null로 되돌린다. 잡아 두었던 금액이 풀리면서 출금 가능 금액이 그만큼 늘어난다.

3. matching-engine — 호가창에서 체결을 판정한다

주문을 받으면 가격별 큐의 뒤에 넣고, 체결이 나오지 않을 때까지 판정을 반복한다. 판정은 가장 높은 매수 호가와 가장 낮은 매도 호가를 꺼내 비교하는 것이다.

// OrderBook.match() — 한 번 호출에 한 건
bestBid = bids.firstEntry()   // TreeMap 역순 정렬 → 높은 가격이 앞
bestAsk = asks.firstEntry()   // TreeMap 정순 정렬 → 낮은 가격이 앞

if (bestBid < bestAsk) 체결 없음

체결가 = bestAsk                                매도 호가를 사용한다
체결량 = min(매수 남은 수량, 매도 남은 수량)     부분 체결이 된다
전량 체결된 주문은 큐와 orderIndex 에서 바로 제거

취소된 주문은 큐 중간에서 즉시 빼지 않는다. ArrayDeque 중간을 삭제하려면 앞에서부터 훑어야 해서 O(n)이 든다. 취소 요청은 orderIndex에서 O(1)에 찾아 취소 표시만 남기고, 체결 판정 직전에 큐 앞쪽에 쌓인 취소분을 한꺼번에 걷어낸다. 자료구조를 이렇게 고른 근거는 ADR-006 「호가창을 TreeMap·Deque·HashMap 조합으로 구성한다」에 적혀 있다.

체결이 나면 최근 체결가를 Redis에 쓰고, 호가 10단계 스냅샷도 함께 저장한다. 조회 API가 호가창을 보려고 매칭 프로세스에 묻지 않고 Redis를 읽게 하기 위한 것이다. 주문 상태와 보유 수량은 여기서 바꾸지 않는다.

4. settlement-engine — 체결 한 건이 바꾸는 것

체결 이벤트 하나가 한 트랜잭션에서 세 가지를 바꾼다.

바뀌는 것내용
주문매수·매도 양쪽 주문의 누적 체결 수량을 올린다. 주문 수량을 다 채우면 상태가 FILLED로 바뀌고 체결 시각이 기록된다.
보유 종목매수자의 보유 행을 잠그고 수량을 더하면서 평균 단가를 다시 계산하며, 매도자의 보유 수량은 그만큼 줄인다.
미수금체결 금액 × (1 − 증거금률)을 미수금으로 만들고, 정산 예정일을 체결일에서 이틀 뒤로 적는다. 상태는 PENDING이다.

매수 반영과 매도 반영이 같은 트랜잭션 안에 있다. 매수자의 보유만 늘고 매도자의 보유는 그대로인 상태가 DB에 남지 않는다.

파티션 키가 중간에 바뀌는 이유

같은 주문이 order-requests와 orders 두 토픽을 지나는데, 두 토픽의 파티션 키가 다르다. 계좌 번호로 시작해서 종목 코드로 바뀐다. 아래 그림은 주문 세 건이 그 두 토픽을 지나며 어느 스레드로 들어가는지를 따라간 것이다.

두 토픽의 파티션 키
단계마다 동시에 갱신되면 곤란한 대상이 달라지므로, 키도 그에 맞춰 달라진다
접수된 주문 Kafka 파티션 컨슈머 스레드 주문 A와 B가 지나는 경로 주문 C가 지나는 경로

주문 A와 주문 B는 계좌가 같아서 앞 구간에서 한 파티션에 모이고, 종목도 같아서 뒤 구간에서도 한 파티션에 모인다. 주문 C는 계좌와 종목이 모두 달라 두 구간 모두 다른 파티션으로 들어간다.

계좌 번호를 키로 삼는 구간
  • 같은 계좌의 요청이 한 파티션에 모이고, 한 파티션은 컨슈머 한 스레드가 맡는다.
  • 그래서 계좌 7번의 두 요청은 앞의 것이 끝난 뒤에 뒤의 것이 처리된다.
  • DB 락을 없앤 것은 아니다. 같은 계좌 행을 두 스레드가 동시에 잠그려는 상황을 줄인 것이다.
종목 코드로 키를 다시 정하는 이유
  • 매칭에서 동시에 갱신되면 곤란한 것은 종목마다 하나씩 있는 호가창이다.
  • 계좌 번호를 그대로 사용하면 같은 종목의 매수와 매도가 서로 다른 스레드로 가서 체결될 수 없다.
  • 그래서 order-engine이 다음 토픽에 발행할 때 키를 종목 코드로 바꿔 붙인다.
이 방식이 치르는 대가
  • 토픽 하나를 파티션 50개로 나눠 쓰므로 종목 여럿이 같은 파티션을 공유한다.
  • 한 종목의 처리가 느려지면 같은 파티션에 실린 다른 종목의 주문도 뒤에서 기다린다.
  • 종목마다 토픽을 만들면 이 간섭이 없지만 토픽이 수천 개가 되어 운영이 어려워진다. 그래서 단일 토픽 파티션 분할을 택했다(ADR-011 「종목별 토픽을 토픽 하나와 파티션 50개로 바꾼다」).

같은 메시지가 두 번 전달돼도 결과가 같게 만든 세 자리

세 컨슈머는 모두 처리를 끝낸 뒤에 위치를 기록하는 방식(at-least-once)으로 돈다. 처리는 됐는데 기록 직전에 프로세스가 죽으면 같은 메시지가 다시 전달된다. 그래서 단계마다 중복을 판정할 근거를 따로 저장해 둔다.

중복 전달을 거르는 지점
단계마다 무엇을 근거로 이미 처리했다고 판정하고, 판정이 맞으면 무엇을 하지 않는지
중복인지 판정하는 지점 실제로 상태를 바꾸는 처리 아무것도 바꾸지 않고 끝나는 경우 처음 보는 메시지일 때 이미 처리한 메시지일 때
판정 근거를 어디에 두었나
  • order-engine은 orders 테이블의 request_id 컬럼에 UNIQUE를 걸어 두고 그 값을 본다.
  • matching-engine은 호가창의 orderIndex와, 전량 체결된 주문의 체결 시각 기록을 본다. 둘 다 메모리에 있다.
  • settlement-engine은 processed_fills 테이블에 남긴 tradeId를 본다.
주문 상태만 보고는 거를 수 없다
  • 부분 체결된 주문은 상태가 여전히 PENDING이다.
  • 그래서 상태만 검사하면 이미 반영한 부분 체결 이벤트가 다시 들어왔을 때 그 검사를 통과한다.
  • 그러면 누적 체결 수량과 보유 수량, 미수금이 한 번 더 더해진다. 체결 단위로 tradeId를 발급해 따로 기록해 두는 이유가 이것이다(ADR-007 「체결마다 tradeId를 발급해 반영 여부를 기록한다」).
저장 위치가 서로 다르다
  • 주문 접수의 근거는 DB 컬럼에 있어 프로세스가 재시작해도 남는다.
  • 매칭의 근거는 메모리에 있어 재시작하면 사라진다. 호가창 자체가 메모리에 있기 때문이다.
  • 메모리에 둔 체결 기록에는 5,000건과 5분이라는 상한을 걸어 두어, 오래된 것부터 버려지게 했다.

주문 저장 단계에서는 조회로 먼저 거르고, 그 조회를 두 요청이 동시에 통과하는 경우에만 request_id UNIQUE가 뒤의 INSERT를 막는다. 이때는 먼저 저장된 주문을 새 트랜잭션으로 다시 읽어 반환한다. 롤백된 트랜잭션을 그대로 재사용하면 조회가 되지 않기 때문에 저장과 복구 조회를 다른 빈으로 나눠 두었다(ADR-008 「주문 접수 멱등키를 requestId로 바꾼다」).

이 구성에서 열려 있는 것

  • 주문 저장 단계에서 미수금 합계를 0으로 놓고 계산한다. order-engine은 모듈 의존 방향 때문에 settlement 모듈을 참조할 수 없어, 미수금 공급자가 항상 0을 돌려준다. 미수금이 남아 있는 계좌에서는 매수 한도가 실제보다 크게 나온다. 코드에는 이 자리를 서비스 사이 트랜잭션 설계와 함께 다룰 대상으로 표시해 두었다.
  • 미수금 변제는 사용자가 상환 API를 호출해야 이뤄진다. 체결 시점에 정산 예정일을 이틀 뒤로 적어 두지만, 그 날짜가 지났다고 잔고에서 자동으로 차감하는 경로는 v1에 없다. 예정일을 스캔해 처리하는 스케줄러는 v2 구성인 settlement-worker에 있다.
  • 호가창은 matching-engine 프로세스의 메모리에만 있다. 프로세스가 재시작하면 비어 있고, 되채울 재료는 DB에 PENDING으로 남은 주문과 각 주문의 누적 체결 수량이다.
  • 거절된 주문은 사용자에게 따로 알리지 않는다. 잔고 부족처럼 다시 시도해도 결과가 같은 실패는 로그를 남기고 폐기한다. 이미 202로 답한 뒤라 응답으로 알릴 수 없고, 사용자는 주문 내역에 그 주문이 없는 것으로 확인하게 된다.
이 구성이 v2로 이어지는 지점. v1에서 잔고를 지키는 수단은 계좌 행의 비관적 락이다. Kafka 파티션 키를 계좌 번호로 둬서 같은 계좌의 요청을 한 스레드에 모았지만, 잔고 검증은 여전히 DB를 왕복하면서 행을 잠근다. v2 엔진은 계좌 상태를 메모리에 올리고 계좌마다 스레드 하나가 전담하게 해서, 이 왕복과 행 잠금을 두지 않는다.
이 문서의 서술은 레포의 v1 경로 코드를 열어 확인한 것이다. 메모리 단일 스레드와 Aeron으로 다시 만든 v2 엔진 경로는 다루지 않는다. 도식은 Archify로 만들어 레이아웃 검사(showcase)를 통과시킨 뒤 이 문서의 색으로 맞춘 것이다.
