주식 거래 기본 개념 증거금·미수금·T+2 결제가 각각 무엇이고, 그중 어디까지가 이 프로젝트에 코드로 있는지

주식을 산다는 말은 거래가 체결되고 바로 등가 교환이 이루어 진다는 건 아니다. 한국 주식시장에서 매수 주문이 체결되면 거래 계약은 즉시 성립하지만, 주식과 대금의 실제 정산은 이틀 뒤에 이루어진다. 이처럼 정산까지 이틀의 유예가 있어서 체결 당시에 대금 전부가 있을 필요는 없다. 그래서 계약금처럼 일부만 먼저 내는 증거금, 그리고 나머지인 미수금이 있다.

이 문서는 본격적으로 다른 문서를 읽기 전, 핵심 개념을 먼저 파악하는 용도의 문서다.

실제 한국 주식시장의 메커니즘과 이 프로젝트에서 코드로 다루는 범위에는 차이가 있다. 도식의 회색 표시 및 '미구현' 문구는 실제 시장엔 있지만 코드로는 구현하지 않은 영역이다. 이번 프로젝트의 목적은 매칭과 계좌 처리를 학습하는 것에 맞춰져 있어, 결제와 신용 거래는 필수적인 수준으로만 가볍게 구현했다.

먼저 용어

매수와 매도주식을 사는 주문이 매수, 파는 주문이 매도이며, 코드상에서는 OrderSide 타입의 두 값으로 표현된다. 매수 주문 시에는 계좌의 현금을, 매도 주문 시에는 보유 주식 수량을 담보로 잡는다.
호가와 체결호가는 사거나 팔겠다고 내놓은 가격이다. 매수 호가는 높은 값부터, 매도 호가는 낮은 값부터 우선순위를 가지며, 두 가격이 맞물리면 체결된다. 체결 건마다 고유한 tradeId가 발급된다.
지정가 주문 (LIMIT)가격을 적어서 내는 주문이다. 적은 가격보다 불리한 값에는 체결되지 않는다. 이 프로젝트의 매칭 엔진이 처리하는 주문은 이것뿐이다.
시장가 주문 (MARKET)가격을 적지 않고 지금 나와 있는 호가에 그대로 체결시키는 주문이다. OrderType에 값은 있지만 이 프로젝트의 주문 접수와 매칭 어디에도 이 값을 따로 다루는 코드가 없다.
증거금률 (marginRate)매수 주문 금액 중 지금 당장 내야 하는 비율을 뜻한다. 시장에선 종목별로 다르게 매기지만, 이 프로젝트는 계좌마다 Account.marginRate 컬럼 하나로 관리한다.
예약 증거금 (reservedMargin)주문 시점에 주문 금액 × 증거금률만큼을 그 주문 몫으로 잡아 두는 금액이다. 해당 주문이 체결되거나 취소되기 전까지 다른 주문에 사용할 수 없다.
미수금 (Unpaid)체결은 됐지만 아직 납부하지 않은 잔여 대금이다. 전체 체결 금액에서 선납한 증거금을 차감한 값이며, 결제 예정일(T+2)을 함께 기록한다. 이 미수금이 정상 정산(상환)되면 상태가 SETTLED로 변경된다.
T+2 결제체결한 날을 T라고 할 때 이틀 뒤에 대금이 실제로 계좌에서 빠져나가는 것을 말한다. 시장 전체가 같은 주기를 사용해서 투자자가 고를 수 없다.
출금 가능 금액계좌 잔고에서 예약 증거금 합계와 미수금 합계를 차감한 값이다. 지금 이 계좌에서 실제로 꺼낼 수 있는 현금이 얼마인지를 말한다.
매수 가능 금액출금 가능 금액을 증거금률로 나눈 값이다. 새 매수 주문의 금액이 이 값을 넘으면 주문을 거절한다.
대용가이미 갖고 있는 주식을 담보로 쳐서 매수 여력에 더해 주는 금액이다. 증권사는 보통 현재가의 일정 비율로 매긴다. 이 프로젝트의 매수 가능 금액 계산에는 이 항목이 들어가지 않는다.
반대매매미수금을 갚지 못한 계좌의 보유 주식을 증권사가 강제로 팔아 대금을 회수하는 것이다. 이 프로젝트에는 이 동작을 하는 코드가 없다.

매수 주문 결제 라이프사이클 (T ~ T+2)

매수 주문 한 건이 체결(T)되어 최종 결제(T+2)에 이르는 시퀀스다. 주문 접수 시 증거금을 묶고, 체결 시 미수금을 생성한 뒤, T+2 결제일에 잔고를 차감해 정산을 마친다. 아래 도식은 이 흐름을 3가지 시나리오로 구분한 것이다.

체결일부터 결제일까지
매수 주문 한 건에서 증거금·미수금·T+2 결제가 각각 언제 일어나는지, 그리고 그중 무엇이 이 프로젝트에 있는지
이 도식 열기
정상 결제 흐름 사전 상환 흐름 잔고 부족 / 반대매매 흐름

「변동 없음」은 계좌상 추가 처리가 없는 정산 대기 구간이다. 주식은 체결 당일 이미 입고 완료된 상태이며 대금만 미수금으로 유지된다.

「T+2 결제」 단계에서 이 프로젝트는 별도의 잔고 수량/금액 검증 없이 미수금 액수만큼 잔고에서 즉시 차감한다. 하단의 회색 노드 「미구현」은 실제 도메인에는 존재하지만 코드 구현에서는 제외된 상태를 나타낸다.

주문을 받을 때와 체결될 때 잔고에서 빠지는 금액이 다르다
  • 주문을 받을 때는 잔고가 줄지 않는다. 주문 금액에 증거금률을 곱한 금액을 예약 증거금으로 묶어 두기만 한다.
  • 체결될 때 그 예약 증거금이 실제로 잔고에서 빠지고, 체결 금액에서 그만큼을 뺀 나머지가 미수금으로 쌓인다.
  • 주문 하나가 여러 번에 걸쳐 체결되면 예약 증거금도 체결된 수량만큼씩 줄어든다. 줄어든 금액을 다 더했을 때 처음 묶은 금액과 원 단위까지 같아야 해서, 체결마다 다시 계산하지 않고 잔량 기준으로 다시 잡는다(ADR-015 「부분 체결 시 예약 장부를 잔량 기준으로 다시 계산」).
결제 워커(settlement-worker) 실제 동작 로직
  • settlement-worker가 일정 간격으로 결제 예정일이 지난 미수금을 찾아 정산한다. 이 프로젝트에서 @Scheduled가 붙은 모듈은 여기뿐이다.
  • 계좌 잔고에서 미수금 액수만큼 빼고, 그 미수금을 같은 금액만큼 상환 처리한다.
  • 같은 건을 두 번 정산하지 않으려고 이미 처리한 체결 번호를 기록해 두고 걸러낸다.
T+2 결제 주기 산정 로직의 한계 (영업일 미반영)
  • 실제 시장의 T+2 결제는 영업일 기준이므로 금요일 체결 건은 다음 주 화요일에 결제된다. 반면 이 프로젝트는 영업일 산정 달력이 존재하지 않아, 체결 시각에 단순 48시간을 더해 결제 예정일을 지정한다.
  • 영업일 계산 대신 주문 매칭과 계좌 처리를 보려고 정산 산식을 일부러 단순하게 두었다.

매수 가능 금액 계산

매수 주문이 들어오면 해당 계좌가 수량 및 금액을 감당할 수 있는지 매수 가능 금액을 통해 먼저 검증한다. 계산 시 계좌 잔고에서 미체결 매수 주문의 증거금과 미수금을 먼저 뺀 후, 해당 금액을 증거금률로 나눈다. 증거금률이 0.40인 경우 현금 1원당 최대 2.5원어치의 주문이 가능하다.

매수 가능 금액
계좌 잔고에서 무엇을 빼고 무엇으로 나눠서 주문 한 건을 받을지 정하는지
이 도식 열기
실제 연산 흐름 미구현 도메인 파이프라인

매수 가능 금액을 구하는 산식은 이 프로젝트의 3개 영역에 똑같이 들어가 있다.
v1 경로: 관계형 DB 계좌 행에 비관적 락을 걸고 처리하는 구간
v2 경로: 메모리에 둔 상태를 단일 스레드로 처리하는 구간
조회 API: 클라이언트 응답용 계좌 정보 산출 구간
세 영역 모두 동일한 수식(산식)을 공유한다.

숫자를 넣어 보면 이렇게 된다. 증거금률은 0.40이고, 이 계좌에는 아직 체결되지 않은 매수 주문도 갚지 않은 미수금도 없는 상태에서 시작한다.

# 주문을 내기 전
출금 가능 금액 = 1,000만원 - 0 - 0          = 1,000만원
매수 가능 금액 = 1,000만원 / 0.40           = 2,500만원

# 70,000원짜리 주식 100주를 매수 주문 = 700만원
700만원 <= 2,500만원                       -> 주문을 받는다
예약 증거금    = 700만원 x 0.40             =   280만원
출금 가능 금액 = 1,000만원 - 280만원         =   720만원
매수 가능 금액 = 720만원 / 0.40             = 1,800만원

# 100주가 전량 체결되면
잔고에서 빠지는 증거금 = 280만원             -> 잔고 720만원
미수금으로 쌓이는 대금 = 700만원 x 0.60      =   420만원
결제 예정일                                 = 체결 시각 + 48시간

# 결제일이 되면
잔고에서 빠지는 대금   = 420만원             -> 잔고 300만원, 미수금 0원

주문 접수 단계에서 주문 가격이 기준가 대비 ±30% 범위 이내인지 추가로 검증한다. 기준가는 최근 체결가를 우선 적용하며, 체결 이력이 없으면 전일 종가를 사용한다. 두 값 모두 조회되지 않는 종목은 존재하지 않는 종목으로 판단해 주문을 즉시 거절한다. 이 검증은 API 서버에서만 한다.

미구현 항목 및 도메인 제약 사항

앞에서 설명한 개념 가운데 실제 증권사에는 있지만 이 프로젝트에 구현하지 않은 것을 모았다.

도식과 소스코드를 대조할 때 헷갈리지 않도록 구현하지 않은 것을 밝혀 둔다.

  • 대용가와 매도 예정금액. 증권사의 매수 여력은 현금에 더해 보유 주식의 담보 가치와 팔기로 한 주식의 대금까지 합쳐서 나온다. 이 프로젝트의 매수 가능 금액은 현금에서 빼기만 하고 더하지 않는다. 계좌 조회 응답에 pendingSellAmount 항목이 있기는 하지만 값은 언제나 0이다.
  • 회전매매. 팔아서 들어올 돈을 담보로 잡아 결제 전에 다시 사는 거래다. 위의 매도 예정금액이 계산에 없으므로 이 프로젝트에서는 성립하지 않는다.
  • 미수금 연체 이자. 미수금 조회 응답에 경과일수와 누적이자 항목이 있지만 둘 다 0으로 고정돼 있다. 이자율 상수도, 날마다 이자를 쌓는 처리도 없다.
  • 반대매매. 미수금을 갚지 못한 계좌의 주식을 강제로 파는 처리가 없다. 담보유지비율을 계산하는 코드도 없다.
  • 계좌를 미수 상태로 바꾸는 처리. AccountStatus에 IN_ARREARS 값이 있고 상태 전이 규칙도 적혀 있지만, 이 값을 실제로 넣는 코드는 테스트에만 있다. 결제일에 잔고가 모자라도 계좌 상태는 ACTIVE로 남는다.
  • 영업일 달력. 결제 예정일을 달력 이틀 뒤로 잡는다. 주말과 공휴일을 건너뛰지 않는다.
  • 시장가 주문 처리. OrderType에 MARKET 값은 있지만 주문 접수와 매칭 어디에도 이 값에 따라 처리가 나뉘는 코드가 없다.

개념이 코드에서 불리는 이름

앞의 용어가 코드에서 어떤 이름으로 있는지 모아 둔 것이다. 매수 경로가 v1과 v2 둘로 나뉘어 있어서 같은 개념이 두 군데에 서로 다른 모양으로 있는 경우가 있다.

개념v1 경로 (관계형 DB)v2 경로 (메모리)
증거금률Account.marginRate — 계좌 행의 컬럼 하나. 두 경로가 같은 값을 읽는다.
예약 증거금Order.reservedMargin 컬럼, 계좌별 합계는 SUM 쿼리로 구한다AccountState.reservations — 주문 번호마다 가격과 잔량을 든 장부
미수금Unpaid 엔티티 — 계좌·주문·금액·결제 예정일·상태AccountState.unpaid 합계 하나와, 결제를 기다리는 PendingSettlement 행
결제 예정일settlementDate — 날짜 값, 오늘에 이틀을 더한다dueAtEpochMillis — 절대 시각, 지금에 48시간을 더한다
결제일 처리사용자가 상환 API를 부를 때만 처리한다settlement-worker가 일정 간격으로 예정일이 지난 건을 찾아 처리한다
계좌 상태AccountStatus — ACTIVE·IN_ARREARS·FROZEN. 실제로 사용되는 값은 ACTIVE뿐이다.
체결 번호tradeId — 체결 한 건마다 붙는 번호. 같은 체결이 두 번 전달돼도 한 번만 반영하려고 사용한다.
본 문서의 모든 내용은 계좌·주문·정산 관련 소스코드를 직접 대조하여 검증했다. '미구현' 표기는 관련 코드가 존재하지 않거나 단순 상수로 처리된 항목을 기준으로 한다.
