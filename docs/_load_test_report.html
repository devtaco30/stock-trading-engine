v1 부하 테스트 리포트 — 주문 접수 경로 k6로 매수 주문 3,000건을 쏘아 접수 파이프라인의 처리량과 결함을 확인했다

이 엔진은 매수 주문을 받을 때 계좌 잔고를 확인하고 주문 금액만큼을 예약 증거금으로 잡는다. 같은 계좌에 주문이 동시에 들어오면 두 요청이 같은 잔고를 근거로 검증을 통과할 수 있어, 한 계좌의 처리가 한 번에 하나씩만 실행돼야 한다. v1은 그것을 Postgres 계좌 행 비관적 락과 Kafka accountId 파티셔닝으로 했고, 그 직렬화가 곧 속도의 천장이 될 것이라는 가설을 세웠다. 그 천장이 실제로 어디인지, 그리고 부하에서만 드러나는 결함이 있는지를 확인하려고 부하를 걸었다.

결과는 둘로 나뉜다. 접수 계층(HTTP 202를 내려주는 데까지)은 초당 수백 건을 실패 없이 받았다. 그런데 그 뒤 Kafka를 거쳐 주문을 DB에 저장하는 단계에서 서로 다른 정상 주문이 같은 멱등키를 받아 중복으로 판정됐고, 그 충돌을 복구하려던 코드가 깨져 주문이 폐기됐다. 멱등키가 중복을 걸러내는 것은 설계대로다. 걸러진 것이 정상 주문이었고, 그것을 되살리려던 코드가 예외를 내고 멈춘 것이 결함이다. 모든 주문을 계좌 하나로 보낸 경우 3,000건 중 180건이 사라졌다.

시나리오 B · 계좌 50개로 분산 시나리오 A · 계좌 하나로 집중 결함과 유실 의도대로 동작한 것

먼저 용어

k6서버에 요청을 대량으로 보내 처리량·지연·한계를 측정하는 오픈소스 부하 테스트 도구(Grafana Labs). 여기서는 매수 요청을 쏘는 발생기로 썼다. 폭주를 재현하자 원래 있던 결함이 드러났다.
VU (virtual user, 가상 사용자)k6가 동시에 굴리는 가상 사용자 수. 동시에 몇 개의 요청이 진행 중인지를 정한다. 이 테스트는 50 VU다.
파티션 (partition)Kafka 토픽을 나눈 분할 단위. 같은 키의 메시지는 같은 파티션으로 가고, 파티션 하나는 컨슈머 스레드 하나가 맡는다. 그래서 파티션 수가 곧 병렬 처리 폭이다.
핫 파티션 (hot partition)같은 키를 가진 메시지가 많아 특정 파티션에만 쌓이는 상태. 파티션을 아무리 늘려도 그 하나를 맡은 스레드가 혼자 처리하므로 병렬성이 사라진다.
멱등키 (idempotency key)같은 요청이 두 번 처리되지 않게 구분하는 값. 이 시점의 코드는 (account_id, requested_at)에 UNIQUE 제약을 걸어 중복 주문을 막았다.
p95 · p99응답 시간을 느린 순으로 정렬했을 때 상위 5%·1% 지점의 값. 평균은 느린 소수를 가려버리므로, tail latency(가장 느린 요청들의 응답 시간)를 보려면 이 값을 본다.

무엇을 어떻게 측정했나

부하 대상은 주문 접수 경로 하나로 한정했다. 매도와 체결을 빼고 매수만 보낸 이유는, 문서에 적힌 병목이 접수 단계의 계좌 락과 직렬화이기 때문이다. 같은 종목(A900110) 매수만 넣으면 상대방 매도 주문이 없어 매칭은 일어나지 않고, 부하가 접수 경로에만 걸린다.

비교하는 조건은 하나다. 같은 부하를 파티션 키만 바꿔 두 번 돌린다. 시나리오 B는 계좌 1001~1050 중에서 무작위로 골라 보낸다. 주문마다 파티션 키가 달라진다. 시나리오 A는 모든 주문을 계좌 1001로 보내므로 파티션 키가 전부 같다. 한 사람이 사용하는 계좌에 주문이 초당 수백 건 들어오는 일은 실제로 없다. 계좌 단위 직렬화가 가장 불리해지는 조건을 일부러 준 것이다. 아래 그림이 그 둘이 파이프라인에서 어떻게 달라지는지다.

측정 경로와 파티션 분포
주문 3,000건이 어디를 지나는지, 그리고 계좌를 여러 개로 나눠 보냈을 때와 하나로만 보냈을 때 파티션에 어떻게 쌓였는지

파티션 0의 B 시나리오 건수를 "일부"로 적은 것은 측정 당시 오프셋을 p1·p2만 기록해서다. 세 파티션 합이 3,000건인 것은 확인했다.

결과

1. 접수 계층은 3,000건을 실패 없이 받았다

두 시나리오 모두 3,000 요청 전부 202 Accepted였고 HTTP 실패는 0%다. api는 검증을 마치면 Kafka에 넘기고 곧바로 응답하므로, order-engine이 밀리는 것과 무관하게 안정적이었다.

초당 접수 건수는 3,000건을 보내는 동안의 평균값이다. 총 요청 수를 그 구간의 시간으로 나눈 것이고, k6가 보고한 http_reqs 비율을 그대로 적었다. 단일 계좌인 A가 오히려 처리량이 높고 p99가 낮게 나왔다. api는 발행만 하므로 이 차이는 부하 도구의 스케줄링과 JVM 워밍업 편차 범위이고, 이 리포트가 보려는 order-engine 병목과는 관계가 없다.

2. 파티션은 Kafka 설정대로 나뉘었다

프로듀서(api)가 파티션 3개를 인식하도록 다시 띄운 뒤 측정했다. 주문들의 accountId가 서로 다른지에 따라 소비 폭이 나뉘었고, 그 수치가 위 도식의 두 행이다. 이 결과가 말해 주는 것은 Kafka 파티셔닝과 컨슈머 설정이 문서대로 동작한다는 것까지다. 엔진이 주문 한 건을 얼마나 빨리 처리하는지는 여기서 나오지 않는다. 이 측정에서 얻은 것은 그다음 항목이다.

3. 부하를 걸자 정상 주문이 폐기됐다

order-engine에서 심각한 결함이 나왔다. 부하를 걸자 (account_id, requested_at) UNIQUE 제약에서 충돌이 대량으로 발생했고, 그 충돌을 복구하려던 코드가 함께 깨졌다.

근본 원인

1. 서버가 찍는 수신 시각으로는 주문을 구분할 수 없다

OrderApiService가 요청마다 requestedAt = Instant.now()를 찍고, 그 값을 계좌 번호와 묶어 멱등키로 사용한다. 같은 밀리초에 도착한 주문들은 같은 값을 받는다. 그래서 계좌가 같고 도착 시각이 겹치면 (account_id, requested_at) UNIQUE를 위반한다. 단일 계좌인 A에서는 모든 요청이 한 계좌로 가서 충돌이 1,807건까지 늘었고, 계좌를 분산한 B에서는 110건에 그쳤다. 이 키는 같은 요청이 연달아 두 번 들어오는 것을 막으려고 설계됐는데, 부하에서는 서로 다른 정상 주문끼리도 충돌한다.

2. 롤백된 트랜잭션 안에서 복구 조회를 한다

OrderCommandService.placeBuyOrder:96~101, 매도 경로도 :144~148에서 같다.

// saveAndFlush가 UNIQUE 위반 → 이 트랜잭션은 rollback-only가 된다
order = orderRepository.saveAndFlush(order);
} catch (DataIntegrityViolationException e) {
    // 같은(망가진) 트랜잭션에서 다시 조회 → Hibernate가 거부한다
    Order existing = orderRepository
        .findByAccountIdAndRequestedAt(...)   // AssertionFailure
        .orElseThrow(...);
}

충돌을 잡아 기존 주문을 돌려주려는 의도였다. 그런데 예외가 난 트랜잭션 안에서 조회하면 Hibernate가 don't flush the Session after an exception occurs AssertionFailure를 던진다. Hibernate가 던진 예외라 컨슈머의 ack 후 폐기 분기에 걸리지 않고 그대로 전파된다. Spring Kafka의 DefaultErrorHandler가 9회 재시도한 뒤 포기하고 메시지를 버려 주문이 폐기된다.

이 catch 분기는 UNIQUE 충돌이 실제로 나야 실행된다. 당시 이 경로를 재현하는 테스트가 없어 한 번도 실행되지 않은 채 남아 있었고, 부하 테스트가 처음으로 이 분기를 실행시켰다.

이 측정에서 무엇을 정했나

파티셔닝은 유지한다. accountId를 키로 사용하면 같은 계좌의 주문이 언제나 한 스레드로 모여 순서대로 처리된다. 계좌 단위 직렬화라는 목적이 지켜지는 것을 확인했고, 계좌를 여럿으로 나눠 보냈을 때 세 스레드가 함께 소비하는 것도 함께 봤다.
멱등키와 복구 경로는 바꿔야 한다. 시각 기반 키를 사용하면 서로 다른 정상 주문끼리도 계속 충돌하는데, 그 충돌을 롤백된 트랜잭션 안에서 복구하려 하면 결국 주문이 폐기된다. 두 가지가 같은 경로에서 이어져 터지므로 함께 고쳐야 한다.
엔진의 처리 능력은 이 측정으로 알 수 없다. 이 리포트에 실린 수치는 둘 다 엔진이 주문을 처리하는 속도가 아니다. 접수 계층 수치는 api가 검증을 마치고 Kafka에 발행하는 데까지 걸리는 시간이고, 파티션 결과는 Kafka 설정이 동작하는지를 보여준다. order-engine이 실제로 처리하는 속도는 아래 한계 절에 적은 이유로 신뢰할 수 없어 싣지 않았다.
그 뒤 무엇을 했나. 위 두 원인을 결정 하나로 함께 처리했다(ADR-008 「주문 접수 멱등키를 requestId로 교체」). 멱등키를 요청마다 고유한 requestId로 교체했고, 중복 확인 조회를 REQUIRES_NEW 트랜잭션으로 분리해 망가진 트랜잭션을 다시 쓰지 않게 했다.

이 측정이 답하지 못하는 것

  • order-engine의 처리량(TPS)은 신뢰할 수 없어 싣지 않았다. DB 저장 건수로 소화 시간을 측정하려 했으나, Kafka 컨슈머 오프셋과 DB TRUNCATE가 따로 놀았고 위 결함의 재시도 재처리가 겹쳐 카운트가 오염됐다. 그래서 믿을 수 있는 신호만 실었다 — k6 접수 지표, 로그 기반 충돌·유실 델타, 파티션별 오프셋.
  • 브로커가 하나인 KRaft 단일 머신이라 네트워크와 복제 비용은 측정 밖이다.
  • 매수만 넣어 매칭·정산 경로는 이번 부하 밖이다. 접수 병목에 집중하려고 그렇게 설계했다.
  • k6와 애플리케이션과 DB가 한 머신에서 자원을 나눠 사용한다. 절대 수치보다 두 시나리오 사이의 상대 비교가 유효하다.
재현: docker compose -f docker-compose.yml -f docker-compose.loadtest.yml up -d → 앱 4개를 --spring.profiles.active=loadtest로 기동 → Redis 토큰 시드 → k6 run -e HOT=0|1 buy.js.
이 측정 뒤 별도 브랜치에서 끝내 main에 병합한 것 셋: decreaseHolding에 비관적 락 추가, 호가창 스냅샷 직렬화를 OrderbookRedisRepository로 이동, 컨슈머 ack 분기에 BusinessException 추가.
