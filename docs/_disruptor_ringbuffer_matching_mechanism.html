Kafka 매칭을 Disruptor RingBuffer가 대체하는 지점

matching-engine 모듈의 AS-IS 코드와 새로 만든 matching-disruptor 모듈(Unit 1)의 TO-BE 코드를 나란히 놓고, 실제로 무엇이 바뀌고 무엇이 그대로 남는지 클래스·메서드 단위로 확인합니다.

1. 맥락

매칭(matching)은 한 종목의 매수·매도 주문 중 체결 가능한 쌍을 찾는 작업입니다. 같은 호가창(OrderBook)을 스레드 두 개가 동시에 건드리면 어느 주문이 먼저 처리됐는지가 뒤섞여 체결 가격·수량이 달라질 수 있습니다. 그래서 한 종목의 주문은 항상 스레드 하나가 순서대로 처리해야 합니다.

지금(AS-IS) 이 순서를 보장하는 주체는 Kafka입니다. 종목코드를 파티션 키로 써서 같은 종목의 메시지를 항상 같은 컨슈머 스레드로 보내고, MatchingConsumer가 그 메시지를 받아 OrderBook을 호출합니다.

이번에 만든 matching-disruptor 모듈(TO-BE)은 이 역할을 Disruptor 라이브러리의 RingBuffer(고정 크기 원형 배열)로 옮깁니다. 네트워크와 브로커를 거치지 않고, 같은 프로세스 안에서 미리 만들어 둔 배열 슬롯으로 주문을 전달합니다. 아래에서 확인하겠지만 OrderBook 자체는 코드 한 줄도 바뀌지 않았습니다. 바뀐 건 주문을 매칭 스레드로 넘기는 방식과, 그 스레드 하나뿐임을 보장하는 주체입니다.

2. 용어

RingBuffer (링 버퍼)
Disruptor가 시작할 때 고정된 크기로 미리 만들어 두는 배열입니다. 이후에는 새 객체를 만들지 않고 같은 슬롯을 계속 돌려씁니다. OrderEvent 클래스 주석에 이 의도가 그대로 적혀 있습니다.
Sequence (시퀀스)
슬롯 하나를 가리키는 번호입니다. MatchingEngine.publishPlace가 호출될 때마다 ringBuffer.next()로 다음 번호를 예약합니다.
프로듀서 / 컨슈머
슬롯에 값을 채우는 쪽(프로듀서)과 채워진 슬롯을 순서대로 읽는 쪽(컨슈머)입니다. 이 프로젝트의 프로듀서는 MatchingEngine.publishPlace·publishCancel, 컨슈머는 MatchingEventHandler입니다.
EventHandler (이벤트 핸들러)
슬롯 하나가 공개(publish)될 때마다 Disruptor가 호출하는 콜백입니다. MatchingEventHandler.onEvent가 이 콜백을 구현합니다.
WaitStrategy (대기 전략)
컨슈머가 새 슬롯이 공개되길 기다리는 방식입니다. MatchingEngine은 인자를 생략하면 BlockingWaitStrategy를 씁니다. 조건 변수로 대기해 CPU를 계속 점유하지 않습니다.
OrderBook (호가창)
한 종목의 매수·매도 주문을 가격순으로 담아 체결 쌍을 찾는 자료구조입니다. AS-IS의 MatchingConsumer와 TO-BE의 MatchingEventHandler 둘 다 이 클래스를 그대로 호출합니다.

3. 범례

4. RingBuffer 슬롯의 생애주기

슬롯 하나가 예약부터 재사용까지 거치는 다섯 단계

코드 근거: MatchingEngine.publishPlace는 long sequence = ringBuffer.next()로 자리를 예약하고, try 블록에서 event.setPlace(...)로 값을 채운 뒤 finally에서 ringBuffer.publish(sequence)를 호출합니다. 값을 채우는 중 예외가 나도 예약한 자리가 막히지 않도록 publish를 finally에 둔 것입니다. 컨슈머 쪽 MatchingEventHandler.onEvent도 finally에서 event.clear()를 호출해 다음 재사용 전까지 이전 주문 데이터를 들고 있지 않게 합니다.

5. 원형 배열 안에서 프로듀서·컨슈머의 위치

고정 크기 배열이 원형으로 이어져 있고, 프로듀서 커서와 컨슈머 시퀀스가 그 위를 따라 이동한다

회색 슬롯은 아직 예약되지 않았거나 컨슈머가 이미 처리하고 clear()까지 끝낸 자리입니다. 주황 슬롯(6·7)은 setPlace·publish가 끝나 컨슈머를 기다리는 자리입니다. 청록으로 빛나는 슬롯(5)은 지금 MatchingEventHandler.onEvent가 읽고 있는 자리입니다. 실제 버퍼 크기는 MatchingEngine 생성자의 bufferSize 인자로 정하며, 2의 거듭제곱이어야 하는 Disruptor의 제약이 있습니다(DisruptorSmokeTest 주석에도 명시돼 있습니다).

6. 안 바뀌는 부분 — OrderBook

AS-IS와 TO-BE가 같은 파일을 그대로 참조한다

세 자료구조 전부 trading 모듈의 OrderBook.java 안에 있습니다. AS-IS의 MatchingConsumer도, TO-BE의 MatchingEventHandler도 이 클래스를 import해서 addOrder()·match()·cancelOrder()를 그대로 호출합니다. 이 파일에는 이번 작업으로 바뀐 줄이 없습니다.

7. 메커니즘 단계별 대체 — AS-IS ↔ TO-BE

같은 역할끼리 세로로 맞춰 무엇이 교체되고, 무엇이 차이로 남고, 무엇이 생략됐는지

매칭 실행 자체의 순서 — computeIfAbsent로 종목별 호가창을 얻고, containsOrder로 중복 주문을 걸러내고, addOrder 후 match()를 빈 결과가 나올 때까지 반복하는 흐름 — 는 MatchingConsumer.handlePlaced와 MatchingEventHandler.handlePlace가 거의 그대로 같습니다. 표에 올린 차이는 그 흐름을 감싸는 조건들(호가창을 어디에 두는지, 예외를 어디까지 잡는지, 체결을 어디로 내보내는지)입니다.

8. 비교표

항목AS-IS · KafkaTO-BE · Disruptor (Unit 1)

예외 발생 시비즈니스 예외는 폐기, 그 외는 Kafka가 재전달도메인 예외만 해당 슬롯 폐기, 그 외는 시퀀스 처리가 멈춤(별도 처리기 없음)

매칭 알고리즘OrderBook.java — 양쪽이 같은 클래스를 그대로 참조. 변경 없음.
대체가 아닌 것 — 체결 출력(Kafka fills 발행)과 Redis 스냅샷은 이번에 Disruptor로 옮겨진 게 아니라 Unit 1 범위 밖입니다. MatchingConsumer.writeOrderbookSnapshot()은 메시지 하나를 처리할 때마다(체결 여부와 무관하게) 호가창을 Redis에 저장하는데, MatchingEventHandler에는 이 호출이 없습니다. 정산으로 이어지는 체결 발행은 v2 전체 계획에서도 계속 Kafka를 씁니다.

9. 코드로 확인

슬롯 생애주기 — 프로듀서 쪽 (MatchingEngine.java)

matching-disruptor/src/main/java/.../MatchingEngine.java

public void publishPlace(long orderId, long accountId, String stockCode,
                         OrderSide side, BigDecimal price, int quantity, Instant orderAt) {
    long sequence = ringBuffer.next();
    try {
        OrderEvent event = ringBuffer.get(sequence);
        event.setPlace(orderId, accountId, stockCode, side, price, quantity, orderAt);
    } finally {
        ringBuffer.publish(sequence);
    }
}

슬롯 생애주기 — 컨슈머 쪽 (MatchingEventHandler.java)

matching-disruptor/src/main/java/.../MatchingEventHandler.java

@Override
public void onEvent(OrderEvent event, long sequence, boolean endOfBatch) {
    try {
        if (event.getType() == EventType.PLACE) {
            handlePlace(event);
        } else if (event.getType() == EventType.CANCEL) {
            handleCancel(event);
        }
    } catch (IllegalArgumentException | IllegalStateException e) {
        // 도메인 불변식 위반(수량 초과·잘못된 상태 전이 등)은 재시도해도 같으므로 이 이벤트만 폐기한다.
        // 핸들러에서 예외를 밖으로 던지면 Disruptor 기본 처리기가 시퀀스를 멈추므로 여기서 잡아 넘긴다.
        log.log(Level.WARNING, "[매칭] 이벤트 폐기: ...");
    } finally {
        // 슬롯 재사용 대비: 이 핸들러가 마지막 소비자이므로 처리 후 비운다.
        event.clear();
    }
}

종목별 호가창 보관 — AS-IS는 동시성 맵, TO-BE는 일반 맵

matching-disruptor/src/main/java/.../MatchingEventHandler.java

// 단일 스레드만 접근하므로 일반 HashMap 으로 충분하다.
private final Map<String, OrderBook> books = new HashMap<>();

private void handlePlace(OrderEvent event) {
    OrderBook book = books.computeIfAbsent(event.getStockCode(), k -> new OrderBook());
    if (book.containsOrder(event.getOrderId())) {
        return; // 멱등성: 같은 주문이 중복 도착하면 무시한다.
    }
    OrderEntry entry = toEntry(event);
    book.addOrder(entry);
    runMatch(event.getStockCode(), book);
}

AS-IS의 OrderBookRegistry가 ConcurrentHashMap을 쓰는 이유는 여러 파티션(종목)을 같은 Spring 빈 인스턴스가 동시에 다룰 수 있어서입니다. MatchingEventHandler는 Disruptor가 스레드 하나에만 배정하는 객체이므로, 이 인스턴스의 books 필드에는 애초에 다른 스레드가 접근하지 않습니다. 그래서 락이 있는 동시성 맵 대신 일반 HashMap으로 충분합니다.
