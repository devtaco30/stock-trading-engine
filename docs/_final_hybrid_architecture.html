DB 락 분산에서 LMAX 하이브리드로 — 컴포넌트별 전환

v1은 DB 비관적 락으로 정합성을 지키고 세 모듈을 Kafka로 이었습니다. v2는 계좌를 인메모리 소유권으로, 매칭을 종목별 LMAX 단일 스레드로 바꾸고, 통신을 성격에 따라 Aeron(속도)과 Kafka(내구성)로 나눕니다. 아래는 무엇을 무엇으로 바꾸는지의 상세입니다.

흐름 TO-BE (v2) — LMAX + Aeron/Kafka + 저널

바뀐 지점: DB 락이 사라지고(계좌 워커 single writer), 주문 경로가 Kafka→Aeron으로 µs가 됐고, settlement가 잔고 쓰기를 잃고, 체결 반영이 fan-out+멱등으로 옮겨졌습니다. 위 두 줄(주문→매칭)은 µs, 아래 두 줄(체결→반영)은 ms입니다.

저널·복제 — 전송(Aeron)과 저장을 분리한다

Aeron은 전송만 빠르게 하고 메모리에 남지 않습니다. 그래서 복구 근거인 저널은 따로 만듭니다. 입력이 도착하면 매칭(BLP)이 처리하기 전에, Journaler가 디스크에 append하고 Replicator가 대기 노드에 복제합니다. 셋이 같은 ring buffer를 fan-out으로 나눠 읽습니다.

입력 1건 → Journaler(디스크) · Replicator(복제) · BLP(매칭) 셋이 ring buffer fan-out
Aeron이 휘발이어도 복구는 됩니다. 전송(Aeron)과 저장(Journaler)은 다른 층이니까요. Kafka는 이 둘을 한 몸으로 묶어 ms인데, v2는 전송을 Aeron으로 빼서 µs로 만들고 저장 책임을 Journaler로 직접 집니다. 복구 = 이 저널 replay.

속도와 내구성은 같은 저울의 양끝. Aeron이 빠른 건 디스크·내구성을 뺐기 때문이라, 체결 정산엔 못 씁니다. 그래서 속도 경로=Aeron, 돈 경로=Kafka로 나눕니다.

LMAX가 필요한 이유. 나눌 수 있으면 샤딩이면 됩니다. 못 나누는 단위(한 종목 호가창, 한 계좌)를 단일 스레드로 둘 수밖에 없으니, 그 스레드를 극한으로 빠르게 만드는 것 — 그게 LMAX입니다.

정리 — v1에서 v2로

계좌를 DB 락에서 인메모리 소유권으로, 매칭을 인메모리에서 종목별 LMAX로, 통신을 Kafka 단일에서 Aeron(속도)·Kafka(내구성)로, 복구를 DB 조회에서 입력 저널 replay로 바꿉니다.

전송(Aeron)과 저장(Journaler)을 분리해 속도와 복구를 동시에 얻고, 계좌는 복제 없이 소유권으로 정합성을 지키며, 체결 교차는 fan-out+멱등으로 잇습니다. 학습으로는 이 전환이 분산 정합성과 하드웨어 최적화를 한 번에 담습니다.
