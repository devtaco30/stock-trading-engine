같은 매매 엔진을 두 번 만들다 — v1 락 기반, v2 single-writer + Aeron

주식 매매 엔진을 두 패러다임으로 구현하며 거래 시스템의 두 요구인 정합성과 속도를 어떻게 다르게 풀었는지 대조한다. v1은 정합성을 비관적 락으로 잡았고 그 대가로 속도에서 병목을 안았다. v2는 계좌마다 단일 writer로 락을 없애고 Aeron 전송으로 속도를 잡되 정합성은 유지한다.

①맥락 — 무슨 문제이고 왜 두 번 만들었나

주식 주문을 받아 체결하는 시스템은 두 가지를 동시에 지켜야 한다. 하나는 정합성이다. 잔고보다 많이 사거나, 가진 것보다 많이 파는 일이 없어야 하고 같은 주문이 두 번 처리돼 돈이 어긋나면 안 된다. 다른 하나는 속도다. 주문 처리가 늦으면 그만큼 체결 기회를 놓친다.

v1은 실무 표준 스택(Spring · JPA · Kafka)으로 정합성을 먼저 확보했다. 여러 스레드가 같은 계좌 행을 동시에 건드리지 못하도록 비관적 락을 걸었다. 정합성은 지켜졌지만 락을 쥔 채 검증 조회와 저장을 수행하는 구조라 락 보유 시간이 길어졌고, 주문 한 건마다 DB 입출력 비용이 그대로 들었다.

v2는 같은 엔진을 반대 방향으로 설계했다. 계좌 하나를 스레드 하나가 전담(single-writer)하게 만들어 락 자체를 없애고 주문·체결 경로의 전송을 Aeron으로 바꿔 지연을 µs(마이크로초, 100만분의 1초) 수준으로 낮춘다. 정합성은 락 대신 소유권·멱등·저널로 지킨다. 아래는 v1(AS-IS)과 v2(TO-BE)를 같은 항목에서 나란히 놓은 비교다.

②용어 — 먼저 이름과 뜻

아래 도식과 설명에 계속 나오는 이름들이다. 백엔드를 갓 시작한 눈높이로 뜻을 붙였다.

핫패스 hot path

요청 하나가 들어와 결과가 나갈 때까지 매번 지나는 경로. 여기에 든 비용은 요청마다 그대로 반복되므로, 느린 작업을 이 경로 밖으로 빼는 것이 성능 설계의 출발점이 된다.

비관적 락 pessimistic lock

어떤 DB 행을 수정하려는 트랜잭션이 그 행을 미리 잠가, 끝날 때까지 다른 트랜잭션이 같은 행을 못 건드리게 하는 방식. 충돌을 미리 막는 대신 뒤에 온 트랜잭션은 기다린다.

network I/O 입출력

프로세스가 DB나 메시지 브로커 같은 다른 서버와 데이터를 주고받는 일. 같은 프로세스 안 메모리 접근보다 수백~수천 배 느리다.

single-writer 단일 writer

하나의 상태(예: 한 계좌)를 오직 한 스레드만 수정하게 하는 규칙. 쓰는 주체가 하나뿐이라 락 없이도 충돌이 생기지 않는다.

Disruptor 디스럽터

LMAX가 공개한 링버퍼(고정 크기 순환 큐) 기반 처리 구조. 단일 소비자 스레드가 이벤트를 순서대로 처리해 락 없이 높은 처리량을 낸다.

Aeron 에어론

LMAX가 만든 저지연 메시징 라이브러리. UDP 위에 손실 복구·순서 보장을 더해, 브로커 없이 µs 수준으로 메시지를 전달한다.

Kafka 카프카

분산 메시지 브로커. 메시지를 디스크에 남겨 내구성과 재처리를 보장한다. 지연은 대략 ms(밀리초, 1000분의 1초) 수준.

Archive 저널 Aeron Archive

Aeron으로 들어온 스트림을 디스크에 녹화해 두는 기록 층. 장애 뒤 특정 지점부터 다시 재생(replay)해 상태를 복구한다.

조회 모델 read model / projection

메모리가 가진 최신 상태를 별도 소비자가 DB에 반영해 둔 읽기 전용 사본. 사용자의 "내 잔고" 조회는 여기서 답한다.

샤딩 sharding

데이터를 키로 나눠 각 조각을 특정 인스턴스가 전담하게 하는 것. 계좌는 accountId, 매칭은 stockCode로 나눈다.

멱등 idempotency

같은 요청이 두 번 들어와도 결과가 한 번 처리한 것과 같게 만드는 성질. 재전송·재처리가 있어도 돈이 두 번 빠지지 않는다.

④주문이 계좌에 반영되기까지 — 두 경로를 나란히

주문 한 건이 API에 도착해 계좌 잔고에 반영될 때까지 두 버전이 각각 어디를 거치는지 본다.

주문 경로 대조
주문 한 건이 지나는 자리를 v1과 v2에서 같은 순서로 늘어놓고, v2에서 없어진 것에 표시했다
v1 경로의 프로세스 Kafka 토픽 — 전달 지연은 ms 차수다 락이 걸리는 자리 v2 경로의 프로세스 v2가 쓰는 Aeron 전송과 Archive 기록
v2에서 없어진 자리 ① Postgres 계좌 행 락
  • v1은 같은 계좌를 여러 컨슈머 스레드가 고칠 수 있어 그 행을 잠갔다.
  • v2는 계좌마다 고치는 스레드가 하나여서 잠글 대상이 없다.
v2에서 없어진 자리 ② 잔고 검증 중의 디스크 접근
  • v1은 잔고를 확인하려고 Postgres를 조회하고 주문 행을 저장한다.
  • v2는 잔고를 메모리에서 확인해 검증 경로에 디스크가 없다.

붉은 칸은 v1에서 락이 걸리는 자리다. v2 경로에는 대응하는 칸이 없다. 위의 두 카드가 그 자리에 무엇이 있었고 왜 없어졌는지다.

v1 · AS-IS 비관적 락

API 서버는 계좌 소유와 가격 제한폭만 확인하고 order-requests 토픽에 발행한 뒤 202를 응답한다. 잔고 검증과 주문 저장은 그 토픽을 구독하는 컨슈머 스레드가 맡는다.

컨슈머는 Account 행에 PESSIMISTIC_WRITE 락을 걸고 예약 증거금 합계를 조회한 뒤 주문을 저장한다. 조회와 저장이 모두 락 안에 있어 락 보유 시간이 그만큼 길어지고 그동안 DB 커넥션도 함께 점유된다.

토픽 키가 accountId라 같은 계좌의 주문은 같은 파티션으로 가고 한 스레드가 순서대로 처리한다. 그래서 같은 계좌끼리 락을 다투는 경우는 줄었지만 주문 한 건마다 드는 DB 비용은 그대로 남는다. 컨슈머 스레드와 파티션을 3개에서 9개로 늘렸을 때 처리 용량이 227.3건/초에서 384.6건/초로 1.7배만 올라간 것이 그 근거다(⑦절 측정).

v2 · TO-BE single-writer + Aeron

계좌를 accountId로 샤딩해 각 계좌를 한 워커 스레드가 전담한다. 같은 계좌 주문은 그 스레드의 큐에 순서대로 쌓여 하나씩 처리되므로 두 스레드가 같은 잔고를 동시에 고치는 경우가 없다. 락을 걸 이유 자체가 사라진다.

주문은 Aeron으로 워커에 도착하고 워커가 받은 입력 스트림은 Archive 저널에 녹화된다. 잔고 검증은 메모리에서 끝나 검증 경로에 DB 왕복이 들어오지 않는다.

디스크를 아예 떼어낸 것은 아니다. 복구에 필요한 녹화와 스냅샷은 그대로 남아 있고, 그 기록이 주문 처리 경로 밖에 있다는 것이 v1과 다른 점이다.

⑤정합성을 지키는 방법 — 락 대신 무엇으로

락을 없앤 v2가 이중 차감·중복 처리를 어떻게 막는지, v1과 대조한다.

v1 · AS-IS 락 + 멱등키

동시 수정은 비관적 락으로 직렬화한다. 검증과 저장 사이에 다른 트랜잭션이 끼어들지 못한다(TOCTOU 방지).

  • 매수: Account 행 락 후 출금 가능 금액 검증
  • 매도: Holding 행 락 후 가용 수량 검증 (보유 − 미체결 매도)
  • 중복 접수: request_id UNIQUE 제약이 재전송을 막음
  • 체결 반영: tradeId 기록으로 at-least-once 중복을 멱등 처리
  • 데드락 방지: 락 순서를 Account → Holding으로 고정
v2 · TO-BE 소유권 + 멱등 + 저널

정합성은 소유권·멱등·저널 셋으로 지킨다. 계좌마다 소유 스레드가 하나뿐이라 동시 수정이 원천적으로 없고, 재처리와 장애는 멱등과 저널이 받아낸다.

  • 소유권: 계좌당 single-writer라 이중 차감이 생기지 않음
  • 체결 fan-out: 한 체결이 매수·매도 두 계좌를 바꿀 때 tradeId 멱등으로 중복 반영 차단
  • 상태 반영: full-state(전체 상태 + seq) 발행 후 오래된 seq는 거부 → 순서 뒤집힘·유실에도 자가 치유
  • 복구: Archive 저널을 특정 지점부터 replay해 매칭 상태 재구성

⑥상태를 어디에 두나 — DB가 원천인가, 메모리가 원천인가

잔고·보유의 진실을 어디가 쥐고 있는지가 두 버전의 근본 차이다.

v1 · AS-IS — DB가 진실의 원천
잔고를 확인하는 경로와 고치는 경로, 사용자가 조회하는 경로가 모두 같은 DB 행을 지난다
v1이 잔고를 읽거나 고치는 경로 Postgres — 잔고와 보유 수량의 진실이 있는 곳

잔고의 진실은 DB 행에 있다. 검증에 필요한 읽기도, 체결 반영 쓰기도, 사용자 조회도 모두 DB를 거친다. 그래서 주문 처리 경로마다 DB 입출력이 한 번씩 들어간다.

v2 · TO-BE — 핫패스의 권위는 메모리
계좌 엔진의 메모리가 잔고를 계산하고 소유한다. 그 상태는 Kafka를 거쳐 조회용 DB 사본에 반영된다
v2 프로세스 — 계좌 엔진과 프로젝션 소비자 Archive 저널 — 재기동 복구가 읽는 기록 Kafka 토픽 — 주문 처리 경로 밖이라 ms 차수여도 된다 Postgres 조회 모델 — 사용자 조회가 읽는 사본

주문 처리 경로에서 잔고의 진실은 메모리에 있다. DB는 프로젝션 소비자가 채우는 조회용 사본이고, 재기동 복구는 Archive replay가 맡는다.

v1 · AS-IS DB = 진실의 원천

잔고와 보유 수량의 진실은 DB에 있다. 주문 검증에 필요한 읽기, 체결 반영 쓰기, 사용자 잔고 조회가 모두 DB를 거친다. 정합성 관리가 단순해지는 대신 핫패스마다 DB 입출력이 들어간다.

v2 · TO-BE 핫패스의 권위는 메모리

잔고를 계산하고 소유하는 주인은 account-worker의 메모리다. 워커는 변경마다 계좌 전체 상태와 seq를 발행하고 프로젝션 소비자가 그것을 DB에 반영한다. DB는 사용자 조회용 읽기 모델 역할만 한다.

DB를 아예 떼어낸 것은 아니다. 계좌 생성과 기동 시 상태 적재, 사용자 조회는 DB를 거친다. 잔고 검증이 도는 핫패스에서만 DB 입출력을 뺐다. 재기동할 때 상태는 Archive 저널 replay로 복구한다.

⑦v1과 v2를 같은 조건에서 측정한 결과

여기까지가 구조 대조다. 두 구조가 실제로 얼마나 다른지를 같은 부하로 측정했다.

측정 구간은 주문 한 건이 실제로 계좌에 반영될 때까지다. v1은 Postgres orders 테이블에 주문 행이 저장된 시점, v2는 계좌 엔진이 증거금을 예약한 시점이 끝점이다. API가 202를 응답하는 시점까지만 측정하면 v1이 뒤로 미뤄 둔 일(브로커 기록 · 컨슈머 수신 · 락 · INSERT)이 통째로 빠지기 때문에, 그 뒤까지 포함했다.

도착률은 초당 192건으로 양쪽에 같게 주었다. 이 값은 v1이 소화할 수 있는 용량의 절반이다. 도착률이 용량에 가까워지면 측정값에 줄에서 기다린 시간이 섞인다. 그래서 양쪽 다 큐가 쌓이지 않는 상태에서 측정했다. 워밍업 한 패스를 버리고 측정 세 패스 가운데 두 번째와 세 번째 값을 인용한다.

v1은 컨슈머 스레드와 파티션을 3개에서 9개로 늘린 설정으로 측정했다. 그 설정의 용량이 더 높아서, v1에 더 나은 조건을 주고 비교했다.

계좌 반영까지 걸린 시간
같은 도착률 초당 192건에서, 주문 한 건이 계좌에 반영될 때까지 걸린 시간을 밀리초로 늘어놓았다

두 번째와 네 번째 막대가 p99다. 평균 하나만 보면 느린 소수를 알 수 없어서, 가장 느린 1%를 뺀 나머지가 어디까지 걸렸는지를 같이 본다.

초당 4,000건을 넣어도 밀리지 않았고, 부하 생성기가 먼저 한계에 닿아 천장은 측정하지 못했다
같은 도착률에서 v2가 p50은 약 6.5배, p99는 약 13배 빠르다. 두 값을 직접 나눠 확인했다(p50 12.4÷1.89=6.6 · 13.3÷2.04=6.5, p99 50.1÷3.89=12.9 · 55.9÷4.18=13.4). 용량은 v1이 초당 384.6건이고 v2는 초당 4,000건에서도 밀리지 않아 10배가 넘지만, v2의 천장을 측정하지 못했으므로 배수의 상한은 알 수 없다.
측정의 한계. 노트북 한 대에서 부하 생성기와 측정 대상이 같은 CPU를 나눠 사용한 조건이다. 초당 192건에서는 부하 생성기의 CPU 사용이 낮아 위 값을 그대로 인용할 수 있지만, 절대값은 이 장비의 값이다. v2에 초당 2,000건을 넣은 조건에서는 부하 생성기가 CPU의 절반 이상을 사용해 그 구간의 p99는 v2의 값이라고 볼 수 없어 이 문서에 넣지 않았다. 원본 데이터는 loadtest/evidence/에 있고, 측정 설계와 정정 이력은 v1/v2 접수 처리량 측정 리포트에 있다. v1만 따로 돌린 초기 부하 테스트는 v1 부하 테스트 리포트에 있다.

ADR-001은 이 구조의 병목을 "락 보유 중 쿼리 → 락 보유 시간 증가 → 커넥션 풀 고갈 위험"으로 기록하고 단기 개선(예약 증거금 합산을 Java 스트림에서 DB SUM으로 교체)과 장기 방향(accountId로 주문을 직렬화해 비관적 락 제거)을 함께 남겼다. v2의 single-writer는 그 장기 방향을 다른 패러다임으로 실현한 것이다.

두 구조의 대조가 이 프로젝트의 내용이다. v1은 DB 행 락으로 같은 계좌의 주문을 한 번에 하나씩만 처리해 정합성을 지켰다. 그 락 안에 검증 조회와 저장이 함께 들어가 있어 주문 한 건마다 DB 비용을 치렀다. v2는 계좌마다 고치는 스레드를 하나로 두어 같은 규칙을 락 없이 지킨다. 전송을 Aeron으로 바꿔 주문 처리 경로에서 브로커와 DB를 뺐고, 그 대가로 내구성을 직접 관리하게 됐다. 같은 문제를 두 방식으로 구현해 트레이드오프를 실측으로 대조한 것이 ⑦절의 수치다.
근거. 주문 경로와 락 위치는 OrderApiService · OrderRequestConsumer · OrderWriter · AccountRepository · HoldingRepository를 직접 열어 확인했다. 전송 구조는 핫패스를 Aeron과 Archive 저널로 정한 ADR-020, 정산 왕복만 Kafka로 되돌린 ADR-033, 계좌 상태를 DB 조회 모델로 내보내기로 한 ADR-021에 있다. 스냅샷 주기는 입력 1만 건마다 찍기로 정한 ADR-034, 락 구조와 그 병목 기록은 ADR-001과 ADR-003이다. ⑦절 수치의 원본 데이터는 loadtest/evidence/에 있다.
